# {frontmatter.title}

This page collects handlers for common tasks in the 1C exchange. The code of the examples comes from the plugin's tests, where each of them runs on a real exchange. The input and result of every hook are described in the [Hooks Reference](/medusa-integrations/1c-enterprise/hooks/reference).

<Note type="default" title="">

Each example registers its own handler, and Medusa allows only one handler per hook. To apply several examples to the same hook, combine them as shown in [Several Changes in One Handler](#several-changes-in-one-handler).

</Note>

## Skip Services

1C keeps services in the same item catalog as goods, but the store doesn't need them, since they have neither stock nor a product page. The handler removes products whose "ВидНоменклатуры" (item kind) requisite is "Услуга" (service) from the batch. The handler makes no database queries.

```ts title="src/workflows/hooks/onec-catalog.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { importOnecProductsWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"
import { readRequisite } from "@gorgo-store/medusa-erp-1c/hooks"

importOnecProductsWorkflow.hooks.setProducts(async ({ products }) => {
  return new StepResponse({
    products: products.filter(({ source }) => readRequisite(source, "ВидНоменклатуры") !== "Услуга"),
  })
})
```

A service removed from the batch isn't created in Medusa. If it got into the store earlier, the handler doesn't delete it, because the import doesn't touch removed products at all.

## Requisites and Properties to Product Fields

1C keeps the full name, weight and material in a product's requisites and properties, while a Medusa product has the `subtitle`, `weight` and `material` fields for them. The exchange doesn't fill these fields, so the handler moves the values itself. The handler makes no database queries.

```ts title="src/workflows/hooks/onec-catalog.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { importOnecProductsWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"
import { readProperty, readRequisite } from "@gorgo-store/medusa-erp-1c/hooks"

importOnecProductsWorkflow.hooks.setProducts(async ({ products, properties }) => {
  return new StepResponse({
    products: products.map(({ source, existing, product }) => {
      const fullName = readRequisite(source, "Полное наименование")
      const weight = Number.parseFloat((readRequisite(source, "Вес") ?? "").replace(",", "."))
      const [material] = readProperty(source, properties, "Материал")

      return {
        source,
        existing,
        product: {
          ...product,
          ...(fullName ? { subtitle: fullName } : {}),
          ...(Number.isFinite(weight) ? { weight } : {}),
          ...(material ? { material } : {}),
        },
      }
    }),
  })
})
```

The handler adds a field to the product only when 1C sent a value. The import would treat a key holding `undefined` as changed and erase a value set in the Medusa Admin. 1C may send the weight with a decimal comma, so the handler replaces it with a dot before parsing.

## Draft Without Images

A product without a single image shows up on the storefront as an empty card. The handler keeps such a product as a draft until an image arrives. The handler makes no database queries.

```ts title="src/workflows/hooks/onec-catalog.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { importOnecProductsWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"

importOnecProductsWorkflow.hooks.setProducts(async ({ products }) => {
  return new StepResponse({
    products: products.map((item) => {
      const images = item.product.images ?? item.existing?.images ?? []

      return images.length ? item : { ...item, product: { ...item.product, status: "draft" } }
    }),
  })
})
```

The exchange publishes the product on every import, so the product gets published by itself as soon as 1C sends an image for it. The flip side is that the next exchange turns a product without images that someone published by hand back into a draft.

## Draft for Products Hidden on the Site

The exchange publishes every product it receives. If part of the items in your 1C database is hidden from the site with a property, for example "Удалить с сайта", the very first export puts those products on the storefront unless a handler stops it. The handler keeps such products as drafts. It doesn't query the database.

```ts title="src/workflows/hooks/onec-catalog.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { importOnecProductsWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"
import { readProperty } from "@gorgo-store/medusa-erp-1c/hooks"

const HIDDEN_ON_SITE_PROPERTY = "Удалить с сайта"
const YES_VALUES = new Set(["true", "да"])

importOnecProductsWorkflow.hooks.setProducts(async ({ products, properties }) => {
  return new StepResponse({
    products: products.map((item) => {
      const hidden = readProperty(item.source, properties, HIDDEN_ON_SITE_PROPERTY).some((value) =>
        YES_VALUES.has(value.trim().toLowerCase()),
      )

      return hidden ? { ...item, product: { ...item.product, status: "draft" } } : item
    }),
  })
})
```

The standard 1C configuration has no "Удалить с сайта" property. It's added in a specific database, so put your own property's name here. 1C sends a boolean property as `true` and a dictionary property as its dictionary value, so the handler accepts both `true` and "Да". Once the property is cleared in 1C, the next exchange publishes the product again.

## Keep Edits Made in the Medusa Admin

Product titles and descriptions often get edited in the Medusa Admin, and the next exchange would bring back the values from 1C. The handler deletes these keys for existing products, and the import leaves the fields unchanged. The handler makes no database queries.

```ts title="src/workflows/hooks/onec-catalog.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { importOnecProductsWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"

importOnecProductsWorkflow.hooks.setProducts(async ({ products }) => {
  return new StepResponse({
    products: products.map((item) => {
      if (!item.existing) {
        return item
      }

      const { title: _title, description: _description, ...product } = item.product

      return { ...item, product }
    }),
  })
})
```

A new product gets its title and description from 1C, because it can't be created without a title. After that, title and description changes made in 1C no longer reach the store.

## Brand to Collection

1C keeps a product's brand in the "Бренд" (brand) property, while in Medusa it's handy to keep brands as collections. The handler looks up the collections named after the batch's brands and assigns the matching one to each product. The handler makes one database query per batch.

```ts title="src/workflows/hooks/onec-catalog.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { ContainerRegistrationKeys } from "@medusajs/framework/utils"
import { importOnecProductsWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"
import { readProperty } from "@gorgo-store/medusa-erp-1c/hooks"

importOnecProductsWorkflow.hooks.setProducts(async ({ products, properties }, { container }) => {
  const brandByOnecId = new Map(products.map(({ source }) => [source.id, readProperty(source, properties, "Бренд")[0]]))
  const titles = [...new Set([...brandByOnecId.values()].filter((title): title is string => Boolean(title)))]

  if (!titles.length) {
    return new StepResponse({ products })
  }

  const query = container.resolve(ContainerRegistrationKeys.QUERY)
  const { data: collections } = await query.graph({
    entity: "product_collection",
    fields: ["id", "title"],
    filters: { title: titles },
  })
  const collectionIdByTitle = new Map(collections.map((collection) => [collection.title, collection.id]))

  return new StepResponse({
    products: products.map((item) => {
      const collectionId = collectionIdByTitle.get(brandByOnecId.get(item.source.id) ?? "")

      return collectionId ? { ...item, product: { ...item.product, collection_id: collectionId } } : item
    }),
  })
})
```

The handler only looks collections up, and you create them in the Medusa Admin. A product whose brand has no collection stays unchanged. A handler can create collections too, but then it needs a rollback function, as described in the [handler rules](/medusa-integrations/1c-enterprise/hooks#how-a-hook-affects-exchange-speed).

## Variant Title from Options

A variant gets the name of its 1C offer, for example "Футболка (Красный, M)". The handler names the variant after its option values instead, "Красный / M". A variant without options keeps its 1C name. The handler doesn't query the database.

```ts title="src/workflows/hooks/onec-variants.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { importOnecVariantsWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"

importOnecVariantsWorkflow.hooks.setVariants(async ({ products }) => {
  return new StepResponse({
    products: products.map((item) => ({
      ...item,
      variants: item.variants.map((variant) => {
        const values = Object.values(variant.options ?? {})

        return values.length ? { ...variant, title: values.join(" / ") } : variant
      }),
    })),
  })
})
```

The values follow the order in which 1C listed the offer's properties. The handler returns every variant of the product, so Medusa doesn't delete any of them.

## SKU for a Taken Article

In 1C, the characteristics of an item often share its article, while a SKU in Medusa is unique. The plugin writes the article to the SKU of one variant only and saves the rest without a SKU. The handler gives such a variant a SKU built from the article and the start of the characteristic `Ид`, for example `ART-1-7a1f86c0`. It doesn't query the database.

```ts title="src/workflows/hooks/onec-variants.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { importOnecVariantsWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"

importOnecVariantsWorkflow.hooks.setVariants(async ({ products }) => {
  return new StepResponse({
    products: products.map((item) => ({
      ...item,
      variants: item.variants.map((variant) => {
        const { id, article } = (variant.metadata?.onec ?? {}) as { id?: string; article?: string }

        return variant.sku || !article || !id ? variant : { ...variant, sku: `${article}-${id.slice(0, 8)}` }
      }),
    })),
  })
})
```

The plugin keeps the article and the characteristic `Ид` in the variant's `metadata.onec`, so the handler doesn't need to parse the offer. Making the new SKU unique is up to the handler. If another variant already has that SKU, the exchange stops with an error.

## Wholesale Price for a Customer Group

The "Оптовая цена" (wholesale price) price type should apply only to customers in the "Опт" (wholesale) group. The handler activates the price list of this price type and gives it a customer group rule, so a guest still sees the retail price. The price list gets the `override` type, so that a group customer pays exactly the 1C price rather than the lower of the wholesale and retail ones. The handler makes one database query per batch, and only when the batch has this price type.

```ts title="src/workflows/hooks/onec-prices.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { ContainerRegistrationKeys, PriceListStatus, PriceListType } from "@medusajs/framework/utils"
import { importOnecPricesWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"

const WHOLESALE_PRICE_TYPE_NAME = "Оптовая цена"
const WHOLESALE_GROUP_NAME = "Опт"

importOnecPricesWorkflow.hooks.setPriceLists(async ({ priceLists }, { container }) => {
  if (!priceLists.some(({ source }) => source.name === WHOLESALE_PRICE_TYPE_NAME)) {
    return new StepResponse({ priceLists })
  }

  const query = container.resolve(ContainerRegistrationKeys.QUERY)
  const { data: groups } = await query.graph({
    entity: "customer_group",
    fields: ["id"],
    filters: { name: WHOLESALE_GROUP_NAME },
  })
  const groupId = groups[0]?.id

  if (!groupId) {
    return new StepResponse({ priceLists })
  }

  return new StepResponse({
    priceLists: priceLists.map((item) =>
      item.source.name === WHOLESALE_PRICE_TYPE_NAME
        ? {
            ...item,
            priceList: {
              ...item.priceList,
              status: PriceListStatus.ACTIVE,
              type: PriceListType.OVERRIDE,
              rules: { "customer.groups.id": [groupId] },
            },
          }
        : item,
    ),
  })
})
```

Create the "Опт" group in the Medusa Admin beforehand. Without it, the price list stays a draft, just as it would without a handler. The handler sets this price list's status, type and rules on every exchange, so the next exchange reverts any changes you make to them in the Medusa Admin.

## Skip Test Orders

Orders the team places to check the storefront shouldn't reach 1C. The handler removes orders from addresses in the `@test.invalid` domain from the export. The handler makes no database queries.

```ts title="src/workflows/hooks/onec-orders.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { exportOnecOrdersWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"

exportOnecOrdersWorkflow.hooks.setOrders(async ({ orders }) => {
  return new StepResponse({
    orders: orders.filter(({ source }) => !source.email?.endsWith("@test.invalid")),
  })
})
```

A removed order doesn't get the exported mark. So it reaches the hook on every export, and the handler removes it again each time.

## Order Source and Customer Comment

A manager in 1C wants to see where an order came from and what the customer wrote. A Medusa order has no separate field for a comment, so the storefront puts it in `metadata.comment`. The handler moves the comment into the document and adds the "Источник" (source) requisite. The handler makes no database queries.

```ts title="src/workflows/hooks/onec-orders.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { exportOnecOrdersWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"

exportOnecOrdersWorkflow.hooks.setOrders(async ({ orders }) => {
  return new StepResponse({
    orders: orders.map(({ source, document }) => {
      const comment = source.metadata?.comment

      return {
        source,
        document: {
          ...document,
          ...(typeof comment === "string" && comment ? { comment } : {}),
          requisites: [...document.requisites, { name: "Источник", value: "Интернет-магазин" }],
        },
      }
    }),
  })
})
```

Saving the comment to the order's `metadata.comment` is up to your storefront. The "Источник" requisite gets into the document, and how 1C handles it depends on your configuration.

## Company Counterparty and Shipping Method

A customer from the "Юрлица" (companies) group should go to 1C as a counterparty with an INN and KPP (tax IDs), and the manager needs the shipping method. The INN and KPP are stored in the customer's `metadata` and the shipping method in the order, and the handler gets all of it with one query for the whole export.

```ts title="src/workflows/hooks/onec-orders.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { ContainerRegistrationKeys } from "@medusajs/framework/utils"
import { exportOnecOrdersWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"

const COMPANY_GROUP_NAME = "Юрлица"

exportOnecOrdersWorkflow.hooks.setOrders(async ({ orders }, { container }) => {
  if (!orders.length) {
    return new StepResponse({ orders })
  }

  const query = container.resolve(ContainerRegistrationKeys.QUERY)
  const { data } = await query.graph({
    entity: "order",
    fields: ["id", "customer.metadata", "customer.groups.name", "shipping_methods.name"],
    filters: { id: orders.map(({ source }) => source.id) },
  })
  const extraById = new Map(data.map((order) => [order.id, order]))

  return new StepResponse({
    orders: orders.map(({ source, document }) => {
      const extra = extraById.get(source.id)
      const isCompany = extra?.customer?.groups?.some((group: { name?: string } | null) => group?.name === COMPANY_GROUP_NAME)
      const { inn, kpp } = (extra?.customer?.metadata ?? {}) as { inn?: string; kpp?: string }
      const delivery = extra?.shipping_methods?.[0]?.name

      return {
        source,
        document: {
          ...document,
          counterparties: document.counterparties.map((counterparty) =>
            isCompany && inn ? { ...counterparty, inn, ...(kpp ? { kpp } : {}) } : counterparty,
          ),
          requisites: delivery
            ? [...document.requisites, { name: "Способ доставки", value: delivery }]
            : document.requisites,
        },
      }
    }),
  })
})
```

The query goes through the link between the order and the customer, so in the database it turns into three SQL queries, but for the whole export rather than per order. The plugin writes the INN and KPP after the counterparty's name and before the address. This position hasn't been checked against a real 1C configuration yet, so make sure your configuration reads them from there.

## Schema Version for an Older 1C Configuration

The plugin writes `ВерсияСхемы="2.10"` to the root of the file, while an older 1C configuration may expect a different version, for example 2.05. The product and document models have no schema version, so the handler edits the finished XML through `setPayload`, in both the catalog export and the order export. The handler makes no database queries.

```ts title="src/workflows/hooks/onec-payload.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { exportOnecCatalogWorkflow, exportOnecOrdersWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"

const OLD_SCHEMA_VERSION = "2.05"

function withSchemaVersion(payload: string): string {
  return payload.replace(/ВерсияСхемы="[^"]*"/, `ВерсияСхемы="${OLD_SCHEMA_VERSION}"`)
}

exportOnecCatalogWorkflow.hooks.setPayload(async ({ payload }) => {
  return new StepResponse({ payload: withSchemaVersion(payload) })
})

exportOnecOrdersWorkflow.hooks.setPayload(async ({ payload }) => {
  return new StepResponse({ payload: withSchemaVersion(payload) })
})
```

The handler changes only the version number, and the file structure stays the one the plugin builds. If your configuration also expects a different structure, edit the XML in the same handler. A string replacement knows nothing about the XML structure, so anything you can express through `setOrders` is more reliable there.

## Several Changes in One Handler

Medusa allows only one handler per hook, so all of your project's changes for one hook have to go into a single handler. It's convenient to keep each change in its own function and call them in turn. Put filtering first, so the other changes don't spend time on removed elements.

```ts title="src/workflows/hooks/onec-catalog.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { importOnecProductsWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"
import { readRequisite, type ProductToImport } from "@gorgo-store/medusa-erp-1c/hooks"

function skipServices(products: ProductToImport[]): ProductToImport[] {
  return products.filter(({ source }) => readRequisite(source, "ВидНоменклатуры") !== "Услуга")
}

function keepManagerEdits(products: ProductToImport[]): ProductToImport[] {
  return products.map((item) => {
    if (!item.existing) {
      return item
    }

    const { title: _title, description: _description, ...product } = item.product

    return { ...item, product }
  })
}

importOnecProductsWorkflow.hooks.setProducts(async ({ products }) => {
  return new StepResponse({ products: keepManagerEdits(skipServices(products)) })
})
```

Make the functions that need database access async and call them with `await`. That way each of them still makes one query per batch.
