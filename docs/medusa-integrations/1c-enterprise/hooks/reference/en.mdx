# {frontmatter.title}

This reference describes when each hook runs, what its handler receives and may return, and what the plugin does with the result. The rules shared by all hooks are on the [Workflow Hooks](/medusa-integrations/1c-enterprise/hooks) page.

## setProducts

A hook of the `importOnecProductsWorkflow` workflow (`import-onec-products`). It runs on every catalog batch of up to 100 products, before they're compared with Medusa products. With a 10,000-product catalog, it runs 100 times.

```ts title="src/workflows/hooks/onec-catalog.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { importOnecProductsWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"

importOnecProductsWorkflow.hooks.setProducts(async ({ products, properties }, { container }) => {
  // ...

  return new StepResponse({ products })
})
```

The handler receives the batch's products and the classifier properties:

The exchange fills `title`, `description`, `external_id`, `type_id`, `status`, `metadata`, `category_ids` and `sales_channels` in `product`, and `thumbnail` and `images` only when 1C sent images. A new product has `handle`, and an existing one has it only when [Update the handle when a product is renamed in 1C](/medusa-integrations/1c-enterprise/settings#edit-the-exchange-rules) is on and the name changed in 1C. The exchange sets `status` to `published` on every product, including one unpublished by hand. To keep some products as drafts, set `status` in the handler, as in the [Draft for Products Hidden on the Site](/medusa-integrations/1c-enterprise/hooks/examples#draft-for-products-hidden-on-the-site) example. It doesn't fill `subtitle`, `weight`, `length`, `height`, `width`, `origin_country`, `hs_code`, `mid_code`, `material`, `collection_id` and `discountable`, but a handler can set them, and the import writes them like the rest.

Return `new StepResponse({ products })`. The handler may edit `product` and remove products from the batch. It can't:

- return a product that wasn't in the batch, or the same product twice;
- change `existing`;
- delete or change `external_id` and `metadata.onec.id` of a new product, because without them the next exchange creates the product a second time;
- change `external_id` and `metadata.onec.id` of an existing product. Deleting these keys is allowed, and the fields then stay as they are.

After the hook, the plugin compares `product` with `existing` and writes only the fields that differ. The plugin creates a product that has no `existing`. A product removed from the batch is neither created nor updated in this exchange.

## setVariants

A hook of the `importOnecVariantsWorkflow` workflow (`import-onec-variants`). The workflow runs inside the offers import, so the hook is called on every offers batch (up to 100 products with all their offers). It runs after the plugin has matched the offers to Medusa variants and decided their SKUs, and before the comparison with Medusa.

```ts title="src/workflows/hooks/onec-variants.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { importOnecVariantsWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"

importOnecVariantsWorkflow.hooks.setVariants(async ({ products, properties }, { container }) => {
  // ...

  return new StepResponse({ products })
})
```

The handler receives the batch's products that already exist in Medusa, along with the offers package properties. The plugin skips the offers of a product that isn't in Medusa yet before calling the hook:

The exchange doesn't fill `allow_backorder`, `barcode`, `ean` and `weight`, but a handler can set them, and the import writes them like the rest.

Return `new StepResponse({ products })`. The handler may edit variants, remove variants from `variants` and remove products from the batch. It can't:

- return a product that wasn't in the batch, or the same product twice;
- return `variants` as anything but an array;
- give a product another product's variant, or return the same variant twice;
- change `metadata.onec.id` of an existing variant, because the next exchange matches the variant by it. Deleting the `metadata` key is allowed, and the variant's metadata then stays as it is.

After the hook, the plugin derives the product's options from the resulting variants. An option with the same title as before the hook keeps its link to the 1C property and its dictionary, and a value missing from the dictionary is added to it. An option with a new title is created without a link to a property, with the values found in the variants. The plugin then compares the variants with `existing` and writes the set only when something in it changed. Medusa deletes a variant removed from `variants`. A product removed from the batch keeps its variants and options unchanged in this exchange.

<Note type="warning">

The plugin finds an option with a new title by that title only within one batch. In the following batches the title is already taken, and their products get a separate option instead of the shared one. So rename options in 1C, and change variant fields and values in the handler.

</Note>

## setPriceLists

A hook of the `importOnecPricesWorkflow` workflow (`import-onec-prices`). The workflow runs inside the offers import, so the hook runs on every offers batch (up to 100 products with all their offers) before reconciling with Medusa.

```ts title="src/workflows/hooks/onec-prices.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { importOnecPricesWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"

importOnecPricesWorkflow.hooks.setPriceLists(async ({ priceLists }, { container }) => {
  // ...

  return new StepResponse({ priceLists })
})
```

Return `new StepResponse({ priceLists })`. If the handler puts a key into `priceList`, such as `rules` or `status`, the import writes it when its value differs from the stored one. The constraints are:

- you can't return a price type that wasn't in the batch, or the same type twice;
- you can't change `existing`;
- a price must belong to a variant from this batch, `amount` must be a number, and a variant can't have two prices in the same currency.

After the hook, the plugin creates price lists for new price types and marks them with `metadata.onec.price_type_id`. In existing ones, it writes the changed `priceList` keys and reconciles prices by variant and currency. The plugin adds new prices, updates changed ones and removes extra ones. If you remove a price type from the list, the plugin touches neither its price list nor its prices in this batch.

## setPayload

Two workflows have this hook, `exportOnecCatalogWorkflow` (`export-onec-catalog`) and `exportOnecOrdersWorkflow` (`export-onec-orders`). It runs once per export, when the XML is already built, and in the order export it runs after `setOrders`. It's a fallback for changes that the product or document model can't express, for example the schema version your 1C configuration expects.

```ts title="src/workflows/hooks/onec-payload.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { exportOnecCatalogWorkflow, exportOnecOrdersWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"

exportOnecCatalogWorkflow.hooks.setPayload(async ({ payload }) => {
  // ...

  return new StepResponse({ payload })
})

exportOnecOrdersWorkflow.hooks.setPayload(async ({ payload }) => {
  // ...

  return new StepResponse({ payload })
})
```

These are two separate hooks, and each one is registered on its own workflow. The handler receives the XML as a string:

## 1C Reading Functions

`@gorgo-store/medusa-erp-1c/hooks` exports two functions that read the values of a 1C product the way CommerceML lays them out.

### readRequisite

```ts
readRequisite(source, name): string | undefined
```

Returns the first value of a requisite from `ЗначенияРеквизитов`, found by its `Наименование`. The name is compared exactly, including spaces and case. In 1C a requisite name is free text, so `Полное наименование` and `ПолноеНаименование` are different requisites. If there's no such requisite, the function returns `undefined`.

### readProperty

```ts
readProperty(source, properties, nameOrId): string[]
```

Returns the values of a property from `ЗначенияСвойств`. The function looks the property up by `Ид` or by name, and expands reference values through `properties` from the hook input. A lookup by name collects all properties with that name, because 1C may have a separate "Бренд" (brand) property for each category. If there are no values, the function returns an empty array.
