# {frontmatter.title}

В справочнике описано, когда вызывается каждый хук, что получает и что может вернуть его обработчик и что плагин делает с результатом. Общие для всех хуков правила описаны на странице [Хуки воркфлоу](/medusa-integrations/1c-enterprise/hooks).

## setProducts

Хук воркфлоу `importOnecProductsWorkflow` (`import-onec-products`). Вызывается на каждую порцию каталога (до 100 товаров) перед сравнением с товарами Medusa. При каталоге в 10 000 товаров хук сработает 100 раз.

```ts title="src/workflows/hooks/onec-catalog.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { importOnecProductsWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"

importOnecProductsWorkflow.hooks.setProducts(async ({ products, properties }, { container }) => {
  // ...

  return new StepResponse({ products })
})
```

В `product` обмен записывает `title`, `description`, `external_id`, `type_id`, `status`, `metadata`, `category_ids` и `sales_channels`, а `thumbnail` и `images` только если 1С прислала изображения. `handle` есть у нового товара, а у существующего только при включённой настройке [Обновлять ярлык при переименовании товара в 1С](/medusa-integrations/1c-enterprise/settings#редактирование-правил-обмена), когда в 1С поменялось название. Поля `subtitle`, `weight`, `length`, `height`, `width`, `origin_country`, `hs_code`, `mid_code`, `material`, `collection_id` и `discountable` обмен не заполняет, но их может задать обработчик, и импорт запишет их наравне с остальными.

Верните `new StepResponse({ products })`. Обработчик может менять `product` и убирать товары из порции. Обработчик не может:

- вернуть товар, которого не было в порции, или один товар дважды;
- поменять `existing`;
- удалить или поменять `external_id` и `metadata.onec.id` у нового товара, потому что без них следующий обмен создаст товар повторно;
- поменять `external_id` и `metadata.onec.id` у существующего товара. Удалить эти ключи можно, тогда поля останутся как есть.

После хука плагин сравнивает `product` с `existing` и записывает только отличающиеся поля. Товар без `existing` плагин создаёт. Товар, убранный из порции, в этом обмене не создаётся и не обновляется.

Поля `allow_backorder`, `barcode`, `ean` и `weight` обмен не заполняет, но их может задать обработчик, и импорт запишет их наравне с остальными.

Верните `new StepResponse({ products })`. Обработчик может менять варианты, убирать варианты из `variants` и убирать товары из порции. Обработчик не может:

- вернуть товар, которого не было в порции, или один товар дважды;
- вернуть `variants` не массивом;
- отдать товару вариант другого товара или вернуть один вариант дважды;
- поменять `metadata.onec.id` у существующего варианта, потому что по нему следующий обмен сопоставляет вариант. Удалить ключ `metadata` можно, тогда метаданные варианта останутся как есть.

После хука плагин выводит опции товара из итоговых вариантов. Опция с тем же названием, что до хука, сохраняет связь со свойством 1С и его справочником, а значение не из справочника добавляется к нему. Опция с новым названием создаётся без связи со свойством, со значениями из вариантов. Затем плагин сравнивает варианты с `existing` и записывает набор, только если в нём что-то изменилось. Вариант, убранный из `variants`, Medusa удалит. У товара, убранного из порции, в этом обмене не меняются ни варианты, ни опции.

<Note type="warning">

Опцию с новым названием плагин находит по названию только внутри одной порции. В следующих порциях это название уже занято, и их товары получат отдельную опцию вместо общей. Поэтому опции лучше переименовывать в 1С, а в обработчике менять поля и значения вариантов.

</Note>

## setPayload

Хук есть у двух воркфлоу, `exportOnecCatalogWorkflow` (`export-onec-catalog`) и `exportOnecOrdersWorkflow` (`export-onec-orders`). Он вызывается один раз за выгрузку, когда XML уже собран, а при выгрузке заказов срабатывает после `setOrders`. Это резервный способ внести правки, которые нельзя выразить через модель товара или документа, например версию схемы, которую ожидает ваша конфигурация 1С.

```ts title="src/workflows/hooks/onec-payload.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { exportOnecCatalogWorkflow, exportOnecOrdersWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"

exportOnecCatalogWorkflow.hooks.setPayload(async ({ payload }) => {
  // ...

  return new StepResponse({ payload })
})

exportOnecOrdersWorkflow.hooks.setPayload(async ({ payload }) => {
  // ...

  return new StepResponse({ payload })
})
```

Это два разных хука, и каждый регистрируется у своего воркфлоу. Обработчик получает XML строкой:

      children: []
    }
  ]}

Верните `new StepResponse({ payload })` с итоговой строкой XML. Если обработчика нет, в 1С уходит XML, собранный плагином. Какие заказы получат отметку о выгрузке, определяет `setOrders`, а не этот хук.

## Функции чтения 1С

`@gorgo-store/medusa-erp-1c/hooks` экспортирует две функции, которые читают значения товара 1С с учётом того, как их раскладывает CommerceML.

### readRequisite

```ts
readRequisite(source, name): string | undefined
```

Возвращает первое значение реквизита из `ЗначенияРеквизитов`, найденного по `Наименованию`. Имя сравнивается точно, с учётом пробелов и регистра. В 1С наименование реквизита является свободным текстом, поэтому `Полное наименование` и `ПолноеНаименование` будут разными реквизитами. Если реквизита нет, функция возвращает `undefined`.

### readProperty

```ts
readProperty(source, properties, nameOrId): string[]
```

Возвращает значения свойства из `ЗначенияСвойств`. Функция ищет свойство по `Ид` или по имени, а значения из справочников разворачивает через `properties` из входных данных хука. При поиске по имени она собирает все одноимённые свойства, потому что в 1С для каждой категории может быть заведено своё свойство «Бренд». Если значений нет, функция возвращает пустой массив.
