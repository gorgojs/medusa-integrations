# {frontmatter.title}

Обмен с 1С выполняется в воркфлоу Medusa, и в нескольких из них плагин предоставляет хуки. Обработчик хука получает данные, которые обмен собирается записать в Medusa или отправить в 1С, и возвращает их изменённую версию. Так можно переносить реквизиты 1С в поля товара, добавлять в заказ данные, которых нет в Medusa, или включать прайс-лист для группы покупателей, не меняя код плагина.

<Note type="info" title="Что такое хук воркфлоу">

Хук воркфлоу позволяет встроить собственную функцию в воркфлоу Medusa. Medusa вызывает её во время выполнения воркфлоу и передаёт ей данные, а результат функции воркфлоу использует дальше. Подробнее читайте в [документации Medusa](https://docs.medusajs.com/learn/fundamentals/workflows/workflow-hooks).

</Note>

## Доступные хуки

| Воркфлоу | Хук | Когда вызывается | Что меняет |
| --- | --- | --- | --- |
| `importOnecProductsWorkflow` | [`setProducts`](/medusa-integrations/1c-enterprise/hooks/reference#setproducts) | на каждую порцию каталога, до 100 товаров | товары Medusa из `import.xml` |
| `importOnecVariantsWorkflow` | [`setVariants`](/medusa-integrations/1c-enterprise/hooks/reference#setvariants) | на каждую порцию предложений, до 100 товаров | варианты товаров и их опции из `offers.xml` |
| `importOnecPricesWorkflow` | [`setPriceLists`](/medusa-integrations/1c-enterprise/hooks/reference#setpricelists) | на каждую порцию предложений, до 100 товаров | прайс-листы нерозничных типов цен и их цены |
| `exportOnecOrdersWorkflow` | [`setOrders`](/medusa-integrations/1c-enterprise/hooks/reference#setorders) | один раз на выгрузку заказов | документы заказов, которые уйдут в 1С |
| `exportOnecOrdersWorkflow`, `exportOnecCatalogWorkflow` | [`setPayload`](/medusa-integrations/1c-enterprise/hooks/reference#setpayload) | один раз на выгрузку, когда XML собран | XML выгрузки заказов или каталога |

Воркфлоу импортируйте из `@gorgo-store/medusa-erp-1c/workflows`. Типы входных данных и результатов хуков, а также функции чтения реквизитов и свойств 1С импортируйте из `@gorgo-store/medusa-erp-1c/hooks`.

<Note type="default" title="">

Во время беты имена хуков и структура элементов ещё могут измениться по отзывам участников. После релиза они будут меняться только в мажорных версиях плагина.

</Note>

## Подключение обработчика

Зарегистрируйте обработчик в файле внутри `src/workflows/hooks` вашего проекта Medusa, и Medusa загрузит его при запуске сервера. Например, этот обработчик не пропускает в магазин услуги из 1С:

```ts title="src/workflows/hooks/onec-catalog.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { importOnecProductsWorkflow } from "@gorgo-store/medusa-erp-1c/workflows"
import { readRequisite } from "@gorgo-store/medusa-erp-1c/hooks"

importOnecProductsWorkflow.hooks.setProducts(async ({ products }) => {
  return new StepResponse({
    products: products.filter(({ source }) => readRequisite(source, "ВидНоменклатуры") !== "Услуга"),
  })
})
```

Обработчик получает товары порции и возвращает их в `StepResponse`, оставив только те, у которых реквизит «ВидНоменклатуры» не равен «Услуга». Функция `readRequisite` читает реквизит товара 1С по наименованию, поэтому разбирать CommerceML вручную не нужно.

## Как устроен элемент

Каждый хук, кроме `setPayload`, получает массив элементов. Элемент собирает в одном месте всё, что нужно обработчику для решения:

- `source` – запись, из которой строится результат. При импорте это запись 1С, у `setVariants` все предложения товара, при выгрузке заказ Medusa.
- `existing` – текущая запись Medusa. Передаётся только при импорте и только для записи, которая уже существует в Medusa.
- Целевое поле – то, что обмен запишет или отправит. У товара это `product`, у вариантов товара `variants`, у типа цен `priceList` и `prices`, у заказа `document`.

Обработчик меняет целевое поле и возвращает элементы. `setPayload` устроен иначе. Он получает готовый XML строкой и нужен для правок, которые нельзя выразить через модель товара или документа, например для версии схемы, которую ожидает ваша конфигурация 1С.

## Правила результата

- **Верните `new StepResponse({ <массив> })`.** Плагин использует только массив, поэтому остальные ключи входных данных возвращать не нужно.
- **Уберите элемент, чтобы пропустить запись в этом обмене.** Заказ, убранный из выгрузки, не получит отметку о выгрузке и уйдёт со следующей.
- **Удалите ключ из `product`, `priceList` или варианта в `variants`, чтобы оставить поле без изменений.** Так значение, заданное в Medusa Admin, сохранится после обмена. Документ заказа уходит в 1С целиком, и удалённый ключ превратится в пустой узел в `orders.xml`. Поэтому в документе меняйте значения, а не удаляйте их.
- **Не добавляйте элементы и не меняйте ключи сопоставления.** Плагин сопоставляет товар и вариант по `Ид` 1С ещё до вызова хука, а 1С узнаёт заказ по `Ид` документа. Если обработчик нарушит это правило, плагин остановит обмен с ошибкой, в которой указано имя хука.
- **На одинаковые входные данные возвращайте одинаковый результат.** Иначе каждый повторный обмен будет заново перезаписывать каталог.

<Note type="default" title="">

Если обработчик вернёт обычный объект или ничего не вернёт, обмен остановится с ошибкой вида `importOnecProductsWorkflow.hooks.setProducts handler must return new StepResponse({ products }), it returned nothing usable`. Medusa передаёт плагину только содержимое `StepResponse`.

</Note>

## Один обработчик на хук

Medusa разрешает только один обработчик на хук во всём приложении. Если зарегистрировать на тот же хук второй обработчик, сервер не запустится и выдаст ошибку `Cannot define multiple hook handlers for the setProducts hook`. Объедините все правки проекта для одного хука в одном обработчике и вызывайте их в нём по очереди.

---

## Как хук влияет на скорость обмена

Обработчик выполняется внутри шага воркфлоу, и всё это время 1С ждёт ответа. `setProducts`, `setVariants` и `setPriceLists` вызываются на каждую порцию, поэтому при каталоге в 10 000 товаров каждый из них сработает сто раз. Движок воркфлоу копирует входные данные и результат хука, а вместе с ними и всё, что вы добавите в элемент.

Так три вида обработчика `setProducts` влияют на обмен:

| Обработчик | Запросов к базе за импорт каталога | Время повторного импорта |
| --- | ---: | ---: |
| Только поля из входных данных | столько же, сколько без обработчика | в пределах погрешности |
| Один запрос на порцию | +10 | в пределах погрешности |
| Запрос на каждый товар | +990 | +12 % |

Замеры сделаны на каталоге из 1 000 товаров и 4 000 предложений, то есть на 10 порциях, с локальной PostgreSQL, где один запрос занимает около миллисекунды. В таблице приведены медианы трёх прогонов, а для запроса на каждый товар результат одного прогона. Повторный импорт почти ничего не записывает, поэтому стоимость обработчика в нём заметнее всего. С удалённой базой к каждому запросу добавляется сетевая задержка, и разница растёт.

Чтобы обработчик не замедлял обмен:

- **Делайте один запрос на порцию.** Соберите ключи всех элементов, выполните один `query.graph` с фильтром по массиву ключей и сложите ответ в `Map`.
- **Не раздувайте элемент.** Справочники, которые нужны только обработчику, держите в локальных переменных, а не в элементе.
- **Записывайте в базу из обработчика только вместе с компенсацией.** Передайте функцию отката вторым аргументом при регистрации хука, а данные для неё вторым аргументом `StepResponse`. Плагин фиксирует каждую порцию отдельно, и порция, завершившаяся ошибкой, откатывает только свои изменения.
- **Не завязывайте результат на порядок пачек.** После неудачи 1С повторяет обмен целиком, и порции могут прийти в другом составе.

Так выглядит запрос на каждый товар. На порцию из 100 товаров это 100 запросов:

```ts
for (const item of products) {
  const [brand] = readProperty(item.source, properties, "Бренд")
  const { data } = await query.graph({
    entity: "product_collection",
    fields: ["id"],
    filters: { title: brand },
  })
  // ...
}
```

Один запрос на порцию получает те же данные сразу для всех товаров:

```ts
const titles = products.flatMap(({ source }) => readProperty(source, properties, "Бренд"))
const { data } = await query.graph({
  entity: "product_collection",
  fields: ["id", "title"],
  filters: { title: titles },
})
const collectionIdByTitle = new Map(data.map((collection) => [collection.title, collection.id]))
```

Полный пример с таким запросом есть на странице [Примеры хуков](/medusa-integrations/1c-enterprise/hooks/examples#бренд-в-коллекцию).

<Note type="warning">

На тестовом каталоге из нескольких товаров запросы на каждый товар незаметны. Они проявляются на полном каталоге, когда обмен уже работает в продакшене.

</Note>

### Собственный замер

Запустите сервер с `LOG_LEVEL=debug`. Плагин запишет в журнал длительность каждого шага импорта каталога, и шаг хука называется так же, как сам хук:

```
[1C Integration] import: import-onec-products › setProducts 35 ms
```

`setVariants` и `setPriceLists` выполняются внутри дочерних воркфлоу импорта предложений, поэтому их время входит в общую строку `import-onec-offers finished in … ms`. Для выгрузок плагин не пишет в журнал время по шагам.
