# {frontmatter.title}

In this guide, you'll learn how to install the 1C:Enterprise plugin, register it in Medusa and set up the exchange in 1C.

<Note type="success" title="The plugin is available to beta participants">

The plugin is published to Gorgo's private package registry. To install it, [apply for the beta](https://gorgojs.com/beta/medusa-1c). Once your application is approved, you get a license key that gives you access to the registry.

</Note>

## Prerequisites

- Medusa v2.17.2 or later
- Node.js v22.23.4, v24.22.1, v26.12.1 or later
- [Integration Module](/medusa-modules/integration) v0.1.4 or later
- A Gorgo license key – [apply for the beta](https://gorgojs.com/beta/medusa-1c)
- A 1C configuration that supports site exchange over CommerceML

---

## Installation

`@gorgo-store` packages are published to the `registry.gorgojs.com` registry, not the public npm registry. Point your package manager at this registry for `@gorgo-store` packages and pass it your license key. Yarn 2 and later reads its settings from `.yarnrc.yml`, npm and pnpm from `.npmrc`:

<CodeTabs>
  <CodeTab label="yarn" value="yarn">
    ```yaml title=".yarnrc.yml"
    npmScopes:
      gorgo-store:
        npmRegistryServer: "https://registry.gorgojs.com"
        npmAuthToken: "${GORGO_LICENSE}"
    ```
  </CodeTab>
  <CodeTab label="pnpm" value="pnpm">
    ```text title=".npmrc"
    @gorgo-store:registry=https://registry.gorgojs.com/
    ```
  </CodeTab>
  <CodeTab label="npm" value="npm">
    ```text title=".npmrc"
    @gorgo-store:registry=https://registry.gorgojs.com/
    //registry.gorgojs.com/:_authToken=${GORGO_LICENSE}
    ```
  </CodeTab>
</CodeTabs>

For Yarn and npm, the license key comes from the `GORGO_LICENSE` environment variable, so the key itself stays out of your project's repository. Set this variable on your machine and in CI, wherever dependencies get installed.

Since version 11.5.3, pnpm doesn't expand environment variables in registry URLs and credentials from the project `.npmrc`. That's why the pnpm `.npmrc` holds only the registry URL, and you save the key in your user-level pnpm settings instead. Run this command on your machine and in CI before installing dependencies:

```bash
pnpm config set //registry.gorgojs.com/:_authToken "$GORGO_LICENSE"
```

The command writes the key to your user's pnpm settings rather than to the project, so it stays out of the repository as well.

Install the plugin together with the Integration Module:

<CodeTabs>
  <CodeTab label="yarn" value="yarn">
    ```bash
    yarn add @gorgo/medusa-integration @gorgo-store/medusa-erp-1c
    ```
  </CodeTab>
  <CodeTab label="pnpm" value="pnpm">
    ```bash
    pnpm add @gorgo/medusa-integration @gorgo-store/medusa-erp-1c
    ```
  </CodeTab>
  <CodeTab label="npm" value="npm">
    ```bash
    npm install @gorgo/medusa-integration @gorgo-store/medusa-erp-1c
    ```
  </CodeTab>
</CodeTabs>

## Configuration

Register the plugin and its integration provider in the `medusa-config.ts` file of your Medusa application:

```ts title="medusa-config.ts"
// ...

module.exports = defineConfig({
  // ...
  plugins: [
    // ...
    {
      resolve: "@gorgo/medusa-integration",
      options: {
        providers: [
          {
            resolve: "@gorgo-store/medusa-erp-1c/providers/integration-1c",
            options: {},
          },
        ],
      },
    },
    {
      resolve: "@gorgo-store/medusa-erp-1c",
      options: {},
    },
  ],
})
```

The configuration registers two things:

- The integration provider in `@gorgo/medusa-integration`. It brings the 1C settings into the Medusa Admin under **Settings → Integrations → 1C:Enterprise**.
- The plugin itself. It adds the exchange URL for 1C, the admin widgets and the exchange workflows.

<Note type="default" title="">

The plugin has no options in `medusa-config`. You set the sales channel, the region, the price types and everything else in the Medusa Admin, as described in [Manage 1C:Enterprise Settings in the Medusa Admin](/medusa-integrations/1c-enterprise/settings). The plugin has no secret fields either, so you don't need to set an `encryptionKey` on the Integration Module for it.

</Note>

## Set Up the Exchange in 1C

1C starts the exchange itself, so you set it up on the 1C side. In the site exchange settings of your 1C configuration, set:

- **Site address** – `https://<your Medusa backend URL>/hooks/erp/1c`
- **User** – the email of a Medusa Admin user
- **Password** – that user's password

The plugin checks the login and password the same way the Medusa Admin does on sign-in. Create a separate user for the exchange. That way 1C doesn't store an employee's password, and you can delete that user or change its password without affecting anyone else.

You don't need to configure compression or file chunk size. The plugin tells 1C itself that it accepts zip archives and file chunks of up to 1 MB. From the received files, it imports the catalog (`import*.xml`) first, then the offers (`offers*.xml`) and the orders (`orders*.xml`).

<Note type="warning">

The plugin keeps the exchange session in the memory of the Medusa process. If the server restarts in the middle of an exchange, the exchange is interrupted and you have to run it again. If your backend runs as several instances, route every request to `/hooks/erp/1c` to the same one. Otherwise a request that lands on another instance gets an authorization failure, even though the login and password are correct.

</Note>

<Note type="warning">

The exchange publishes every product it receives, including one you unpublished by hand. If part of the items in your 1C database is hidden from the site, for example with a "Удалить с сайта" property, register the handler from the [Draft for Products Hidden on the Site](/medusa-integrations/1c-enterprise/hooks/examples#draft-for-products-hidden-on-the-site) example before the first exchange. Otherwise the very first export puts those products on the storefront.

</Note>

## Record Matching

The plugin recognizes a Medusa record by its `Ид` from 1C, not by its name or article:

- **Product** – by the product `Ид` in the Medusa product's `metadata.onec.id`.
- **Variant** – by the product `Ид` and the characteristic `Ид` in the variant's `metadata.onec.id`. An offer for the whole product becomes a variant without a characteristic `Ид`.

So renaming a product or changing its article in 1C doesn't create duplicates in Medusa.

The plugin writes the offer's article to the variant's SKU as long as no other variant holds that SKU. In 1C an article doesn't have to be unique, while a SKU in Medusa does, so the plugin saves a variant whose article is taken without a SKU and logs it. The variant always keeps the article itself in `metadata.onec.article`, and that's what the plugin sends as `<Артикул>` in the catalog and order exports to 1C. To fill the SKU your own way, use the `setVariants` hook, as in the [SKU for a Taken Article](/medusa-integrations/1c-enterprise/hooks/examples#sku-for-a-taken-article) example.

The plugin builds a new product's handle from its name, transliterated, and part of its `Ид`. For an `Ид` that's a GUID, that's the first group, and any other `Ид` goes in whole. For example, a product named "Фильтр масляный" with the `Ид` `ed1cf3b2-b655-11f1-85e2-fa163e2913c2` gets the handle `filtr-maslyanyj-ed1cf3b2`, so products with the same name don't get the same handle. The plugin doesn't change an existing product's handle unless **Update the handle when a product is renamed in 1C** is on, see [Edit the Exchange Rules](/medusa-integrations/1c-enterprise/settings#edit-the-exchange-rules).

## Exchange Log

Exchange entries in the Medusa log start with `[1C Integration]`. After every catalog and offers batch, the plugin writes a progress line:

```
[1C Integration] import: progress catalog 40% (200/500 products, batch 2/5)
```

The plugin commits each batch separately, so the batches processed before an interruption stay in the database. Repeating the whole exchange is safe, because the plugin matches both products and variants by their 1C `Ид`, as described in [Record Matching](#record-matching).

When an offer's article is already the SKU of another variant, the plugin logs a warning:

```
[1C Integration] import: Offer d4f9a3f0-6e9b-11f0-8be5-fa163e2913c2#7a1f86c0-7355-11f0-8fc6-fa163e2913c2: article "123" is already the SKU of variant variant_01JB2K8R4M, the variant is saved without a SKU and keeps the article in metadata.
```

On the following exchanges, the plugin logs the same conflict at the `debug` level, so the log doesn't repeat the same warnings.

When the exchange fails, 1C receives a `failure` response with the reason, and the same reason goes to the log. To see the duration of every import step, enable the `debug` log level, for example with the `LOG_LEVEL=debug` environment variable.
