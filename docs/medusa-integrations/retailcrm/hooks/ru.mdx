# {frontmatter.title}

Обмен с RetailCRM работает как воркфлоу Medusa, и у каждого из них есть хук. Обработчик хука получает то, что плагин собирается отправить в CRM или применить в Medusa, и возвращает исправленную версию. Так вы задаёте способ оформления, оставляете часть заказов вне CRM, передаёте пользовательское поле или не даёте изменению из CRM дойти до Medusa, не меняя код плагина.

<Note type="info" title="Что такое хук воркфлоу">

Хук воркфлоу это точка внутри воркфлоу Medusa, куда вы подключаете собственную функцию. Medusa вызывает её во время выполнения воркфлоу, передаёт ей данные, а воркфлоу использует то, что функция вернула. Подробнее в [документации Medusa](https://docs.medusajs.com/learn/fundamentals/workflows/workflow-hooks).

</Note>

---

## Доступные хуки

| Воркфлоу | Хук | Когда выполняется | Что меняет |
| --- | --- | --- | --- |
| `exportRetailcrmOrdersWorkflow` | [`setOrders`](#setorders) | один раз на отправку, до запроса к CRM | тела заказов, которые уходят в CRM |
| `exportRetailcrmCustomersWorkflow` | [`setCustomers`](#setcustomers) | один раз на отправку, до запроса к CRM | тела покупателей, которые уходят в CRM |
| `exportRetailcrmPaymentsWorkflow` | [`setPayments`](#setpayments) | один раз на отправку, до запроса к CRM | тела платежей, которые уходят в CRM |
| `importRetailcrmHistoryWorkflow` | [`setOrders`](#setorders-при-импорте) | один раз на проход истории, после разбора записей | изменения, применяемые к заказам Medusa, и заказы, создаваемые из CRM |
| `importRetailcrmHistoryWorkflow` | [`setCustomers`](#setcustomers-при-импорте) | один раз на проход истории, после разбора записей | изменения, применяемые к покупателям Medusa |

Импортируйте воркфлоу из `@gorgo-store/medusa-crm-retailcrm/workflows`, а типы входа, элемента и результата хуков из `@gorgo-store/medusa-crm-retailcrm/hooks`.

---

## Регистрация обработчика

Зарегистрируйте обработчик в файле в папке `src/workflows/hooks` проекта Medusa, и Medusa загрузит его при старте сервера. Например, этот обработчик задаёт способ оформления, который CRM показывает у каждого заказа из магазина:

```ts title="src/workflows/hooks/retailcrm-orders.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { exportRetailcrmOrdersWorkflow } from "@gorgo-store/medusa-crm-retailcrm/workflows"

exportRetailcrmOrdersWorkflow.hooks.setOrders(async ({ orders }) => {
  return new StepResponse({
    orders: orders.map((item) => ({
      ...item,
      order: { ...item.order, orderMethod: "shopping-cart" },
    })),
  })
})
```

Обработчик получает запланированные элементы, возвращает их в `StepResponse`, и плагин отправляет то, что обработчик вернул. Поле `order` элемента это тело в формате самой CRM, поэтому здесь можно задать любое поле заказа CRM.

---

## Как устроен элемент

Каждый хук получает массив элементов. Элемент собирает всё, что нужно обработчику для решения:

- `source` – из чего собран элемент. При отправке это заказ, покупатель или платёж Medusa. При импорте это записи истории одного заказа или покупателя CRM.
- `existing` – только при импорте, заказ или покупатель Medusa, к которому относятся записи, или `null` для заказа или покупателя, заведённого в CRM.
- `crm` – только при импорте, заказ или покупатель CRM, прочитанный целиком, когда записи этого требовали.
- Целевое поле – что плагин отправляет или применяет. При отправке это `order`, `customer` или `payment`, при импорте `order` или `customer` с желаемыми изменениями.
- `action` – что плагин собирается сделать с элементом: `create`, `edit` или `skip` при отправке, `apply`, `create` или `skip` при импорте. У пропущенного элемента есть `skipReason`.

---

## Правила результата

- **Возвращайте `new StepResponse({ <массив> })`.** Плагин использует только массив.
- **Уберите элемент, чтобы в этом проходе запись осталась как есть.** Заказ, убранный из отправки, не получает отметку CRM и уходит со следующим запуском задачи повторной отправки. Изменение из CRM, убранное при импорте, не применяется, а курсор истории всё равно проходит дальше.
- **Поставьте `action: "skip"` с `skipReason` с тем же результатом**, но с причиной в журнале.
- **Не добавляйте элементы и не меняйте `externalId`.** CRM узнаёт заказ, покупателя и платёж по `externalId`, и плагин останавливает проход с ошибкой, называющей хук, если обработчик его изменил или вернул элемент, которого не было в плане.
- **Возвращайте один и тот же результат для одного и того же входа.** Плагин сравнивает тело с отправленным в прошлый раз, и обработчик, который меняет тело при каждом вызове, отправляет в CRM каждое повторное событие.

<Note type="default" title="">

Если обработчик вернул обычный объект или ничего, проход останавливается с ошибкой вида `exportRetailcrmOrdersWorkflow.hooks.setOrders handler must return new StepResponse({ orders }), it returned nothing usable`. Medusa передаёт плагину только то, что находится внутри `StepResponse`.

</Note>

## Примеры

### Заказы одного канала остаются вне CRM

Магазин продаёт на маркетплейсе через второй канал продаж, и у тех заказов своя CRM. Обработчик их пропускает. Заказ уже есть в каждом элементе, поэтому обработчик не делает запросов к базе.

```ts title="src/workflows/hooks/retailcrm-orders.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { exportRetailcrmOrdersWorkflow } from "@gorgo-store/medusa-crm-retailcrm/workflows"

const MARKETPLACE_CHANNEL = "sc_01J…"

exportRetailcrmOrdersWorkflow.hooks.setOrders(async ({ orders }) => {
  return new StepResponse({
    orders: orders.filter(({ source }) => source.sales_channel_id !== MARKETPLACE_CHANNEL),
  })
})
```

Убранный здесь заказ не получает отметку CRM, так что задача повторной отправки раз в час предлагает его обработчику снова, и обработчик снова его пропускает. Это дешевле, чем кажется: задача читает только заказы за последние сутки.

### Пользовательское поле из метаданных заказа

Витрина сохраняет пожелания покупателя к доставке в метаданных заказа, а в CRM для них есть пользовательское поле. Обработчик копирует значение.

```ts title="src/workflows/hooks/retailcrm-orders.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { exportRetailcrmOrdersWorkflow } from "@gorgo-store/medusa-crm-retailcrm/workflows"

exportRetailcrmOrdersWorkflow.hooks.setOrders(async ({ orders }) => {
  return new StepResponse({
    orders: orders.map((item) => {
      const wishes = item.source.metadata?.delivery_wishes
      if (typeof wishes !== "string") return item
      return { ...item, order: { ...item.order, customFields: { ...item.order.customFields, delivery_wishes: wishes } } }
    }),
  })
})
```

### Статус CRM, который не отменяет заказ

В CRM есть статус из группы `cancel`, которым менеджеры откладывают заказ, и магазин не хочет, чтобы он отменял заказ Medusa даже при включённом переключателе **Отменять заказы**. Обработчик убирает статус из изменений и оставляет остальное.

```ts title="src/workflows/hooks/retailcrm-history.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { importRetailcrmHistoryWorkflow } from "@gorgo-store/medusa-crm-retailcrm/workflows"

importRetailcrmHistoryWorkflow.hooks.setOrders(async ({ orders }) => {
  return new StepResponse({
    orders: orders.map((item) => {
      if (item.order?.status?.code !== "cancel-parked") return item
      const { status: _status, ...rest } = item.order
      return { ...item, order: rest }
    }),
  })
})
```

Статус всё равно попадает в `metadata.retailcrm.status`, потому что `fields` его сохраняет. Чтобы скрыть его и там, удалите `status` и `status_group` из `fields`.
