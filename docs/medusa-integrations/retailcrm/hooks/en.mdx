# {frontmatter.title}

The exchange with RetailCRM runs as Medusa workflows, and every one of them exposes a hook. A hook handler receives what the plugin is about to send to the CRM or apply in Medusa, and returns a corrected version. That's how you set an order method, keep some orders out of the CRM, pass a custom field, or stop a CRM change from reaching Medusa, without changing the plugin's code.

<Note type="info" title="What Is a Workflow Hook">

A workflow hook is a point inside a Medusa workflow where you plug in your own function. Medusa calls it while the workflow runs and passes it data, and the workflow uses whatever the function returns. Read more in the [Medusa documentation](https://docs.medusajs.com/learn/fundamentals/workflows/workflow-hooks).

</Note>

---

## Available Hooks

| Workflow | Hook | When It Runs | What It Changes |
| --- | --- | --- | --- |
| `exportRetailcrmOrdersWorkflow` | [`setOrders`](#setorders) | once per send, before the request to the CRM | the order bodies that go to the CRM |
| `exportRetailcrmCustomersWorkflow` | [`setCustomers`](#setcustomers) | once per send, before the request to the CRM | the customer bodies that go to the CRM |
| `exportRetailcrmPaymentsWorkflow` | [`setPayments`](#setpayments) | once per send, before the request to the CRM | the payment bodies that go to the CRM |
| `importRetailcrmHistoryWorkflow` | [`setOrders`](#setorders-on-import) | once per history run, after the records are planned | the changes applied to Medusa orders and the orders created from the CRM |
| `importRetailcrmHistoryWorkflow` | [`setCustomers`](#setcustomers-on-import) | once per history run, after the records are planned | the changes applied to Medusa customers |

Import the workflows from `@gorgo-store/medusa-crm-retailcrm/workflows` and the hook input, element and result types from `@gorgo-store/medusa-crm-retailcrm/hooks`.

---

## Register a Handler

Register the handler in a file under `src/workflows/hooks` in your Medusa project, and Medusa loads it when the server starts. For example, this handler sets the order method the CRM shows for every order from the store:

```ts title="src/workflows/hooks/retailcrm-orders.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { exportRetailcrmOrdersWorkflow } from "@gorgo-store/medusa-crm-retailcrm/workflows"

exportRetailcrmOrdersWorkflow.hooks.setOrders(async ({ orders }) => {
  return new StepResponse({
    orders: orders.map((item) => ({
      ...item,
      order: { ...item.order, orderMethod: "shopping-cart" },
    })),
  })
})
```

The handler receives the planned elements, returns them in a `StepResponse`, and the plugin sends what the handler returned. The element's `order` is the body in the CRM's own format, so any field of the CRM order can be set here.

---

## How an Element Is Built

Every hook receives an array of elements. An element brings together what the handler needs to decide:

- `source` – what the element is built from. On export, it's the Medusa order, customer or payment. On import, it's the history records of one CRM order or customer.
- `existing` – on import only, the Medusa order or customer the records belong to, or `null` for an order or customer created in the CRM.
- `crm` – on import only, the CRM order or customer read in full, when the records required it.
- The target field – what the plugin sends or applies. It's `order`, `customer` or `payment` on export, and `order` or `customer` with the desired changes on import.
- `action` – what the plugin is going to do with the element: `create`, `edit` or `skip` on export, `apply`, `create` or `skip` on import. A skipped element carries `skipReason`.

---

## Result Rules

- **Return `new StepResponse({ <array> })`.** The plugin uses only the array.
- **Remove an element to leave that record alone in this run.** An order removed from the export doesn't get the CRM mark and goes out with the next resend job. A CRM change removed on import isn't applied, and the history cursor still moves past it.
- **Set `action: "skip"` with a `skipReason` to the same effect**, with the reason in the log.
- **Don't add elements or change `externalId`.** The CRM recognizes an order, a customer and a payment by their `externalId`, and the plugin stops the run with an error naming the hook if a handler changes it or returns an element that wasn't planned.
- **Return the same result for the same input.** The plugin compares the body with the one it sent last time, and a handler that changes the body on every call sends every repeated event to the CRM.

<Note type="default" title="">

If a handler returns a plain object or nothing, the run stops with an error like `exportRetailcrmOrdersWorkflow.hooks.setOrders handler must return new StepResponse({ orders }), it returned nothing usable`. Medusa passes the plugin only what's inside the `StepResponse`.

</Note>

## Examples

### Orders of One Channel Stay Out of the CRM

The store sells on a marketplace through a second sales channel, and those orders have their own CRM. The handler skips them. Every element already carries the order, so the handler makes no database queries.

```ts title="src/workflows/hooks/retailcrm-orders.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { exportRetailcrmOrdersWorkflow } from "@gorgo-store/medusa-crm-retailcrm/workflows"

const MARKETPLACE_CHANNEL = "sc_01J…"

exportRetailcrmOrdersWorkflow.hooks.setOrders(async ({ orders }) => {
  return new StepResponse({
    orders: orders.filter(({ source }) => source.sales_channel_id !== MARKETPLACE_CHANNEL),
  })
})
```

An order removed here gets no CRM mark, so the resend job offers it to the handler again every hour, and the handler skips it again. That's cheaper than it sounds: the job reads the orders of the last day only.

### A Custom Field from the Order Metadata

The storefront saves the delivery wishes of the buyer in the order metadata, and the CRM has a custom field for them. The handler copies the value.

```ts title="src/workflows/hooks/retailcrm-orders.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { exportRetailcrmOrdersWorkflow } from "@gorgo-store/medusa-crm-retailcrm/workflows"

exportRetailcrmOrdersWorkflow.hooks.setOrders(async ({ orders }) => {
  return new StepResponse({
    orders: orders.map((item) => {
      const wishes = item.source.metadata?.delivery_wishes
      if (typeof wishes !== "string") return item
      return { ...item, order: { ...item.order, customFields: { ...item.order.customFields, delivery_wishes: wishes } } }
    }),
  })
})
```

### A CRM Status That Doesn't Cancel

The CRM has a status in the `cancel` group that managers use to park an order, and the store doesn't want it to cancel the Medusa order even with **Cancel orders** on. The handler drops the status from the changes and keeps the rest.

```ts title="src/workflows/hooks/retailcrm-history.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { importRetailcrmHistoryWorkflow } from "@gorgo-store/medusa-crm-retailcrm/workflows"

importRetailcrmHistoryWorkflow.hooks.setOrders(async ({ orders }) => {
  return new StepResponse({
    orders: orders.map((item) => {
      if (item.order?.status?.code !== "cancel-parked") return item
      const { status: _status, ...rest } = item.order
      return { ...item, order: rest }
    }),
  })
})
```

The status still lands in `metadata.retailcrm.status`, because `fields` keeps it. To hide it there as well, delete `status` and `status_group` from `fields`.
