# {frontmatter.title}

This page describes the exchange the plugin runs once the integration is connected and enabled. The settings it refers to are described in [Manage RetailCRM Settings](/medusa-integrations/retailcrm/settings), and every step of the exchange can be changed with the [workflow hooks](/medusa-integrations/retailcrm/hooks).

## From Medusa to the CRM

The plugin listens to Medusa events in subscribers and sends the entity to the CRM right away. The CRM knows a Medusa entity by its `externalId`, which is the Medusa ID: `order_…` for an order, `cus_…` for a customer and `pay_…` for a payment. The order number people see in the CRM is the Medusa display ID.

| Medusa event | What the plugin sends |
| --- | --- |
| `order.placed` | Creates the order in the CRM with the customer, items, delivery and payments, in the status mapped for a placed order. |
| `order.updated` | Edits the order with the full list of items and the current delivery and addresses. The status isn't sent, so a status the manager set in the CRM stays. |
| `order.canceled`, `order.completed` | Edits the order with the status mapped for a canceled or completed order. |
| `payment.captured` | Marks the CRM payment with the paid status and the capture time. |
| `payment.refunded` | Marks the CRM payment with the unpaid status on a full refund, and only adds a comment on a partial one. |
| `customer.created`, `customer.updated` | Creates or edits a customer with an account in every connected CRM store. |

An order goes only to the instance whose sales channel matches the order's. A customer goes to every instance.

### Customers

Before the order, the plugin makes sure its customer exists in the CRM. A customer with an account is looked up by `externalId` and created when the CRM doesn't have one. A guest is looked up by email, as the official WooCommerce module does. A guest the CRM already has gets the Medusa ID as its `externalId` through `customers/fix-external-ids`, and a guest the CRM doesn't have gets created. That's why a guest checkout appears in the CRM with a customer even though Medusa emits no `customer.created` event for guests.

### Items and prices

An item goes with the price before discounts in `initialPrice` and the discount per unit in `discountManualAmount`, so a discount never applies twice. The item references the CRM offer by the Medusa variant ID in `offer.externalId` and the SKU in `offer.xmlId`, and carries the Medusa line item ID in `externalIds` under the `medusa` code. An offer the CRM doesn't find is created as a free item with the name and price from Medusa.

### Payments

Every payment of the order goes with the order when it's created, and the CRM requires a payment type on each of them. The type comes from the payment type mapping, or from the payment type set as the API default in your account, if that type is open to the store of the instance. A payment with no type at all stays out and the plugin writes a warning to the log. After that, payments are edited by `externalId` on capture and refund, and a payment the CRM lost is created again. The plugin keeps the CRM IDs of the payments in the order's metadata, because a Medusa payment has no metadata of its own.

### Repeated events

The plugin remembers a hash of the body it last sent in the order's metadata. An `order.updated` event whose body hashes to the same value sends nothing, so a metadata write or a repeated event doesn't reach the CRM.

## From the CRM to Medusa

The CRM has no webhooks. It records every change in a history, and the plugin reads it with a scheduled job. The job runs every minute and reads the history of an instance as often as the **Poll interval (minutes)** setting says, with a cursor it keeps in its own table, so a restart continues where the previous run stopped. Changes made through the plugin's own API key are recognized by the CRM's `apiKey.current` flag and skipped. Every record is handled on its own, so a record the plugin can't read goes to the log and the run goes on.

| Changed in the CRM | What happens in Medusa |
| --- | --- |
| Order status | The code and its group land in `metadata.retailcrm.status` and `status_group`. A status of the `cancel` group cancels the order, and one of the `complete` group completes it, only when the matching switch in [Changes from CRM](/medusa-integrations/retailcrm/settings#edit-the-changes-from-crm) is on. |
| Items | The plugin reads the whole order from the CRM and compares it with the Medusa order. It adds the items that are new, changes quantities and prices, and sets the quantity of a removed item to zero, as one order edit that Medusa confirms, reserving stock and adjusting the amount due. |
| Delivery type and cost | In the same order edit, the plugin replaces the order's shipping method with a shipping option of the Medusa type mapped to the CRM delivery type, from the zone of the current option, with the cost from the CRM. A delivery type without a mapping, or without such an option in the zone, is only recorded in the metadata. |
| Delivery address | The order's shipping address gets the address from the CRM. |
| Customer of the order | The order gets the email of the CRM customer, and the Medusa customer when the CRM customer is linked to one. |
| Payment status | The status lands in the order's metadata. A status marked as payment complete captures the payment made through Medusa's system payment provider, when **Capture manual payments** is on. With the same switch on, a paid CRM payment without a Medusa counterpart marks the order's open payment collection as paid. |
| Manager, comments, order type, order method, custom fields | Recorded in `metadata.retailcrm` as `manager_id`, `manager_comment`, `customer_comment`, `order_type`, `order_method` and `custom_fields`. |
| Customer name and phone | Written to the Medusa customer. |
| Customer address | Written to the customer's default shipping address, or a new address is created. |
| Customer email | Never applied, because the email is the customer's login in Medusa. The CRM value is recorded in the metadata. |
| Order deleted in the CRM | Treated like the `cancel` group and recorded as `deleted_at` in the metadata. |

Item and delivery edits are applied while **Apply order edits** is on, and the delivery address is applied either way. The plugin cancels the Medusa order edit and writes an error to the log if Medusa rejects it, for example when a quantity goes below what's already fulfilled, and the rest of the record still applies. An order that has another order edit in progress waits for the next run.

Corporate customers, merged orders and customers, loyalty bonuses and the data of CRM delivery modules aren't applied. They're recorded in the metadata and passed to the hooks.

### Orders Created in the CRM

An order a manager creates in the CRM has no `externalId`. When **Create new orders** is on and the **Order methods** card lists the order's method or reads **All methods**, the plugin creates the order in Medusa through `createOrderWorkflow`, with the region that matches the CRM store's currency, the sales channel of the instance, the items matched to variants by ID or SKU, the delivery as a shipping option of the mapped type in the zone that covers the address country, and the customer by email. Right after that, it calls `orders/fix-external-ids`, so the CRM order gets the Medusa order ID and the next change comes back as an edit of this order. An order without an email, without items, or with an item without a price isn't created, and the reason goes to the log. The same happens to a customer created in the CRM with an email.

### What the Plugin Keeps in the Metadata

Everything the plugin knows about an order in the CRM is in `order.metadata.retailcrm`:

| Key | Meaning |
| --- | --- |
| `id`, `site`, `number` | The CRM order ID, the store code and the order number in the CRM. |
| `sent_hash`, `sent_at` | The hash and time of the last body sent to the CRM. |
| `status`, `status_group` | The current CRM status and its group. |
| `payments` | The CRM payments by Medusa payment ID, with the CRM ID, type, status and amount. |
| `manager_id`, `manager_comment`, `customer_comment`, `order_type`, `order_method`, `custom_fields`, `delivery_code`, `delivery_cost` | The CRM fields that have no Medusa counterpart. |
| `last_history_id` | The last history record applied to this order. |
| `imported_at`, `external_id_fixed` | Set on an order created from the CRM. |
| `extra` | History fields the plugin doesn't understand, as they came. |

A customer has `customer.metadata.retailcrm` with `id`, `site`, `sent_hash`, `sent_at`, `external_id_fixed` and the CRM fields that have no Medusa counterpart: `patronymic`, `birthday`, `sex`, `tags`, `manager_id`, `vip`, `bad`, `subscribed`, `source` and `custom_fields`.

## When the CRM Is Unavailable

A subscriber that fails to send an order writes an error to the log and doesn't retry, because Medusa delivers an event once. Instead, a scheduled job runs every hour and sends again the orders of the last day that have no CRM ID in their metadata, and the customers with an account that have none. The plugin's client retries a request up to three times with a growing delay when the CRM answers `Service overloaded.`, that's the CRM's rate limit, or when the network fails, and keeps its own limit of eight requests per second per instance.
