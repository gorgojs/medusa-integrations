# {frontmatter.title}

Справочник описывает, когда вызывается каждый хук, что получает и может вернуть его обработчик и что плагин делает с результатом. Правила, общие для всех хуков, описаны на странице [Хуки воркфлоу](/medusa-integrations/1c-pro/hooks).

---

## setProducts

Хук воркфлоу `importOnecProductsWorkflow` (`import-onec-products`). Вызывается на каждую пачку каталога, до 100 товаров, до сравнения с товарами Medusa. Каталог в 10 000 товаров вызовет его 100 раз.

```ts title="src/workflows/hooks/onec-catalog.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { importOnecProductsWorkflow } from "@gorgo-pro/medusa-erp-1c/workflows"

importOnecProductsWorkflow.hooks.setProducts(async ({ products, properties }, { container }) => {
  // ...

  return new StepResponse({ products })
})
```

В `product` обмен записывает `title`, `description`, `handle`, `external_id`, `type_id`, `status`, `metadata`, `category_ids` и `sales_channels`, а `thumbnail` и `images` только когда 1С прислала картинки. Поля `subtitle`, `weight`, `length`, `height`, `width`, `origin_country`, `hs_code`, `mid_code`, `material`, `collection_id` и `discountable` обмен не заполняет. Их может задать обработчик, и импорт запишет их так же, как остальные.

Верните `new StepResponse({ products })`. Обработчик может поправить `product` и убрать товар из пачки. Чего он сделать не может:

- вернуть товар, которого не было в пачке, или один товар дважды;
- поменять `existing`;
- удалить или поменять `external_id` и `metadata.onec.id` у нового товара, потому что без них следующий обмен заведёт товар заново;
- поменять `external_id` и `metadata.onec.id` у существующего товара. Удалить эти ключи можно, тогда поля останутся как есть.

После хука плагин сравнивает `product` с `existing` и пишет только поля, которые отличаются. Товар без `existing` он создаёт. Убранный из пачки товар в этом обмене не создаётся и не обновляется.

## setPriceLists

Хук воркфлоу `importOnecPricesWorkflow` (`import-onec-prices`). Воркфлоу запускается внутри импорта предложений, поэтому хук вызывается на каждую пачку предложений, до 100 товаров со всеми их предложениями, до сверки с Medusa.

```ts title="src/workflows/hooks/onec-prices.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { importOnecPricesWorkflow } from "@gorgo-pro/medusa-erp-1c/workflows"

importOnecPricesWorkflow.hooks.setPriceLists(async ({ priceLists }, { container }) => {
  // ...

  return new StepResponse({ priceLists })
})
```

Обработчик получает по элементу на каждый нерозничный тип цен из `offers.xml`. Розничный тип плагин пишет в цену варианта, и в хук он не попадает:

Верните `new StepResponse({ priceLists })`. Ключ, который обработчик добавит в `priceList`, например `rules` или `status`, импорт запишет, если он отличается от записанного. Ограничения такие:

- нельзя вернуть тип цен, которого не было в пачке, или один тип дважды;
- нельзя поменять `existing`;
- цена должна относиться к варианту из этой пачки, `amount` должен быть числом, и двух цен в одной валюте у варианта быть не может.

После хука плагин создаёт прайс-листы новых типов цен и помечает их `metadata.onec.price_type_id`. У существующих он пишет изменившиеся ключи `priceList` и сверяет цены по варианту и валюте, добавляя новые, обновляя изменившиеся и удаляя лишние. Убранный из списка тип цен в этой пачке не трогается вовсе, ни прайс-лист, ни его цены.

## setOrders

Хук воркфлоу `exportOnecOrdersWorkflow` (`export-onec-orders`). Вызывается один раз на выгрузку заказов в 1С, до сборки XML. В выгрузку попадают неотменённые заказы, которые ещё не выгружались и не пришли из 1С.

```ts title="src/workflows/hooks/onec-orders.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { exportOnecOrdersWorkflow } from "@gorgo-pro/medusa-erp-1c/workflows"

exportOnecOrdersWorkflow.hooks.setOrders(async ({ orders }, { container }) => {
  // ...

  return new StepResponse({ orders })
})
```

## setPayload

Хук есть у двух воркфлоу, `exportOnecCatalogWorkflow` (`export-onec-catalog`) и `exportOnecOrdersWorkflow` (`export-onec-orders`). Вызывается один раз на выгрузку, когда XML уже собран. У выгрузки заказов он идёт после `setOrders`. Это резервный способ для того, чего нет в модели товара или документа, например для версии схемы, которую ждёт ваша конфигурация 1С.

```ts title="src/workflows/hooks/onec-payload.ts"
import { StepResponse } from "@medusajs/framework/workflows-sdk"
import { exportOnecCatalogWorkflow, exportOnecOrdersWorkflow } from "@gorgo-pro/medusa-erp-1c/workflows"

exportOnecCatalogWorkflow.hooks.setPayload(async ({ payload }) => {
  // ...

  return new StepResponse({ payload })
})

exportOnecOrdersWorkflow.hooks.setPayload(async ({ payload }) => {
  // ...

  return new StepResponse({ payload })
})
```

Это два разных хука, и каждый регистрируется у своего воркфлоу. Обработчик получает XML строкой:

## Функции чтения 1С

`@gorgo-pro/medusa-erp-1c/hooks` экспортирует две функции, которые читают значения товара 1С так, как их раскладывает CommerceML.

### readRequisite

```ts
readRequisite(source, name): string | undefined
```

Первое значение реквизита из `ЗначенияРеквизитов` по его `Наименованию`. Имя сравнивается точно, с пробелами и регистром. У 1С это свободный текст, и `Полное наименование` с `ПолноеНаименование` разные реквизиты. Если реквизита нет, функция вернёт `undefined`.

### readProperty

```ts
readProperty(source, properties, nameOrId): string[]
```

Значения свойства из `ЗначенияСвойств`. Свойство ищется по `Ид` или по имени, а значения-справочники разворачиваются через `properties` из входных данных хука. По имени собираются все одноимённые свойства, потому что 1С может завести своё свойство «Бренд» под каждую категорию. Если значения нет, функция вернёт пустой массив.
