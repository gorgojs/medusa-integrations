# {frontmatter.title}

In this guide, you'll learn how to install [Medusa DTC Starter by Gorgo](https://github.com/gorgojs/medusa-dtc-starter), configure both apps, and connect your first integration.

## Requirements

- Node.js v20 or later
- PostgreSQL v15 or later
- npm, yarn, or pnpm

---

## Installation

Install the starter one of two ways: scaffold a new project with Medusa's own CLI, or clone the repository and configure each app by hand.

### Approach 1: Install with Medusa Application

<CodeTabs>
  <CodeTab label="yarn" value="yarn">
    ```bash
    yarn dlx create-medusa-app@latest --repo-url https://github.com/gorgojs/medusa-dtc-starter
    ```
  </CodeTab>
  <CodeTab label="pnpm" value="pnpm">
    ```bash
    pnpm dlx create-medusa-app@latest --repo-url https://github.com/gorgojs/medusa-dtc-starter
    ```
  </CodeTab>
  <CodeTab label="npm" value="npm">
    ```bash
    npx create-medusa-app@latest --repo-url https://github.com/gorgojs/medusa-dtc-starter
    ```
  </CodeTab>
</CodeTabs>

`--repo-url` tells `create-medusa-app` to scaffold from the specified repository instead of the official Medusa starter, but the usual prompts for a project name and a database stay the same. By default, the command also runs migrations, creates an admin user, and seeds the database. Pass `--no-migrations` to skip all three.

### Approach 2: Install Separately

1. Clone the repository and install dependencies:

   <CodeTabs>
     <CodeTab label="yarn" value="yarn">
       ```bash
       git clone https://github.com/gorgojs/medusa-dtc-starter.git
       cd medusa-dtc-starter
       yarn install
       ```
     </CodeTab>
     <CodeTab label="pnpm" value="pnpm">
       ```bash
       git clone https://github.com/gorgojs/medusa-dtc-starter.git
       cd medusa-dtc-starter
       pnpm install
       ```
     </CodeTab>
     <CodeTab label="npm" value="npm">
       ```bash
       git clone https://github.com/gorgojs/medusa-dtc-starter.git
       cd medusa-dtc-starter
       npm install
       ```
     </CodeTab>
   </CodeTabs>

2. Create the backend's environment file and point `DATABASE_URL` at a real database:

   ```bash title="Terminal"
   cp apps/backend/.env.template apps/backend/.env
   ```

   ```bash title="apps/backend/.env"
   DATABASE_URL=postgres://postgres:@localhost:5432/medusa-dtc-starter
   ```

3. Run the migrations, seed the initial data, and start the backend:

   <CodeTabs>
     <CodeTab label="yarn" value="yarn">
       ```bash
       cd apps/backend
       yarn medusa db:migrate
       yarn seed
       yarn dev
       ```
     </CodeTab>
     <CodeTab label="pnpm" value="pnpm">
       ```bash
       cd apps/backend
       pnpm medusa db:migrate
       pnpm seed
       pnpm dev
       ```
     </CodeTab>
     <CodeTab label="npm" value="npm">
       ```bash
       cd apps/backend
       npx medusa db:migrate
       npm run seed
       npm run dev
       ```
     </CodeTab>
   </CodeTabs>

4. Open the Admin dashboard at `http://localhost:9000/app`, sign in with `admin@medusajs.com` and `supersecret`, and copy the publishable API key from **Settings → Publishable API Keys**.

   The seed creates that account. Change both values in `apps/backend/src/migration-scripts/data/store/json/store.json` before you seed a database anyone else can reach.

5. Create the storefront's environment file with that key:

   ```bash title="Terminal"
   cp apps/storefront/.env.template apps/storefront/.env.local
   ```

   ```bash title="apps/storefront/.env.local"
   NEXT_PUBLIC_MEDUSA_PUBLISHABLE_KEY=pk_6c3...
   ```

6. Start the storefront:

   <CodeTabs>
     <CodeTab label="yarn" value="yarn">
       ```bash
       cd apps/storefront
       yarn dev
       ```
     </CodeTab>
     <CodeTab label="pnpm" value="pnpm">
       ```bash
       cd apps/storefront
       pnpm dev
       ```
     </CodeTab>
     <CodeTab label="npm" value="npm">
       ```bash
       cd apps/storefront
       npm run dev
       ```
     </CodeTab>
   </CodeTabs>

The storefront runs at `http://localhost:8000`. The repository root is set up for pnpm, so `pnpm dev` there starts both apps at once. With npm or yarn, start each app from its own directory.

## Configuration

### Backend

Before the backend can run, set a real value for `DATABASE_URL` and `INTEGRATION_ENCRYPTION_KEY`:

```bash title="apps/backend/.env"
DATABASE_URL=postgres://postgres:@localhost:5432/medusa-dtc-starter
INTEGRATION_ENCRYPTION_KEY=supersecret
```

Everything else in `apps/backend/.env.template` ships with a working localhost default, apart from the SMTP block, which points at a placeholder host until you fill it in. What the rest of them do:

| Variable | What it does |
|---|---|
| `DATABASE_URL` | Connection string for PostgreSQL. `DB_NAME` holds the database name it interpolates |
| `INTEGRATION_ENCRYPTION_KEY` | Encrypts the secret fields the Integration Module stores |
| `JWT_SECRET`, `COOKIE_SECRET` | Signing secrets for tokens and cookies |
| `COOKIE_SECURE` | Set it to `true` on a live domain to send cookies over HTTPS only |
| `STORE_CORS`, `ADMIN_CORS`, `AUTH_CORS` | Origins allowed to call the Store API, Admin, and authentication. Add your own domain here when you move either app off localhost |
| `REDIS_URL` | Redis instance for the cache, event bus, and workflow engine. Production uses it whenever it is set. `CACHE_REDIS_URL` points the cache alone at a separate instance |
| `USE_REDIS` | Set it to `true` to use `REDIS_URL` in development too. Without it all three run in memory, which is enough for development |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS` | Mail server the transactional emails go through. Nothing is sent until you fill these in |
| `SMTP_FROM`, `SMTP_REPLY_TO` | Sender and reply-to addresses on those emails |
| `STORE_NAME`, `STORE_EMAIL`, `STORE_PHONE`, `STORE_ADDRESS` | Store details printed in the email templates |
| `STOREFRONT_DEFAULT_LOCALE` | Language an email falls back to when the buyer's own is unknown |
| `STOREFRONT_URL` | Storefront address, used for the links inside emails and for revalidation webhooks |
| `REVALIDATE_SECRET` | Shared secret the backend sends with every revalidation webhook. It has to match the storefront's value |
| `S3_BUCKET`, `S3_ENDPOINT`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_REGION` | Move file uploads to S3-compatible storage. Read in production only |
| `MEDUSA_ADMIN_ONBOARDING_NEXTJS_DIRECTORY` | Storefront directory that Medusa's onboarding flow points at |

Replace every `supersecret` value before going to production.

### Storefront

For the storefront, you need at least the publishable API key from your Medusa backend:

```bash title="apps/storefront/.env.local"
NEXT_PUBLIC_MEDUSA_PUBLISHABLE_KEY=pk_6c3...
```

The rest already ship with working localhost defaults:

| Variable | What it does |
|---|---|
| `NEXT_PUBLIC_MEDUSA_PUBLISHABLE_KEY` | Publishable API key from Medusa Admin. Required |
| `NEXT_PUBLIC_MEDUSA_BACKEND_URL` | Address the storefront calls the backend at |
| `NEXT_PUBLIC_BASE_URL` | The storefront's own address, used for absolute URLs in metadata, the sitemap, and `llms.txt` |
| `NEXT_PUBLIC_SITE_NAME` | Store name shown in the header, footer, and checkout, and used in the `schema.org` markup and the `llms.txt` endpoint |
| `NEXT_PUBLIC_DEFAULT_REGION` | Country code the storefront falls back to when it cannot tell where a visitor is. The template's `en` matches no seeded region, and then the first region the backend returns wins |
| `GEOLOCATION_PROVIDER`, `GEOLOCATION_PROVIDER_API_KEY` | How a first-time visitor's country is detected. On Vercel or Cloudflare you can leave the provider unset, see the [Set Up Country Detection](/tools/medusa-dtc-starter/setup-country-detection) documentation |
| `GEOLOCATION_DEBUG` | Set it to `true` and every response explains which country the middleware picked and why |
| `NEXT_PUBLIC_ADDRESS_AUTOCOMPLETE_PROVIDER`, `NEXT_PUBLIC_ADDRESS_AUTOCOMPLETE_PROVIDER_API_KEY` | Address suggestions during checkout, see the [Set Up Address Autocomplete](/tools/medusa-dtc-starter/setup-address-autocomplete) documentation |
| `NEXT_PUBLIC_STRIPE_KEY` | Stripe publishable key, needed only if you take payments through Stripe |
| `NEXT_PUBLIC_MEDUSA_PAYMENTS_PUBLISHABLE_KEY`, `NEXT_PUBLIC_MEDUSA_PAYMENTS_ACCOUNT_ID` | Key and connected account for Medusa Cloud Payments. The key is used when `NEXT_PUBLIC_STRIPE_KEY` is empty |
| `NEXT_PUBLIC_GA_MEASUREMENT_ID` | Google Analytics 4 measurement ID. Leave it empty and the storefront loads no analytics script at all |
| `REVALIDATE_SECRET` | Has to match the same variable in `apps/backend/.env`, because the backend sends that value with every revalidation webhook. Change it before production |
| `MEDUSA_CLOUD_S3_HOSTNAME`, `MEDUSA_CLOUD_S3_PATHNAME` | Allow images from the Medusa Cloud bucket. Needed only when you deploy there |
| `NODE_ENV` | Node environment |

## Add Integrations

The Integration Module ([`@gorgo/medusa-integration`](/medusa-modules/integration)) is already registered in `medusa-config.ts` with an empty `providers` array, so there's nothing to wire up before you can add one. Once the backend is running, add a payment, fulfillment, or ERP integration and configure it from Medusa Admin, see the [Browse and Add an Integration](/medusa-modules/integration/manage-integrations#browse-and-add-an-integration) documentation.

## Troubleshooting

### Storefront Can't Reach the Backend, or Shows a Region Error

The storefront's logs show:

```text title="Storefront logs"
Error fetching regions. Did you set up regions in your Medusa Admin and define a NEXT_PUBLIC_MEDUSA_BACKEND_URL environment variable.
```

The cause is one of two things: either `NEXT_PUBLIC_MEDUSA_BACKEND_URL` isn't set or points to the wrong place, or the backend has no region configured yet. Check that the backend is running and reachable at that URL. If there really are no regions, the seed script creates several, see the [Customize Seed Data](/tools/medusa-dtc-starter/customize-seed-data) documentation.

### Stripe Checkout Doesn't Load

The storefront's logs show one of two errors:

```text title="Storefront logs"
Stripe key is missing. Set NEXT_PUBLIC_STRIPE_KEY environment variable.
```

The first one means the storefront tried to render Stripe Elements without a Stripe publishable key set.

```text title="Storefront logs"
Stripe client secret is missing. Cannot initialize Stripe.
```

The second one means no Stripe payment session exists on the cart yet, usually because the selected region has no Stripe provider configured.

### The Storefront Opens in the Wrong Country

A first-time visitor lands in a region that has nothing to do with their location, usually the same one every time.

Set `GEOLOCATION_DEBUG=true` in `apps/storefront/.env.local`, reload, and read the `x-geo-*` headers on the document request in the browser's network panel. `x-geo-source` names what answered: `cookie` means the `_medusa_country` cookie was never cleared, so clear it or open a new private window; `fallback-first` means nothing resolved and `NEXT_PUBLIC_DEFAULT_REGION` matched no seeded region either, so set it to a real country code; `x-geo-provider: platform` means `GEOLOCATION_PROVIDER` never reached the server. See the [Set Up Country Detection](/tools/medusa-dtc-starter/setup-country-detection) documentation for what each header means.

---

### Address Autocomplete Doesn't Work

If the address field doesn't suggest anything as you type during checkout, the DaData key is probably missing. Create an account on [DaData](https://dadata.ru/?ref=276331), set your key in `NEXT_PUBLIC_ADDRESS_AUTOCOMPLETE_PROVIDER_API_KEY`, and leave `NEXT_PUBLIC_ADDRESS_AUTOCOMPLETE_PROVIDER` set to `dadata`. See the [Set Up Address Autocomplete](/tools/medusa-dtc-starter/setup-address-autocomplete) documentation for configuring autocomplete and connecting a different provider.

### CORS Errors in the Browser Console

`STORE_CORS`, `ADMIN_CORS`, and `AUTH_CORS` in the backend's `.env` are allow-lists. If you move the storefront or Admin to a different port or domain, add that origin to the matching variable and restart the backend.
