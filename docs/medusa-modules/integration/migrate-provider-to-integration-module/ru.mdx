# {frontmatter.title}

В этом руководстве вы узнаете, как мигрировать существующий провайдер Medusa на управление своими настройками через [Модуль интеграций](/medusa-modules/integration).

<Note type="info" title="Что такое Модуль интеграций?">

Модуль интеграций позволяет любому плагину описывать свои параметры в виде схемы, а администраторам магазина настраивать их в Admin, без правок `medusa-config` и без повторного развёртывания приложения Medusa. Он генерирует UI, предоставляет CRUD API и валидацию, поэтому вам не нужно писать свои модели данных, роуты, формы или воркфлоу.

</Note>

---

## Зачем мигрировать

Когда параметры провайдера заданы в `medusa-config.ts`, сменить токен, пароль или любую другую настройку - значит поправить код, обновить переменные окружения и заново развернуть Medusa. Модуль интеграций избавляет от этой рутины. Он строит UI для управления настройками провайдера по простому декларативному описанию их схемы, и администратор магазина управляет ими в Admin, без правок `medusa-config.ts` и без повторного развёртывания.

Если вы уже написали UI для своего провайдера, то миграция на Модуль интеграций позволит вам:

- Избавиться от лишнего кода. Вам не нужно поддерживать модели данных, роуты, UI-формы, валидацию и воркфлоу.
- Получить UI по стандартам Medusa, чтобы ваш провайдер выглядел и работал как нативная интеграция.
- Хранить секреты зашифрованными, а не в открытом виде.
- Проверять соединение с внешним сервисом прямо из Admin.
- Подключать несколько инстансов провайдера, каждый со своими настройками.

---

## Пример миграции

В этом руководстве примеры кода взяты из реальной миграции нашего [провайдера модуля фулфилмента ApiShip](https://www.npmjs.com/package/@gorgo/medusa-fulfillment-apiship).

До миграции настройки ApiShip хранились в `store.metadata.apiship`: токен, подключения к курьерским службам, адрес отправителя по умолчанию, габариты товара и налоговые настройки. Эти данные обслуживал собственный Admin UI, и на каждую CRUD-операцию был отдельный API-роут. Модуль интеграций сводит всё это в один раздел **Настройки → Интеграции**.

Список параметров провайдера плоский, и каждый параметр отображается одним элементом в генерируемой UI-форме. Отсюда простое правило разделения: скалярные настройки становятся параметрами дескриптора, а в кастомный UI переносится только то, для чего в каталоге нет подходящего элемента, например, для параметров с типом `json`. У нашего провайдера ApiShip это ровно одна вещь: список подключений к курьерским службам, потому что это массив объектов JSON.

## Шаг 1: Опишите дескриптор

Рядом с существующим провайдером доставки создайте новый провайдер Модуля интеграций в файле `providers/integration-apiship/services/apiship-integration.ts` и опишите в нём дескриптор. Это тот же список настроек, что и раньше, но каждое поле теперь объявлено явно: тип, обязательность, значение по умолчанию и способ отображения в UI-форме.

```text title="Structure"
src/providers/
├── integration-apiship/          # новый: дескриптор настроек для Модуля интеграций
└── fulfillment-apiship/          # существующий: провайдер модуля фулфилмента, который читает настройки через Модуль интеграций
```

```ts title="providers/integration-apiship/services/apiship-integration.ts"
import { AbstractIntegrationProvider, defineIntegration, z } from "@gorgo/medusa-integration"
import { ProviderKeys } from "../../../types"
import { APISHIP_ICON } from "../icon"

const descriptor = defineIntegration({
  category: "fulfillment",
  displayName: "apiship.name",
  description: "apiship.description",
  icon: APISHIP_ICON,
  preferredLayoutId: "core:two-column",
  supportsMultipleInstances: true,

  options: {
    token: {
      type: "string",
      required: true,
      secret: true,
      control: "secret",
      label: "apiship.fields.token"
    },
    is_test: {
      type: "boolean",
      default: false,
      control: "switch",
      label: "apiship.fields.isTest"
    },
    is_cod: {
      type: "boolean",
      default: false,
      control: "switch",
      label: "apiship.fields.isCod"
    },
    delivery_cost_vat: {
      type: "enum",
      // Значения enum строковые; числовая ставка НДС для ApiShip приводится при чтении.
      values: ["-1", "0", "5", "10", "20" /* ... */],
      default: "-1",
      control: "select",
      label: "apiship.fields.deliveryCostVat",
      // Уходит в ApiShip только вместе с наложенным платежом, иначе поле скрыто.
      visibleWhen: {
        field: "is_cod",
        equals: true
      },
      valueLabels: {
        "-1": "apiship.vat.noVat",
        "0": "apiship.vat.vat0",
        "5": "apiship.vat.vat5",
        "10": "apiship.vat.vat10",
        "20": "apiship.vat.vat20"
        /* ... */
      },
    },
    default_product_length: {
      type: "number",
      default: 10,
      positive: true,
      control: "number",
      label: "apiship.fields.defaultProductLength"
    },
    // ...width, height, weight
    sender_country_code: {
      type: "enum",
      values: ["RU", "KZ" /* ... */],
      control: "select",
      label: "apiship.fields.senderCountryCode"
    },
    // ...sender_address_string, sender_contact_name, sender_phone
    // Подключения к курьерским службам образуют список записей, а контрола для этого
    // в каталоге нет, поэтому у них остаётся свой Admin UI (см. шаг 4). Но они всё равно
    // часть схемы: шифруются и валидируются наравне с остальными полями.
    settings: {
      type: "json",
      default: {
        connections: []
      },
      control: "json",
      label: "apiship.fields.settings"
    },
  },

  sections: [
    {
      id: "credentials",
      title: "apiship.sections.credentials",
      options: ["token", "is_test"]
    },
    {
      id: "payment_and_tax",
      title: "apiship.sections.paymentAndTax",
      column: "side",
      options: ["is_cod", "delivery_cost_vat"]
    },
    {
      id: "default_product_sizes",
      title: "apiship.sections.defaultProductSizes",
      column: "side",
      options: ["default_product_length" /* ...width, height, weight */]
    },
    {
      id: "sender",
      title: "apiship.sections.sender",
      options: ["sender_country_code" /* ...адрес, ФИО, телефон */]
    },
  ],

  testConnection: async ({ options }) => {
    // Лёгкий read-only вызов к API ApiShip, подтверждающий валидность токена.
    // Возвращает { status, message }, исключений не бросает.
  },
})

export type ApishipIntegrationOptions = z.infer<typeof descriptor.optionsSchema>

export class ApishipIntegrationProvider extends AbstractIntegrationProvider {
  static identifier = ProviderKeys.APISHIP

  get descriptor() {
    return descriptor
  }
}

export default ApishipIntegrationProvider
```

<Note type="default" title="">

`secret: true` у параметра `token` зашифрует это поле перед сохранением. Держите значения по умолчанию в одной общей константе и ссылайтесь на неё из `default`. Резолвер применит их во время выполнения, форма редактирования подставит в поля, а карточка покажет как текущее значение, так что все три останутся согласованными.

</Note>

<Note type="warning">

Параметры без `default` не попадают в итоговую конфигурацию. Это то, что нужно, когда «пусто» является реальным состоянием поля. Адрес отправителя ApiShip, например, не нужен для расчёта цены, только для создания заказа, поэтому его проверяет провайдер в момент создания заказа, а не `required` в дескрипторе. Если помечать такое поле `required`, любая конфигурация, где оно не заполнено, станет *неполной*, а неполную интеграцию резолвер считает ненастроенной, то есть провайдер модуля фулфилмента перестанет работать и выдаст ошибку во время выполнения.

</Note>

## Шаг 2: Подключите провайдер в `medusa-config.ts`

```ts title="medusa-config.ts"
// ...

const APISHIP_INTEGRATION_ID = "apiship-1"

module.exports = defineConfig({
  // ...
  plugins: [
    {
      resolve: "@gorgo/medusa-integration",
      options: {
        encryptionKey: process.env.INTEGRATION_ENCRYPTION_KEY,
        providers: [
          {
            resolve: "@gorgo/medusa-fulfillment-apiship/providers/integration-apiship",
            id: APISHIP_INTEGRATION_ID,
            options: {},
          },
        ],
      },
    },
    // ...
  ],
  modules: [
    {
      resolve: "@medusajs/medusa/fulfillment",
      options: {
        providers: [
          {
            resolve: "@gorgo/medusa-fulfillment-apiship/providers/fulfillment-apiship",
            id: "apiship",
            options: {
              id: APISHIP_INTEGRATION_ID
            },
          },
        ],
      },
    },
    // ...
  ],
})
```

<Note type="warning">

У провайдера Модуля интеграций задаётся параметр `id` из которого собирается итоговый идентификатор инстанса вида `int_<identifier>_<id>`. Такой же `id` нужно передать провайдеру модуля фулфилмента, чтобы он знал, какие настройки читать. Если провайдер интеграций поддерживает несколько инстансов, то у каждого будет свой `id`, которые можно передать разным провайдерам модуля фулфилмента.

</Note>

Далее, добавьте секретный ключ шифрования в переменные окружения. Он нужен модулю интеграций, чтобы зашифровать секреты перед сохранением в базу данных:

```text title=".env"
INTEGRATION_ENCRYPTION_KEY=supersecret
```

## Шаг 3: Переключите на чтение опций через `resolveIntegrationOptions`

Раньше провайдер модуля фулфилмента читал параметры из `store.metadata.apiship`. Теперь он получает их из модуля интеграций через `resolveIntegrationOptions()`, передавая свой `identifier` и `id` инстанса (тот самый `id` из `medusa-config.ts`). Модуль возвращает значения параметров уже расшифрованными, провалидированными и с применёнными значениями по умолчанию:

```ts title="providers/fulfillment-apiship/core/apiship-base.ts"
// ...
import { resolveIntegrationOptions } from "@gorgo/medusa-integration"
import { ProviderKeys } from "../../../types"
import { ApishipOptions } from "../../integration-apiship/services/apiship-integration"


class ApishipBase extends AbstractFulfillmentProviderService {
  protected instanceId_: string | null

  constructor({ logger }, options?: Record<string, unknown>) {
    super()
    this.logger_ = logger
    this.instanceId_ = (options?.id as string | undefined) ?? null
  }

  private async getApishipOptions_(): Promise<ApishipOptions> {
    const options = await resolveIntegrationOptions<ApishipOptions>({
      identifier: ProviderKeys.APISHIP,
      instance_id: this.instanceId_,
    })
    return options
  }

  // ... 
}
```

## Шаг 4: Перенесите кастомный Admin UI

Раньше у ApiShip была своя страница настроек в Admin. Теперь эту страницу интеграции формирует Модуль интеграции по дескриптору: доступы, оплата и НДС, габариты товара и отправитель генерируются как секции.

Единственная секция настроек, которая остаётся кастомной - это список подключений к курьерским службам. Она встраивается в ту же страницу виджетом через зону расширения `gorgo.integration.apiship.main.after`. Виджет получает ключ инстанса от Модуля интеграций через `data.providerId` и передаёт его во все свои хуки и запросы:

```tsx title="admin/widgets/apiship-integration-main.tsx"
// ...
import { defineWidgetConfig } from "@medusajs/admin-sdk"
import type { IntegrationSectionData } from "@gorgo/medusa-integration"
import { useApishipOptions } from "../hooks/api/apiship"

const ApishipIntegrationWidget = ({ data }: { data: IntegrationSectionData }) => {
  // Ключ инстанса от модуля: "int_apiship" или "int_apiship_<id>".
  const providerId = data.providerId

  // Читаем через собственный admin-роут, передавая ключ: виджет работает в браузере,
  // поэтому резолвить параметры на сервере он не может.
  const { apiship_options } = useApishipOptions(providerId)

  return (
    <>
      // ...существующие компоненты, providerId передаётся дальше во все хуки и запросы
    </>
  )
}

export const config = defineWidgetConfig({
  // зона расширения модуля: виджет встанет под сгенерированными секциями
  zone: "gorgo.integration.apiship.main.after",
})

export default ApishipIntegrationWidget
```

<Note type="warning">

`resolveIntegrationOptions` работает только на сервере. Он запускает воркфлоу в контейнере приложения. Виджет вместо этого читает через ваш собственный admin-роут, и этот роут решает, что отдавать: не возвращайте секреты в ответ, а всё, что уже покрыто секцией дескриптора, пусть отдаёт `GET /admin/integrations/:provider_id` Модуля интеграций.

</Note>

Записывать значения параметров нужно так же. Соберите новое значение своего `json`-параметра и передайте в воркфлоу `upsertIntegrationWorkflow` Модуля интеграций. Он ограничит запись объявленными параметрами, объединит их с сохранёнными значениями, провалидирует, зашифрует секреты и отправит событие `integration.updated`, чтобы сбросить кэш резолвера:

```ts title="workflows/update-apiship-options.ts"
import { upsertIntegrationWorkflow } from "@gorgo/medusa-integration"

// ...сначала собираем новый список подключений из сохранённого, затем:
upsertIntegrationWorkflow.runAsStep({
  input: transform({ input, settings }, (d) => ({
    provider_id: d.input.provider_id ?? DEFAULT_APISHIP_PROVIDER_ID,
    // Без `section_id`: виджет передаёт идентификаторы параметров напрямую.
    values: { settings: d.settings },
  })),
})
```

Модуль передаёт в виджет готовый ключ инстанса через `data.providerId`, так что передавать его в свои хуки и запросы можно напрямую. В итоге одна страница настроек для ApiShip совмещает сгенерированные секции и специфичный UI.

## Итог

Миграция завершена. Теперь провайдер модуля фулфилмента получает настройки из Medusa Admin без правок кода и без повторного развёртывания, хранит секреты зашифрованными, по умолчанию поддерживает несколько инстансов и может проверять соединение с внешним API. Почти весь прежний собственный UI исчез, потому что модуль генерирует его из дескриптора, а то, что осталось, находится на одной странице со сгенерированными секциями.

Полный код провайдера модуля фулфилмента ApiShip после миграции доступен в репозитории [`medusa-integrations`](https://github.com/gorgojs/medusa-integrations/tree/main/packages/providers/fulfillment-apiship).
