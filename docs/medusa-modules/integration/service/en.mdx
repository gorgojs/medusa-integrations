# {frontmatter.title}

This reference lists the methods of `IntegrationModuleService`, the Integration Module's main service. Code that has access to the Medusa container, such as an API route, a subscriber, a scheduled job, or a workflow step, resolves it by the `INTEGRATION_MODULE` key:

```ts title="src/api/admin/my-integration/route.ts"
import type { MedusaRequest, MedusaResponse } from "@medusajs/framework/http"
import { INTEGRATION_MODULE, IntegrationModuleService } from "@gorgo/medusa-integration"

export async function GET(req: MedusaRequest, res: MedusaResponse) {
  const integrationModuleService: IntegrationModuleService = req.scope.resolve(INTEGRATION_MODULE)

  const { integrations } = await integrationModuleService.listIntegrationsOverview({ category: "payment" })

  res.json({ provider_ids: integrations.map((integration) => integration.provider_id) })
}
```

`listIntegrationsOverview` returns every registered payment instance with its state, and the route sends back their keys. A provider in its own module's isolated container can't resolve the service this way, so it reads options through `resolveIntegrationOptions`, see [Reading Options](/medusa-modules/integration/reading-options).

<Note type="warning">

Change settings only through the module's [workflows](/medusa-modules/integration/workflows). The service's data-management methods, such as `updateIntegrations`, write the record as is. They don't validate the values or encrypt secrets, don't emit `integration.updated`, so consumers keep getting the cached options, and leave no record in the change history.

</Note>

## Resolving Options

| Method | Returns | Description |
| --- | --- | --- |
| `getResolvedOptions(identifier, instanceId?)` | `Promise<ResolvedOptions \| null>` | The instance's decrypted and validated options with defaults applied, as `{ options, meta }`, or `null` when the integration isn't configured, is disabled, or is incomplete. Throws a plain `Error`, not a `MedusaError`, when no provider is registered under that identifier and instance. Throws a `MedusaError` when a stored secret can't be decrypted. Cached for up to 60 seconds. |
| `clearOptionsCache(providerId?)` | `void` | Clears the cached options of one instance, or of every instance without an argument. |

## Registered Providers

| Method | Returns | Description |
| --- | --- | --- |
| `hasProviderId(providerId)` | `boolean` | Whether a provider is registered under the instance key. |
| `getProviderDescriptor(providerId)` | `IntegrationDescriptor \| undefined` | The provider's descriptor, with its `identifier` and `instanceId`. |
| `getProviderUiDescriptor(providerId)` | `UiDescriptor \| undefined` | The descriptor prepared for the Admin, with its sections, fields, and layout. |
| `listUiDescriptors()` | `UiDescriptor[]` | The same for every registered instance. |
| `getSecretKeys(providerId)` | `string[]` | The ids of the provider's secret options. |
| `getPackageMeta(providerId)` | `{ version, author, author_url }` | The details of the npm package the provider comes from, or `null` values when they can't be found. |

`UiDescriptor` is the `descriptor` that [`GET /admin/integrations/:provider_id`](/medusa-modules/integration/admin-api#integrations) returns, with the descriptor's `identifier`, `instanceId`, and `category`, its i18n keys and icon, its layout, `hasTestConnection`, and `sections` with their `fields`. The package root exports it, along with `UiSection` and `UiField`, the types of a section and a field.

## Stored Integrations

| Method | Returns | Description |
| --- | --- | --- |
| `listIntegrationsOverview(query?)` | `Promise<IntegrationOverviewResult>` | Every registered instance merged with its stored state, as the integrations list in the Admin shows it. The result holds `integrations`, one `IntegrationOverviewItem` per instance, along with `count` and `categories`. `query` is an `IntegrationOverviewQuery` with `q`, `category`, `limit`, and `offset`, the same as [`GET /admin/integrations`](/medusa-modules/integration/admin-api#list-integrations). Without `limit`, it returns every instance. Throws a `MedusaError` when a stored secret of any instance can't be decrypted. |
| `findByProviderId(providerId)` | `Promise<Integration \| undefined>` | The stored record of the instance, or `undefined` before the first save. |
| `isComplete(record)` | `boolean` | Whether a stored record passes full validation against its provider's descriptor. Returns `false` when the record's provider isn't registered. Throws a `MedusaError` when a stored secret can't be decrypted. |
| `getStoredValues(providerId)` | `Promise<Record<string, unknown>>` | The full stored configuration with the secrets decrypted, without validation or defaults. Returns `{}` when the instance has no stored record. Throws a `MedusaError` when a stored secret can't be decrypted. Never send the result to the browser. |
| `readPlainOptions(record)` | `Record<string, unknown>` | The stored `options` of a record with the secret options left as stored and the other options readable, including a value saved while its option was still secret. Never throws, so it works when a secret can't be decrypted. The Admin API routes build the record they return from it. Strip the secret options before you send the result to the browser, as the routes do. |
| `encryptForStorage(descriptor, values)` | `Record<string, unknown>` | A copy of `values` with the secret options encrypted, ready to store as the `options` of an `Integration`. It writes nothing. It needs `encryptionKey` only when the descriptor has secret options. |

The package root exports `IntegrationOverviewQuery`, `IntegrationOverviewResult`, and `IntegrationOverviewItem`, the types of `listIntegrationsOverview`.

`getStoredValues`, `isComplete`, `listIntegrationsOverview`, and `getResolvedOptions` decrypt stored secrets, and they need `encryptionKey` only when a record holds a value to decrypt. They throw a `MedusaError` of type `unexpected_state` when `encryptionKey` is missing, when it isn't the key a secret was saved with, or when a secret is stored in a format version the installed module doesn't know. Refer to [Integration Module Options](/medusa-modules/integration/module-options#encryptionkey) for the error messages and how to keep the key stable, and to [Integration Provider Descriptor](/medusa-modules/integration/descriptor#secrets-and-encryption) for how these methods read a value saved before its option's `secret` flag changed.

## Metadata

| Method | Returns | Description |
| --- | --- | --- |
| `getMetadataKey(input)` | `Promise<T \| undefined>` | The value of one top-level key of the instance's `metadata`, or `undefined` when the key or the record is missing. `input` is `{ identifier, instance_id?, key }`. |
| `updateMetadataKey(input, update)` | `Promise<T \| null \| undefined>` | Rewrites one top-level key of the instance's `metadata` under a row lock. `update` gets the current value and returns the new one, `null` to remove the key, or `undefined` to write nothing. Returns what `update` returned. Leaves no record in the change history and emits no event. Throws a `MedusaError` of type `not_found` when the instance has no stored record yet. |
| `mergeIntegrationMetadata(providerId, patch)` | `Promise<void>` | Merges `patch` into `metadata` the way Medusa does, where `""` removes a key and `null` clears it all, under the same row lock. `upsertIntegrationWorkflow` saves `metadata` through it. |

When your plugin keeps working state in the integration's `metadata`, such as a cursor or the state of an exchange, write it only with `updateMetadataKey`. `updateIntegrations` merges `metadata` in memory without a lock, so of two writes at the same time one is lost. `upsertIntegrationWorkflow` takes a ready value, not a function, so it can't check the current value of a key and write in one step, and every save emits `integration.updated`, which clears the cached options. With `updateMetadataKey`, writers of one record wait for each other, so a check and a write in `update` happen as one step:

```ts title="src/subscribers/import-requested.ts"
import type { SubscriberArgs, SubscriberConfig } from "@medusajs/framework"
import { INTEGRATION_MODULE, IntegrationModuleService } from "@gorgo/medusa-integration"

type ImportState = { state: "staged" | "importing" | "done"; session_id: string }

export default async function importRequested({ event, container }: SubscriberArgs<{ session_id: string }>) {
  const integrationModuleService: IntegrationModuleService = container.resolve(INTEGRATION_MODULE)

  const claimed = await integrationModuleService.updateMetadataKey<ImportState>(
    { identifier: "my-erp", key: "my_erp_import" },
    (current) =>
      current?.state === "staged" && current.session_id === event.data.session_id
        ? { ...current, state: "importing" }
        : undefined
  )

  if (!claimed) {
    return
  }

  // run the import
}

export const config: SubscriberConfig = { event: "my-erp.import_requested" }
```

If the event arrives twice, only the first subscriber moves the state from `staged` to `importing`, and the second gets `undefined` and exits.

Keep to a few rules:

- Name the key after your plugin, such as `my_erp_import`. The store's own code and the Admin's metadata form share `metadata` with every plugin.
- Keep the value small. Put files and long lists into the File Module and store their ids in the key.
- Keep `update` synchronous and quick. It runs while the record is locked, and the Admin can't save the integration's settings until it returns.

The form keeps keys it didn't change as they are, so a value your plugin writes while the form is open stays. A provider in its own module's isolated container can't resolve the service. Call `updateMetadataKey` from an API route, a subscriber, a scheduled job, or a workflow step.

## Connection Test

| Method | Returns | Description |
| --- | --- | --- |
| `runTestConnection(providerId)` | `Promise<{ status, message? }>` | Runs the provider's connection test against the resolved options. Refer to [Integration Module Workflows](/medusa-modules/integration/workflows#testintegrationconnectionworkflow) for the results the module produces itself. It neither stores `last_test_status` nor emits `integration.tested`, which `testIntegrationConnectionWorkflow` does. When a stored secret can't be decrypted, it reports `failed` with the error's message instead of throwing. |

## Change History

| Method | Returns | Description |
| --- | --- | --- |
| `listChangeActors()` | `Promise<{ users, system }>` | `users` holds the admin users who made changes, as `IntegrationChangeUser` objects with the email stored with their latest change. `system` says whether anything else made changes. |
| `listChangeFields()` | `Promise<IntegrationChangeField[]>` | Every option id and label key the history names, as `{ field, label }`, including options and integrations that no longer exist. |
| `recordChange(input)` | `Promise<string \| null>` | Stores one history record and returns its id. `input` is a `RecordIntegrationChangeInput`, exported from the package root. `provider_id`, `change_type` (`created`, `updated`, `enabled`, `disabled`, or `deleted`), and `actor` (an `IntegrationChangeActor`) are required. `actor_label`, `diff` (a `DiffEntry[]`), `metadata`, and `created_at`, which defaults to now, are optional. It never throws. On failure, it logs a warning and returns `null`. The module's workflows call it through `recordIntegrationChangeStep`. |

To read the records themselves, use the generated methods of `IntegrationChange` below. They return the stored rows as they are. Unlike the [Admin API routes](/medusa-modules/integration/admin-api#change-history), they don't hide the values of options that became secret after a change was recorded. The package root exports `IntegrationChangeUser` and `IntegrationChangeField`.

## Catalog and Licenses

| Method | Returns | Description |
| --- | --- | --- |
| `getCatalog()` | `Promise<CatalogItem[]>` | The [integration catalog](/medusa-modules/integration/browse-integrations), with `installed` and `provider_id` for every entry registered in the project. |
| `listLicenseStates()` | `LicenseStateEntry[]` | The latest license check result of every paid Gorgo integration. |
| `recheckLicenseStates()` | `Promise<LicenseStateEntry[]>` | Checks the licenses right away and returns the fresh results. |

A catalog item, of type `CatalogItem`, is an entry of the Gorgo catalog, with `integrationId`, `slug`, `npm`, `category`, `label`, and more, plus `installed` and `provider_id`. A license entry, of type `LicenseStateEntry`, is the verdict for one npm package, with `package`, `state`, `checked_at`, `subscription`, `latest_allowed_version`, and the provider `identifiers` the package ships. The package root exports both types. The Admin API returns the same shapes, refer to [Catalog and Licenses](/medusa-modules/integration/admin-api#catalog-and-licenses) for its routes.

## Generated Data-Management Methods

The service extends Medusa's `MedusaService`, which generates data-management methods for both [data models](/medusa-modules/integration/data-models):

- for `Integration`: `listIntegrations`, `listAndCountIntegrations`, `retrieveIntegration`, `createIntegrations`, `updateIntegrations`, `deleteIntegrations`, `softDeleteIntegrations`, and `restoreIntegrations`;
- for `IntegrationChange`: `listIntegrationChanges`, `listAndCountIntegrationChanges`, `retrieveIntegrationChange`, `createIntegrationChanges`, `updateIntegrationChanges`, `deleteIntegrationChanges`, `softDeleteIntegrationChanges`, and `restoreIntegrationChanges`.

Use the `list` and `retrieve` methods to read. They return records of the types `Integration` and `IntegrationChange`, both exported from the package root. The stored `options` of an `Integration` hold its secrets encrypted. Refer to Medusa's [service factory reference](https://docs.medusajs.com/resources/service-factory-reference) for their parameters.
