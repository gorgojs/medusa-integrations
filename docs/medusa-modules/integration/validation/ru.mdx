# {frontmatter.title}

В этом руководстве вы узнаете, как объявить правила валидации параметров интеграции, когда Модуль интеграций проверяет каждое из них и как их протестировать.

<Note type="default" title="">

Все правила из этого руководства объявляются в дескрипторе провайдера. Полный список полей параметра смотрите в справочнике [Дескриптор провайдера интеграций](/medusa-modules/integration/descriptor).

</Note>

## Когда модуль проверяет параметры

Модуль проверяет параметры в два момента, и каждый раз в разном объёме:

- **При сохранении.** Когда администратор магазина сохраняет секцию или ваш код отправляет значения параметров, модуль проверяет только отправленные параметры. Их правила он применяет к сохранённой конфигурации, поверх которой наложены отправленные значения, без значений по умолчанию из дескриптора. Поэтому правило может читать параметры из других секций. Если правило не проходит, сохранение отклоняется и ничего не записывается.
- **Полная валидация.** Модуль проверяет всю собранную конфигурацию с подставленными значениями по умолчанию: все правила каждого параметра и общее правило дескриптора. От результата зависит, считается ли интеграция полностью настроенной. Полная валидация выполняется каждый раз, когда потребитель получает параметры и когда Admin показывает статус интеграции. Сохранение она никогда не блокирует.

Сохраняются настройки по секциям, поэтому конфигурация может быть корректной в каждой секции по отдельности и при этом неполной в целом. Такая интеграция получает статус **Не завершено**, и потребители не получат её параметры, пока администратор магазина не заполнит недостающее.

| Правило | При сохранении | Полная валидация |
| --- | --- | --- |
| [Встроенные правила](#встроенные-правила) типа параметра и `required` | Только отправленные параметры | Все параметры |
| [`validate` параметра](#правила-параметра) | Только отправленные параметры | Все параметры |
| [`validate` дескриптора](#правила-для-нескольких-секций) | Никогда | Всегда |

Схема показывает оба прохода рядом и то, где рядом с ними стоит проверка соединения:

```mermaid alt="Схема показывает два прохода валидации, при сохранении и полную, и проверку соединения как отдельное действие"
flowchart TD
  subgraph save ["При сохранении"]
    s1["Встроенное правило отправленного параметра"] --> s2["Его validate"]
    s2 --> s3["Сохранено или отклонено с 400"]
  end
  subgraph full ["Полная валидация"]
    f1["Значения по умолчанию и встроенные правила"] --> f2["validate каждого параметра"]
    f2 --> f3["validate дескриптора"]
    f3 --> f4["Завершено или Не завершено"]
  end
  f4 -->|"итоговые параметры"| test["Проверка соединения, отдельное действие"]
```

При сохранении каждый отправленный параметр проходит встроенное правило, а затем собственный `validate`, и любая проблема отклоняет сохранение с ошибкой `400`. Полная валидация разбирает всю конфигурацию целиком и решает, завершена ли интеграция, но сохранение она не блокирует. Проверка соединения не относится ни к одному из проходов. Администратор магазина запускает её отдельным действием, и она вызывает `testConnection` дескриптора только с параметрами, которые удалось получить, то есть для включённой и полностью настроенной интеграции. Как её написать, читайте в руководстве [Как создать провайдер Модуля интеграций](/medusa-modules/integration/create-integration-module-provider#testconnection).

## Встроенные правила

У каждого типа параметра (`type`) есть свои правила, например формат URL для `url` или допустимые значения `values` для `enum`. Поля конкретного типа добавляют новые, например `minLength` и `pattern` для `string` или `min`, `max` и `int` для `number`. Все они перечислены в разделе [Дополнительные поля по типу параметра](/medusa-modules/integration/descriptor#дополнительные-поля-по-типу-параметра).

`required: true` отклоняет параметр без значения. Для всех типов, кроме `string` и `json`, значением не считается пустая строка, а для всех типов ещё и `null`. Параметр с `default` никогда не нарушает `required`, потому что пропуск заполняет значение по умолчанию.

Форма в Admin тоже отмечает обязательные поля и не отправляет их пустыми. Исключение составляет секрет, у которого уже есть сохранённое значение: пустое поле оставляет его как есть.

Для параметра типа `string` правило про пустую строку не действует, потому что пустая строка для него значение. На сервере одного `required: true` достаточно, чтобы принять `""`, и интеграция считается полностью настроенной с пустым полем. Форма в Admin не даст отправить пустое обязательное поле, а запрос к API Admin или виджет даст. Добавьте обязательному параметру `string` значение `minLength: 1`, чтобы отклонять такие значения, как это делает провайдер ЮKassa для своих `shopId` и `secretKey`.

## Правила параметра

Если встроенных правил параметра недостаточно, добавьте ему функцию `validate`. Она получает значение параметра и контекст с двумя полями:

- `options` – конфигурация, по которой проверяется правило, с соседними параметрами из всех секций. При сохранении это сохранённые значения с наложенными поверх отправленными, без значений по умолчанию из дескриптора. При полной валидации это вся конфигурация после подстановки значений по умолчанию;
- `addIssue({ message, path? })` – сообщает о проблеме. Без `path` проблема относится к самому параметру.

Например, код ставки НДС обязателен, только пока включены чеки:

```ts title="providers/integration-my/services/my-integration.ts"
import { defineIntegration } from "@gorgo/medusa-integration"
import type { OptionValidateContext } from "@gorgo/medusa-integration"

const requiredWhenReceipt = (value: number | undefined, ctx: OptionValidateContext) => {
  if (ctx.options.useReceipt && value == null) {
    ctx.addIssue({ message: "Required when receipts are enabled" })
  }
}

const descriptor = defineIntegration({
  category: "payment",
  displayName: "my.name",
  options: {
    apiKey: {
      type: "string",
      control: "secret",
      secret: true,
      required: true,
      minLength: 1,
      label: "my.apiKey"
    },
    useReceipt: {
      type: "boolean",
      default: false,
      label: "my.useReceipt"
    },
    vatCode: {
      type: "enum",
      values: [1, 2, 3, 4, 5, 6],
      label: "my.vatCode",
      visibleWhen: { field: "useReceipt", equals: true },
      validate: requiredWhenReceipt,
    },
  },
  sections: [
    {
      id: "credentials",
      title: "my.credentials",
      options: ["apiKey"]
    },
    {
      id: "receipts",
      title: "my.receipts",
      options: ["useReceipt", "vatCode"]
    },
  ],
})
```

`vatCode` не помечен `required`, поэтому магазину, который не отправляет чеки, заполнять его не нужно. `visibleWhen` только прячет поле в Admin, пока `useReceipt` выключен, а обязательным его делает `requiredWhenReceipt`. Правило читает `useReceipt` из `ctx.options`. Это конфигурация с наложенными отправленными значениями, поэтому правило видит переключатель независимо от того, сохраняется ли он вместе с `vatCode`.

Условное поле проверяйте в `validate` и не сочетайте `required: true` с `visibleWhen`. Поле, скрытое через `visibleWhen`, всё равно отправляется и проверяется, потому что форма в Admin подставляет и отправляет все поля своей секции. Скрытый параметр типа `number`, `enum`, `url`, `email` или `uuid` без `default` уходит пустым, не проходит `required`, и модуль отклоняет сохранение, пока поле скрыто.

<Note type="default" title="">

При сохранении правило параметра выполняется, только если этот параметр отправлен. Если бы `useReceipt` находился в другой секции, его включение сохранилось бы без ошибок, а полная валидация оставила бы интеграцию в статусе **Не завершено**, пока администратор магазина не заполнит `vatCode`.

</Note>

<Note type="warning">

Правило, которое читает соседний параметр со `default`, может видеть разные значения в двух проходах. Если этот параметр находится в секции, которая ещё не сохранена, при сохранении правило не найдёт его, а при полной валидации найдёт значение по умолчанию. Правило может пройти при сохранении, а интеграция останется в статусе **Не завершено**. Подставляйте значение по умолчанию соседнего параметра прямо в правиле, например `ctx.options.mode ?? "webhook"` для параметра `mode` с `default: "webhook"`.

</Note>

## Правила для нескольких секций

Правило, которое сравнивает несколько параметров и не относится ни к одному из них, задаётся в собственном `validate` дескриптора. Оно получает всю собранную конфигурацию и `addIssue`, который через `path` может указать на любой параметр:

```ts title="providers/integration-my/services/my-integration.ts"
const descriptor = defineIntegration({
  // ...
  validate: (full, { addIssue }) => {
    if (full.mode === "webhook" && !full.webhookSecret) {
      addIssue({ path: ["webhookSecret"], message: "Required when mode is \"webhook\"" })
    }
  },
})
```

Это правило выполняется только при полной валидации. Секция с `mode` сохранится в любом случае, а интеграция останется в статусе **Не завершено**, пока правило сообщает о проблеме. Если правило на самом деле касается одного параметра, задайте его в `validate` этого параметра, чтобы администратор магазина узнал о проблеме при сохранении.

## Что видит администратор магазина

Сохранение, которое не прошло валидацию, возвращает ошибку `400`, и Admin показывает её сообщение в уведомлении. В сообщении каждая проблема записана как `<идентификатор параметра>: <сообщение>`, например `vatCode: Required when receipts are enabled`.

Конфигурация, которая не проходит полную валидацию, получает статус **Не завершено** в списке и на странице интеграции. Проблемы полной валидации Admin не перечисляет, поэтому сообщения правил для нескольких секций пишите для разработчика, который тестирует дескриптор, а не для администратора магазина.

## Тестирование правил

`@gorgo/medusa-integration` экспортирует полную валидацию самого модуля, поэтому unit-тест может проверить дескриптор без запущенного приложения Medusa:

- `collectValidationIssues(descriptor, config)` возвращает все проблемы в виде `{ path, message }` и пустой массив для полной конфигурации;
- `isDescriptorComplete(descriptor, config)` возвращает `true`, если проблем нет.

Например, тест для дескриптора выше:

```ts title="providers/integration-my/__tests__/descriptor.unit.spec.ts"
import { collectValidationIssues } from "@gorgo/medusa-integration"
import MyIntegrationProvider from "../services/my-integration"

const descriptor = new MyIntegrationProvider().descriptor

describe("my integration descriptor", () => {
  it("requires a VAT code once receipts are on", () => {
    expect(
      collectValidationIssues(descriptor, { apiKey: "key", useReceipt: true })
    ).toEqual([
      { path: "vatCode", message: "Required when receipts are enabled" },
    ])
  })
})
```

`collectValidationIssues` выполняет те же проверки, что и модуль перед тем, как параметры станут активными. Он разбирает всю конфигурацию схемой дескриптора, которая за один проход подставляет значения по умолчанию и применяет встроенные правила, а затем выполняет `validate` каждого параметра и `validate` дескриптора. Если встроенное правило не прошло, собственные правила всё равно выполняются, но над исходной конфигурацией без значений по умолчанию, поэтому правило, которое читает соседний параметр со значением по умолчанию, не найдёт его. `path` соединяет точками идентификатор параметра и вложенные ключи.
