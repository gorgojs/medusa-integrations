# {frontmatter.title}

This reference lists the data models of the Integration Module. Like any Medusa data model, each one also has `created_at`, `updated_at`, and `deleted_at`.

<Note type="default" title="">

Read these models through the module's [service](/medusa-modules/integration/service) or the [Admin API](/medusa-modules/integration/admin-api), and change them only through its [workflows](/medusa-modules/integration/workflows).

</Note>

## Relations Overview

The two models aren't related in the database. An `IntegrationChange` names its integration only by `provider_id`, as the diagram shows.

```mermaid alt="Diagram showcasing the Integration and IntegrationChange models, joined by provider_id without a foreign key"
erDiagram
  Integration {
    string id PK
    string provider_id UK
    enum category
    boolean is_enabled
    enum last_test_status
  }
  IntegrationChange {
    string id PK
    string provider_id
    string change_type
    string actor_type
    datetime created_at
  }
  Integration |o..o{ IntegrationChange : "provider_id"
```

`Integration` and `IntegrationChange` share the `provider_id` value, but `IntegrationChange.provider_id` is plain text, so there is no foreign key and no cascade. Deleting an integration leaves its changes in place, so a change outlives its integration.

## Integration

The stored settings of one integration instance, in the `integration` table. The module creates the record on the first save of any section and deletes it when the store admin deletes the integration. A registered provider without a record is **Not configured**.

Whether the integration is complete isn't stored. The module checks it against the provider's current descriptor whenever it's needed, so it can't go stale when the descriptor changes.

The `integration` table has a unique index on `provider_id` that covers the records that aren't soft-deleted, an index on `category`, and an index on `deleted_at`.
