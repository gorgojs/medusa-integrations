# {frontmatter.title}

This reference lists the workflows and steps the Integration Module exports. The module's own [Admin API routes](/medusa-modules/integration/admin-api) run these workflows, and your code can run them too, for example from an API route, a subscriber, or your own workflow.

<Note type="warning">

Change integration settings only through these workflows. A write through the module's service skips validation, encryption, the cache reset, and the change history, see [Integration Module Service](/medusa-modules/integration/service).

</Note>

## Import Paths

`upsertIntegrationWorkflow`, `getResolvedIntegrationOptionsWorkflow`, and `getResolvedIntegrationOptionsStep` are exported from the package root. Every workflow and step on this page is exported from the `@gorgo/medusa-integration/workflows` subpath.

For example, a workflow of your own that disables an integration as one of its steps:

```ts title="src/workflows/disable-my-integration.ts"
import { createWorkflow, WorkflowResponse } from "@medusajs/framework/workflows-sdk"
import { setIntegrationEnabledWorkflow } from "@gorgo/medusa-integration/workflows"

export const disableMyIntegrationWorkflow = createWorkflow(
  "disable-my-integration",
  () => {
    const integration = setIntegrationEnabledWorkflow.runAsStep({
      input: { provider_id: "int_my", is_enabled: false },
    })

    return new WorkflowResponse(integration)
  }
)
```

`runAsStep` runs the module's workflow as a step of yours. The input has no `actor`, so the change history records the change with the `system` actor type. If a later step of your workflow fails, the integration returns to its previous state and its history record is removed.

<Note type="warning">

Only `setIntegrationEnabledStep` and `recordIntegrationChangeStep` have a rollback. If you run `upsertIntegrationWorkflow`, `deleteIntegrationWorkflow`, or `testIntegrationConnectionWorkflow` as a step of your own workflow and a later step fails, the saved options, the deletion, and `last_test_status` stay, while the history record is removed. A change can then remain with no entry in the change history. Refer to [Steps](#steps) to learn what each step does on rollback.

</Note>

## Workflows

Every workflow below except `getResolvedIntegrationOptionsWorkflow` ends with `emitIntegrationEventStep`, which emits the workflow's [event](/medusa-modules/integration/events) once every earlier step has finished. A run that fails before that step, for example with a `not_found` or `invalid_data` error, emits nothing, and a rollback doesn't emit a second event.

### upsertIntegrationWorkflow

Saves option values of an integration instance. It creates the stored record on the first save and updates it afterwards. This is the workflow behind saving a section in the Admin. It runs these steps in order.

```mermaid alt="Diagram showcasing the steps of upsertIntegrationWorkflow, from reading the stored state to emitting integration.updated"
flowchart TD
  state["getIntegrationStateStep"] --> apply["applyIntegrationSectionStep"]
  apply --> save["upsertIntegrationRecordStep"]
  save -->|"skipped when an update changes no field"| history["recordIntegrationChangeStep"]
  history --> emit["emitIntegrationEventStep"]
  emit -->|"emits"| event(["integration.updated"])
```

The first step reads the stored state, which lets the change history tell a first save from an update. The history record is skipped when an update changes no field, and the event is emitted either way.

The workflow validates the written options against the stored configuration with the new values on top, encrypts secrets, and saves the record. Then it records a `created` or `updated` change, unless nothing changed, and emits `integration.updated`. It returns the stored `Integration` record, whose `options` hold the secrets encrypted.

It fails with a `not_found` error when no provider is registered under `provider_id`, and with an `invalid_data` error for an unknown `section_id` or values that fail validation.

### setIntegrationEnabledWorkflow

Enables or disables a configured integration. It runs these steps in order.

```mermaid alt="Diagram showcasing the steps of setIntegrationEnabledWorkflow, from reading the stored state to emitting integration.updated"
flowchart TD
  state["getIntegrationStateStep"] --> set["setIntegrationEnabledStep"]
  set -->|"skipped when already in that state"| history["recordIntegrationChangeStep"]
  history --> emit["emitIntegrationEventStep"]
  emit -->|"emits"| event(["integration.updated"])
```

The state read in the first step lets the workflow skip the history record when the integration is already in the requested state. The event is emitted either way.

The workflow sets `is_enabled` on the stored record, records an `enabled` or `disabled` change unless the integration was already in that state, and emits `integration.updated`. It returns the updated record. It fails with a `not_found` error when the integration has no stored record yet, since there is nothing to enable before the first save. If a later step fails, the previous state is restored.

### deleteIntegrationWorkflow

Deletes the stored settings of an integration instance. The provider stays registered, and the integration shows as not configured again. It runs these steps in order.

```mermaid alt="Diagram showcasing the steps of deleteIntegrationWorkflow, from deleting the stored record to emitting integration.updated"
flowchart TD
  delete["deleteIntegrationRecordStep"] -->|"skipped when nothing was deleted"| history["recordIntegrationChangeStep"]
  history --> emit["emitIntegrationEventStep"]
  emit -->|"emits"| event(["integration.updated"])
```

The history record is skipped when there was nothing to delete, and the event is emitted either way.

The workflow deletes the stored record, records a `deleted` change with a snapshot of the values that were configured, and emits `integration.updated`. It returns `{ deleted, diff }`, where `deleted` is `false` when there was nothing to delete. It never decrypts the stored secrets, so it works even when the encryption key has changed.

### testIntegrationConnectionWorkflow

Runs the connection test the provider's descriptor declares. It runs these steps in order.

```mermaid alt="Diagram showcasing the steps of testIntegrationConnectionWorkflow, from running the test to emitting integration.tested"
flowchart TD
  run["runTestConnectionStep"] -->|"stores the status only if a record exists"| emit["emitIntegrationEventStep"]
  emit -->|"emits"| event(["integration.tested"])
```

The test step stores `last_test_status` only when the integration has a stored record, and the event is emitted whatever the result is.

<MedusaTypeList
  sectionTitle="Input"
  types={[
    {
      name: "provider_id",
      type: "string",
      description: "The instance's key, `int_<identifier>[_<instanceId>]`.",
      optional: false,
      expandable: false,
      children: []
    },
    {
      name: "actor",
      type: "IntegrationChangeActor",
      description: "Who runs the test. It's passed on in the `integration.tested` event, and the test itself isn't recorded in the change history.",
      optional: true,
      expandable: false,
      children: []
    }
  ]}
/>

The workflow runs the test against the resolved options and returns `{ status, message? }`. Besides what your `testConnection` returns, the module produces these results itself, and the workflow doesn't throw for any of them:

- `{ status: "skipped", message: "No test configured" }` when the descriptor has no `testConnection`.
- `failed` with the message `Unknown integration provider "<id>"` when no provider is registered under `provider_id`.
- `failed` with the message `Not configured` when the descriptor declares a test, but the integration isn't configured, is disabled, or is incomplete. The module doesn't call `testConnection` in that case.
- `failed` with the error's message when `testConnection` throws, or with the message `Test failed` when the error has none.

The workflow emits `integration.tested` for each of these results. Refer to [Connection Test](/medusa-modules/integration/descriptor#connection-test) to learn what the Admin shows for each status.

The module's scheduled job, `test-integration-connections-daily`, runs this workflow every day at 03:00 for each enabled integration whose provider declares a test, with the actor `{ type: "job", id: "test-integration-connections-daily" }`. That includes an enabled integration that is still incomplete, which gets `failed` with the message `Not configured`.

Resolves an integration instance's options, the same way as `resolveIntegrationOptions` and the service's `getResolvedOptions`.

## Steps

The workflows above are built from these steps. Use them in a workflow of your own when you need only part of what a workflow does. The last column says what a step does when a later step of your workflow fails.

| Step | Input | What it does | On rollback |
| --- | --- | --- | --- |
| `getResolvedIntegrationOptionsStep` | `{ identifier, instance_id? }` | Returns the resolved options, or `null`. | Nothing to undo. |
| `getIntegrationStateStep` | `{ provider_id }` | Returns `{ existed, title, is_enabled }` of the stored record before a change. | Nothing to undo. |
| `applyIntegrationSectionStep` | `{ provider_id, section_id?, values }` | Picks the options to write, validates them, and returns `{ category, options, diff }`, where `options` is the full configuration ready to store, with secrets encrypted. Stores nothing. | Nothing to undo. |
| `upsertIntegrationRecordStep` | `{ provider_id, category, options, title? }` | Creates or updates the stored record. | None. The saved record stays. |
| `setIntegrationEnabledStep` | `{ provider_id, is_enabled }` | Sets `is_enabled` on the stored record. | Restores the previous `is_enabled`. |
| `deleteIntegrationRecordStep` | `{ provider_id }` | Deletes the stored record and returns `{ deleted, diff }`. | None. The record stays deleted. |
| `runTestConnectionStep` | `{ provider_id }` | Runs the connection test and stores its status as `last_test_status`, if the integration has a stored record. | None. `last_test_status` stays. |
| `recordIntegrationChangeStep` | `{ provider_id, change_type, actor?, diff?, skip? }` | Writes a change history record, or nothing when `skip` is `true` or an `updated` change has no fields. Never fails the workflow. | Removes the history record. |
| `emitIntegrationEventStep` | `{ name, data }` | Emits an event through Medusa's event bus. | None. The emitted event stays. |
