# {frontmatter.title}

In this guide, you'll learn how to create a Medusa provider that manages its settings through the [Integration Module](/medusa-modules/integration).

<Note type="info" title="What is the Integration Module?">

The Integration Module lets any plugin describe its options as a schema, and store admins configure them in the Admin, with no `medusa-config` edits and no redeploy of the Medusa app. It generates the UI, provides a CRUD API and validation, so you don't have to write your own data models, routes, forms, or workflows.

</Note>

<Prerequisites items={[
  {
    text: "A Medusa application on v2.17.2 or later, with the Integration Module installed and its migrations run",
    link: "/medusa-modules/integration#installation"
  },
  {
    text: "A Medusa plugin to add the provider to, with @gorgo/medusa-integration as a peer and a dev dependency",
    link: "/tools/create-medusa-plugin"
  }
]}/>

The diagram shows what this guide builds and how the parts connect:

```mermaid alt="Diagram showcasing how medusa-config.ts, the provider definition and the service lead to the Integration Module, which generates the settings page the store admin fills in and serves the options to your code"
flowchart TD
  config["medusa-config.ts"] -->|"registers"| definition["index.ts<br/>ModuleProvider"]
  definition -->|"declares"| service["MyIntegrationProvider<br/>static identifier, descriptor"]
  service -->|"descriptor"| module["Integration Module"]
  module -->|"generates"| page["Settings → Integrations"]
  admin(["Store admin"]) -->|"fills in the options"| page
  code["Your code"] -->|"resolveIntegrationOptions"| module
```

`medusa-config.ts` registers the provider definition, which is the `index.ts` file that calls `ModuleProvider`. The definition declares the service class, which has a `static identifier` and a `descriptor`. The Integration Module turns the descriptor into the page under **Settings → Integrations**, where the store admin fills in the options. Your code then reads them with `resolveIntegrationOptions`.

## Implementation Example

When you write your own Integration Module provider, it helps to see how a finished one is put together.

For a real implementation, read the [YooKassa payment provider in the Medusa Integrations repository](https://github.com/gorgojs/medusa-integrations/tree/main/packages/providers/payment-yookassa).

---

## 1. Create the Provider Directory

Start by creating a new directory for your Integration Module provider. In a plugin it goes under `src/providers`, for example `src/providers/integration-my`.

If you don't have a plugin yet, create one together with an example project using [`create-medusa-plugin`](/tools/create-medusa-plugin).

---

## 2. Create the Integration Module Provider Service

Create the file `src/providers/integration-my/services/my-integration.ts`, which declares the integration provider's descriptor and the service itself.

![Directory structure in the Medusa plugin after creating the service file](/static/integration/plugin/src-providers-integration-my-services-my-integration.webp)

```ts title="providers/integration-my/services/my-integration.ts"
import {
  AbstractIntegrationProviderService
} from "@gorgo/medusa-integration"

class MyIntegrationProvider extends AbstractIntegrationProviderService {
  // TODO add methods
}

export default MyIntegrationProvider
```

The parent class you're extending here, `AbstractIntegrationProviderService`, is abstract, so the subclass must implement its `descriptor` property (declared as a `get`). The class also needs a `static identifier`, which the loader relies on.

### identifier

Every Integration Module provider has a unique identifier. The store admin configures the provider under it, and a consumer reads the provider's options by the same one.

#### Example

```ts title="providers/integration-my/services/my-integration.ts"
class MyIntegrationProvider extends AbstractIntegrationProviderService {
  static identifier = "my"
  // ...
}
```

The loader reads this static field to build the key your instance is registered under: `int_<identifier>_<id>`, or `int_<identifier>` without an ID.

### descriptor

The provider class must implement the `descriptor` property. The descriptor holds a single declaration of the options, how they group into settings sections, and an optional connection test. You create it with `defineIntegration`.

<Note type="default" title="">

Refer to [General Concepts](/medusa-modules/integration/concepts#descriptor) for an overview of the descriptor, and to [Integration Provider Descriptor](/medusa-modules/integration/descriptor) for the full reference of every `options` field (`type`, `control`, `default`, `required`, `secret`, `visibleWhen`, `validate`, and others), by type. [Validate Integration Options](/medusa-modules/integration/validation) covers the rules you can declare, and [Localize an Integration](/medusa-modules/integration/localization) covers the translations for the `my.*` i18n keys.

</Note>

#### Example

```ts title="providers/integration-my/services/my-integration.ts"
import {
  AbstractIntegrationProviderService,
  defineIntegration,
  z
} from "@gorgo/medusa-integration"

const descriptor = defineIntegration({
  category: "payment",
  displayName: "my.name",
  options: {
    apiKey: {
      type: "string",
      control: "secret",
      secret: true,
      required: true,
      minLength: 1,
      label: "my.apiKey"
    },
    sandbox: {
      type: "boolean",
      control: "switch",
      default: false,
      label: "my.sandbox"
    },
  },
  sections: [
    {
      id: "credentials",
      title: "my.credentials",
      options: ["apiKey", "sandbox"]
    },
  ],
})

export type MyOptions = z.infer<typeof descriptor.optionsSchema>

export class MyIntegrationProvider extends AbstractIntegrationProviderService {
  // ...
  get descriptor() {
    return descriptor
  }
}

export default MyIntegrationProvider
```

`MyOptions` is the resolved, validated shape: `defineIntegration` builds `optionsSchema` from the `options` object, and since `apiKey` is `required` and `sandbox` has a `default`, both end up non-optional in `MyOptions`.

A `required` option of type `string` accepts an empty string, so `apiKey` also sets `minLength: 1`. An empty key then fails validation, and the integration stays incomplete until the admin enters a value. Refer to [Validate Integration Options](/medusa-modules/integration/validation) to learn about the rules you can declare.

### validateOptions

Like other Medusa providers, an Integration Module provider can declare a static `validateOptions` to check its `medusa-config.ts` configuration at load time.

#### Example

```ts title="providers/integration-my/services/my-integration.ts"
class MyIntegrationProvider extends AbstractIntegrationProviderService {
  // ...
  static validateOptions(options: Record<string, unknown>) {
    // optional fail-fast check of options.providers[].options
  }
}
```

The base class's own `validateOptions` is a no-op (`(): void | never {}`), so overriding it is optional. The `void | never` return type signals it either returns nothing or throws to fail the load.

<Note type="default" title="">

In practice, `options.providers[].options` is almost always `{}` for an Integration Module provider. The store admin sets the real settings in the Admin rather than in `medusa-config.ts`, so `validateOptions` matters less here than it does for other Medusa providers.

</Note>

### testConnection

Unlike `validateOptions`, which checks the provider's configuration in `medusa-config.ts`, `testConnection` checks the integration's own options, such as an API key, against the third-party service. The store admin runs it from the Admin, and a scheduled job re-tests every enabled integration once a day. You declare it directly in the descriptor.

#### Example

```ts title="providers/integration-my/services/my-integration.ts"
const descriptor = defineIntegration({
  // ...
  testConnection: async ({ options }) => {
    const res = await fetch("https://api.my.com/ping", {
      headers: { Authorization: `Bearer ${options.apiKey}` },
    })

    return res.ok
      ? { status: "passed" }
      : { status: "failed", message: `My responded with ${res.status}` }
  },
})
```

`status` is one of `"passed" | "failed" | "skipped"`. Returning `{ status: "failed", message }` counts as a normal result, not an error. If `testConnection` throws, the module reports the test as `failed` with the error's message, so the store admin sees it in the Admin either way.

## 3. Create Module Provider Definition File

Create the file `src/providers/integration-my/index.ts` with the following content:

![Directory structure in the Medusa plugin after creating the provider definition file](/static/integration/plugin/src-providers-integration-my-index.webp)

```ts title="providers/integration-my/index.ts"
import { ModuleProvider } from "@medusajs/framework/utils"
import { INTEGRATION_MODULE } from "@gorgo/medusa-integration"
import MyIntegrationProvider from "./services/my-integration"

export default ModuleProvider(INTEGRATION_MODULE, {
  services: [MyIntegrationProvider],
})
```

This exports the provider definition, declaring `MyIntegrationProvider` as its service.

---

## 4. Register the Provider

To use your Integration Module provider, add it to the Integration Module's `providers` array in `medusa-config.ts`, and list the plugin itself in `plugins`. Replace `<your-plugin-package>` with the `name` in your plugin's `package.json`:

```ts title="medusa-config.ts"
module.exports = defineConfig({
  // ...
  plugins: [
    {
      resolve: "@gorgo/medusa-integration",
      options: {
        encryptionKey: process.env.INTEGRATION_ENCRYPTION_KEY,
        providers: [
          {
            resolve: "<your-plugin-package>/providers/integration-my",
            options: {},
          },
        ],
      },
    },
    {
      resolve: "<your-plugin-package>",
      options: {},
    },
    // ...
  ],
})
```

The loader instantiates `MyIntegrationProvider` from the `providers` entry. Its `resolve` is the plugin's package name followed by the provider's path, `<your-plugin-package>/providers/integration-my`, which relies on the plugin's `"./providers/*"` export in `package.json`.

The second entry lists the plugin itself. Medusa loads a plugin's Admin extensions, such as its translations and widgets, only for packages listed in `plugins`. Without the entry the provider still registers, but the Admin doesn't load the plugin's translations, so the integration page shows keys such as `my.name` instead of readable text.

That `resolve` value is for a provider in a plugin. A provider that sits inside the Medusa application itself is registered by its path from the application's directory, such as `./src/providers/integration-my`, and needs no entry in `plugins`. Medusa resolves a relative path against the application's directory, so the same path fails for a provider in a plugin.

<Note type="warning">

Leave out `id` while your provider has a single instance, as in the example above. The provider then registers under the key `int_<identifier>`, which is `int_my`, and a consumer reads its options with `{ identifier: "my" }`. Add an `id` only when you register the provider more than once, with one `id` per instance. The key then becomes `int_<identifier>_<id>`, for example `int_my_eu`, and a consumer has to pass the same value as `instance_id`. Otherwise `resolveIntegrationOptions` throws, because nothing is registered under `int_my`. Refer to [Identifiers and Instances](/medusa-modules/integration/concepts#identifiers-and-instances) to learn how instances work.

</Note>

Next, add the secret encryption key to your environment variables. The Integration Module uses it to encrypt secrets before saving them to the database:

```text title=".env"
INTEGRATION_ENCRYPTION_KEY=supersecret
```

Any non-empty value works. The module derives it via SHA-256 into a 32-byte AES-256-GCM key, so use a high-entropy one, for example `openssl rand -hex 32`.

---

## 5. Test It Out

Start the server and open **Settings → Integrations** in Medusa Admin. Your integration appears in the list. Fill in the options, then choose **Test connection** in the action menu next to the integration's name to run `testConnection`.

To read the saved options, use `resolveIntegrationOptions` and pass the same `identifier` your provider class declares:

```ts title="providers/payment-my/services/my-payment.ts"
import { resolveIntegrationOptions } from "@gorgo/medusa-integration"
import type { MyOptions } from "../../integration-my/services/my-integration"

const options = await resolveIntegrationOptions<MyOptions>({
  identifier: "my",
})
```

The returned `options` is typed as `MyOptions`, already decrypted and validated. By default the call throws a `MedusaError` if the integration is not configured, disabled, or incomplete.

<Note type="default" title="">

Refer to [Reading Options](/medusa-modules/integration/reading-options) to learn how to read an integration's options from a route, subscriber, or workflow step.

</Note>
