# {frontmatter.title}

An integration provider's [descriptor](/medusa-modules/integration/concepts#descriptor) is where you declare the integration's options, how they group into settings sections, their validation, and an optional connection test. This page is the full reference for every field you can put in one.

<Note type="default" title="">

For the roles involved and how an option moves from the descriptor to a resolved value at runtime, see [General Concepts](/medusa-modules/integration/concepts).

</Note>

## defineIntegration

Create a descriptor with `defineIntegration`. It builds `optionsSchema` from your `options` catalog, used for `z.infer`, defaults, and full validation.

```ts title="providers/integration-my/services/my-integration.ts"
import { defineIntegration, AbstractIntegrationProviderService } from "@gorgo/medusa-integration"

const descriptor = defineIntegration({
  category: "payment",
  displayName: "my.name",
  options: {
    apiKey:  {
      type: "string",
      control: "secret",
      secret: true,
      required: true,
      label: "my.apiKey"
    },
    sandbox: {
      type: "boolean",
      control: "switch",
      default: false,
      label: "my.sandbox"
    },
  },
  sections: [
    {
      id: "credentials",
      title: "my.credentials",
      options: ["apiKey", "sandbox"]
    },
  ],
})

export class MyIntegration extends AbstractIntegrationProviderService {
  static identifier = "my"

  get descriptor() {
    return descriptor
  }
}
```

This descriptor declares `apiKey` and `sandbox`, grouped into a single `credentials` section. `defineIntegration` fails fast at load time in two cases: a section referencing an option id that isn't in `options`, and an `enum` option whose `values` mixes strings and numbers.

## Generated CRUD and Validation

The module generates the CRUD API from the descriptor and validates every write. Validation covers per-option rules, such as types, ranges, and patterns, along with cross-section rules that span the whole configuration. There is nothing to build for each integration.

See [Validate Integration Options](/medusa-modules/integration/validation) for when each rule runs and how to test the descriptor's rules, and [Admin API Routes](/medusa-modules/integration/admin-api) for the generated routes.

---

## Enabled and Complete

Options become live only when the integration is both enabled and complete, meaning it passes full validation. An incomplete draft or a disabled integration never resolves, so half-finished configuration cannot leak into runtime.

---

## Secrets and Encryption

Options marked `secret` are encrypted at rest with AES-256-GCM and never reach the browser. The CRUD API masks them and reports only whether each one is set. Saving a secret as blank keeps its stored value instead of clearing it.

Secret values don't reach the [change history](/medusa-modules/integration/change-history) either. For a secret option, the history shows only that its value was set, replaced, or removed. It keeps the values of every other option as they are.

<Note type="warning">

An option that holds a credential but isn't marked `secret: true` is shown in the Admin and kept in the change history in plain text. On startup, the module logs a warning for every option whose name looks like a credential but isn't marked `secret: true`. A name looks like a credential when it contains `password`, `passwd`, `secret`, `token`, `apiKey`, or `privateKey`, in any letter case.

</Note>

Encryption needs a key, set as `encryptionKey` when you register the module. See [Integration Module Options](/medusa-modules/integration/module-options#encryptionkey) for how to set it and what happens without one.

## Connection Test

A descriptor can declare an optional connection test that checks credentials against the third-party service. Store admins run it on demand, and a scheduled job re-tests every enabled integration once a day, at 03:00 by the server's clock.

Add `testConnection` to the descriptor. It receives the already-resolved (decrypted) options and returns a status:

```ts title="providers/integration-my/services/my-integration.ts"
const descriptor = defineIntegration({
  // ...
  testConnection: async ({ options }) => {
    const res = await fetch("https://api.my.com/ping", {
      headers: { Authorization: `Bearer ${options.apiKey}` },
    })

    if (!res.ok) {
      return { status: "failed", message: `My responded with ${res.status}` }
    }

    return { status: "passed" }
  },
})
```

`status` is one of `passed`, `failed`, or `skipped`, and the optional `message` is shown to the store admin in the Admin next to the test result. The module stores the status as the integration's `last_test_status` and emits the [`integration.tested` event](/medusa-modules/integration/events).

The test runs only against options that resolve. When the integration is disabled or incomplete, the module reports `failed` with the message `Not configured` without calling `testConnection`. When `testConnection` throws, the module reports `failed` with the error's message.

---

## Runtime Options Resolution

Consumers read typed, validated, and decrypted options, with descriptor defaults applied. An incomplete or disabled integration resolves to nothing rather than partial data. See [Reading Options](/medusa-modules/integration/reading-options) for the ways to read them and how long the module caches them.
