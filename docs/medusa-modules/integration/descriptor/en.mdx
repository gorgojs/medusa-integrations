# {frontmatter.title}

An integration provider's [descriptor](/medusa-modules/integration/concepts#descriptor) is where you declare the integration's options, how they group into settings sections, their validation, and an optional connection test. This page is the full reference for every field you can put in one.

<Note type="default" title="">

For the roles involved and how an option moves from the descriptor to a resolved value at runtime, see [General Concepts](/medusa-modules/integration/concepts).

</Note>

## defineIntegration

Create a descriptor with `defineIntegration`. It builds `optionsSchema` from your `options` catalog, used for `z.infer`, defaults, and full validation.

```ts title="providers/integration-my/services/my-integration.ts"
import { defineIntegration, AbstractIntegrationProviderService } from "@gorgo/medusa-integration"

const descriptor = defineIntegration({
  category: "payment",
  displayName: "my.name",
  options: {
    apiKey:  {
      type: "string",
      control: "secret",
      secret: true,
      required: true,
      label: "my.apiKey"
    },
    sandbox: {
      type: "boolean",
      control: "switch",
      default: false,
      label: "my.sandbox"
    },
  },
  sections: [
    {
      id: "credentials",
      title: "my.credentials",
      options: ["apiKey", "sandbox"]
    },
  ],
})

export class MyIntegration extends AbstractIntegrationProviderService {
  static identifier = "my"

  get descriptor() {
    return descriptor
  }
}
```

This descriptor declares `apiKey` and `sandbox`, grouped into a single `credentials` section. `defineIntegration` fails fast at load time in two cases: a section referencing an option id that isn't in `options`, and an `enum` option whose `values` mixes strings and numbers.

## Generated CRUD and Validation

The module generates the CRUD API from the descriptor and validates every write. Validation covers per-option rules, such as types, ranges, and patterns, along with cross-section rules that span the whole configuration. There is nothing to build for each integration.

Refer to [Validate Integration Options](/medusa-modules/integration/validation) to learn when each rule runs and how to test the descriptor's rules, and to [Admin API Routes](/medusa-modules/integration/admin-api) for the generated routes.

---

## Enabled and Complete

Options become live only when the integration is both enabled and complete, meaning it passes full validation. An incomplete draft or a disabled integration never resolves, so half-finished configuration cannot leak into runtime.

---

## Secrets and Encryption

Options marked `secret` are encrypted at rest with AES-256-GCM and never reach the browser. The CRUD API masks them and reports only whether each one is set. Saving a secret as blank keeps its stored value instead of clearing it.

<Note type="warning">

`secret: true` doesn't select the `secret` control. Without `control: "secret"`, the Admin renders the option as a plain text input, so the value the store admin types is visible, and the field doesn't say that leaving it blank keeps the stored value. When the option is also `required`, the Admin demands a value on every save of its section, so the store admin has to retype the stored secret each time. Set `control: "secret"` on every `secret: true` option.

</Note>

Secret values don't reach the [change history](/medusa-modules/integration/change-history) either. For a secret option, the history shows only that its value was set, replaced, or removed. It keeps the values of every other option as they are.

<Note type="warning">

An option that holds a credential but isn't marked `secret: true` is shown in the Admin and kept in the change history in plain text. On startup, the module logs a warning for every option whose name looks like a credential but isn't marked `secret: true`. The warning is logged once per provider identifier, even when the provider is registered more than once. A name looks like a credential when it contains `password`, `passwd`, `secret`, `token`, `apiKey`, or `privateKey`, in any letter case. `apiKey` and `privateKey` also match with an underscore or a hyphen between the words, such as `api_key` or `private-key`. The match is on part of the name, so `clientSecret` and `accessToken` count, while `publishableKey` and `terminalKey` don't.

</Note>

The module encrypts a secret value when it saves it, and decrypts it when it reads the integration. When you change an option's `secret` flag after a store admin has saved a value for it, the integration keeps working:

- When you add `secret: true`, the module reads the stored plain-text value as it is, so the consumer, the connection test, and the Admin keep working. The next save of any section of the integration stores the value encrypted, because a save encrypts the whole merged configuration again.
- When you remove `secret: true`, the module decrypts the stored value when it reads the integration. The consumer, the `values` that [`GET /admin/integrations/:provider_id`](/medusa-modules/integration/admin-api#the-integration-object) returns, and the `deleted` record in the change history get plain text, and the next save stores the value unencrypted. If the value doesn't decrypt, for example after a change of `encryptionKey`, the module returns the stored string as it is, without an error.

One case still fails. The module takes a stored string as encrypted when it starts with `v<digits>:`, or when it has the shape of a value encrypted by version 0.x of the module, which is standard base64 (`A-Z`, `a-z`, `0-9`, `+`, `/`, and `=` as padding) at least 40 characters long, with a length that's a multiple of 4 and at least 29 bytes once decoded. A plain-text value of that shape under an option you've just marked `secret: true` doesn't decrypt, and reading the integration throws the error described in [Integration Module Options](/medusa-modules/integration/module-options#encryptionkey). To recover, delete the stored settings with the [`DELETE /admin/integrations/:provider_id`](/medusa-modules/integration/admin-api#delete-the-settings) route, then enter them again. To stay clear of it, decide whether an option is secret before a store admin saves a value for it.

Encryption needs a key, set as `encryptionKey` when you register the module. Refer to [Integration Module Options](/medusa-modules/integration/module-options#encryptionkey) to learn how to set it and what happens without one.

## Connection Test

A descriptor can declare an optional connection test that checks credentials against the third-party service. Store admins run it on demand, and a scheduled job re-tests every enabled integration once a day, at 03:00 by the server's clock.

Add `testConnection` to the descriptor. It receives the already-resolved (decrypted) options and returns a status:

```ts title="providers/integration-my/services/my-integration.ts"
const descriptor = defineIntegration({
  // ...
  testConnection: async ({ options }) => {
    const res = await fetch("https://api.my.com/ping", {
      headers: { Authorization: `Bearer ${options.apiKey}` },
    })

    if (!res.ok) {
      return { status: "failed", message: `My responded with ${res.status}` }
    }

    return { status: "passed" }
  },
})
```

`status` is one of `passed`, `failed`, or `skipped`. The module stores the status as the integration's `last_test_status` and emits the [`integration.tested` event](/medusa-modules/integration/events). It doesn't store `message`, which only the event and the Admin notification carry.

When the status isn't `passed`, the Admin shows `message` in a notification, or the status itself when there is no message. A `passed` result shows a fixed success notification, whatever `message` holds.

The test runs only against options that resolve. When the integration isn't configured, is disabled, or is incomplete, the module reports `failed` with the message `Not configured` without calling `testConnection`. When `testConnection` throws, the module reports `failed` with the error's message. Refer to [Integration Module Workflows](/medusa-modules/integration/workflows#testintegrationconnectionworkflow) to learn every result the module produces itself, including an unknown provider and a descriptor without `testConnection`.

## Runtime Options Resolution

Consumers read typed, validated, and decrypted options, with descriptor defaults applied. An incomplete or disabled integration resolves to nothing rather than partial data. Refer to [Reading Options](/medusa-modules/integration/reading-options) to learn the ways to read them and how long the module caches them.

---

## Value Lists Across Versions

Several descriptor fields take their value from a fixed list. These are `category`, the `type` and `control` of an option, the `column` of a section, `preferredLayoutId`, and the `status` that `testConnection` returns. The lists change between versions of the module this way:

- A new value arrives in a minor release. A new category or connection test status also brings a migration, because the database checks the stored value against the list. Run `npx medusa db:migrate` after the upgrade to apply it.
- A value is removed or renamed only in a major release.

Code that branches on one of these values, such as a `switch` over `category`, needs a branch for a value it doesn't know. Then a minor release of the module doesn't break it.
