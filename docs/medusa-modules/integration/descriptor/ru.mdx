# {frontmatter.title}

В [дескрипторе](/medusa-modules/integration/concepts#дескриптор) провайдера интеграций вы объявляете параметры интеграции, их группировку по секциям настроек, валидацию и необязательную проверку соединения. На этой странице собран полный справочник по каждому полю, которое можно в нём указать.

<Note type="default" title="">

Роли участников и то, как параметр проходит путь от дескриптора до итогового значения во время выполнения, описаны в разделе [Основные концепции](/medusa-modules/integration/concepts).

</Note>

## defineIntegration

Создайте дескриптор через `defineIntegration`. Он собирает из каталога `options` схему `optionsSchema`, которая используется для `z.infer`, значений по умолчанию и полной валидации.

```ts title="providers/integration-my/services/my-integration.ts"
import { defineIntegration, AbstractIntegrationProviderService } from "@gorgo/medusa-integration"

const descriptor = defineIntegration({
  category: "payment",
  displayName: "my.name",
  options: {
    apiKey:  {
      type: "string",
      control: "secret",
      secret: true,
      required: true,
      label: "my.apiKey"
    },
    sandbox: {
      type: "boolean",
      control: "switch",
      default: false,
      label: "my.sandbox"
    },
  },
  sections: [
    {
      id: "credentials",
      title: "my.credentials",
      options: ["apiKey", "sandbox"]
    },
  ],
})

export class MyIntegration extends AbstractIntegrationProviderService {
  static identifier = "my"

  get descriptor() {
    return descriptor
  }
}
```

Этот дескриптор объявляет `apiKey` и `sandbox`, сгруппированные в одну секцию `credentials`. `defineIntegration` сразу выбрасывает ошибку при загрузке в двух случаях: если секция ссылается на id параметра, которого нет в `options`, и если `values` параметра типа `enum` смешивает строки и числа.

## Сгенерированный CRUD и валидация

Модуль генерирует CRUD API из дескриптора и валидирует каждую запись. Валидация покрывает правила на уровне отдельного параметра (типы, диапазоны, паттерны) вместе с правилами между секциями, охватывающими всю конфигурацию. Ничего писать под каждую интеграцию не нужно.

Когда срабатывает каждое правило и как тестировать правила дескриптора, читайте в руководстве [Валидация параметров интеграции](/medusa-modules/integration/validation), а сгенерированные роуты описаны в справочнике [API-роуты Admin](/medusa-modules/integration/admin-api).

## Включена и заполнена

Параметры становятся активными, только когда интеграция и включена, и заполнена, то есть проходит полную валидацию. Незавершённый черновик или выключенная интеграция никогда не отдают параметры, поэтому недоделанная конфигурация не может попасть в работающее приложение.

## Секреты и шифрование

Параметры с пометкой `secret` шифруются при хранении алгоритмом AES-256-GCM и никогда не попадают в браузер. CRUD API маскирует их и сообщает лишь, задано значение или нет. Сохранение секрета пустым оставляет прежнее хранимое значение, а не стирает его.

Значения секретных параметров не попадают и в [историю изменений](/medusa-modules/integration/change-history). Для них история показывает только, что значение задано, заменено или удалено. Значения остальных параметров она хранит как есть.

<Note type="warning">

Параметр с учётными данными без пометки `secret: true` показывается в Admin и хранится в истории изменений открытым текстом. При запуске модуль пишет в лог предупреждение о каждом параметре, название которого похоже на учётные данные, но не помечено `secret: true`. Похожим считается название, в котором без учёта регистра встречается `password`, `passwd`, `secret`, `token`, `apiKey` или `privateKey`.

</Note>

Для шифрования модулю нужен ключ, задайте его как `encryptionKey` при регистрации модуля. О том, как задать его и что происходит без него, смотрите в разделе [Параметры Модуля интеграций](/medusa-modules/integration/module-options#encryptionkey).

## Проверка соединения

Дескриптор может объявить необязательную проверку соединения, которая сверяет учётные данные со сторонним сервисом. Администраторы магазина запускают её по требованию, а запланированная задача раз в сутки, в 03:00 по часам сервера, заново проверяет каждую включённую интеграцию.

Добавьте `testConnection` в дескриптор. Он получает уже итоговые (расшифрованные) параметры и возвращает статус:

```ts title="providers/integration-my/services/my-integration.ts"
const descriptor = defineIntegration({
  // ...
  testConnection: async ({ options }) => {
    const res = await fetch("https://api.my.com/ping", {
      headers: { Authorization: `Bearer ${options.apiKey}` },
    })

    if (!res.ok) {
      return { status: "failed", message: `My responded with ${res.status}` }
    }

    return { status: "passed" }
  },
})
```

`status` принимает одно из значений `passed`, `failed` или `skipped`, а необязательное `message` Admin показывает администратору магазина рядом с результатом проверки. Модуль сохраняет статус в `last_test_status` интеграции и отправляет [событие `integration.tested`](/medusa-modules/integration/events).

Проверка выполняется только с параметрами, которые удалось получить. Если интеграция выключена или не завершена, модуль сообщает `failed` с текстом `Not configured` и `testConnection` не вызывает. Если `testConnection` выбрасывает исключение, модуль сообщает `failed` с текстом ошибки.

## Получение параметров во время выполнения

Потребители читают типизированные, проверенные и расшифрованные параметры с применёнными значениями по умолчанию из дескриптора. Незаполненная или выключенная интеграция возвращает пустой результат, а не частичные данные. Способы чтения параметров и то, как долго модуль их кэширует, описаны в руководстве [Чтение параметров](/medusa-modules/integration/reading-options).
