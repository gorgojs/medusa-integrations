# {frontmatter.title}

В этом документе вы узнаете, что такое провайдер Модуля интеграций, что нужно для его реализации, как модуль регистрирует его при старте приложения и как модель данных `Integration` представляет каждый зарегистрированный инстанс в базе данных.

## Что такое провайдер Модуля интеграций

Провайдер Модуля интеграций объявляет интеграцию: её параметры, их группировку в секции настроек и необязательную проверку соединения. Администратор магазина настраивает её в Admin, без правок `medusa-config` и без повторного развёртывания.

Модуль интеграций не зависит от типа провайдера, поэтому, в отличие от встроенных коммерческих модулей Medusa, он не поставляется с провайдером по умолчанию или провайдером-заглушкой. Провайдером Модуля интеграций может быть любой плагин, провайдер или собственный модуль. Полный список сценариев смотрите в разделе [Где можно применять Модуль интеграций](/medusa-modules/integration/concepts#где-можно-применять-модуль-интеграций).

Каждый провайдер, зарегистрированный в параметре `providers` Модуля интеграций, представлен в базе данных [моделью данных `Integration`](#модель-данных-integration).

---

## Создание собственного провайдера Модуля интеграций

Провайдер Модуля интеграций представляет собой модуль, чей сервис расширяет `AbstractIntegrationProviderService`, импортированный из `@gorgo/medusa-integration`. Как и у других провайдеров Medusa, один модуль может регистрировать несколько сервисов провайдера Модуля интеграций, каждый со своим `static identifier`, и каждый становится отдельным провайдером.

`AbstractIntegrationProviderService` объявляет следующие члены класса:

| Член класса | Описание |
| --- | --- |
| `static identifier: string` | Обязательное поле. Стабильный идентификатор провайдера, общий для всех его инстансов. |
| `get descriptor()` | Обязательное абстрактное свойство. Возвращает [дескриптор](/medusa-modules/integration/descriptor), созданный через `defineIntegration`: параметры, секции, валидацию и необязательную проверку соединения. |
| `static validateOptions(options)` | Необязательный метод. Fail-fast проверка конфигурации провайдера из `medusa-config.ts` при загрузке приложения. По умолчанию ничего не делает. |
| `getIdentifier()` | Реализован в базовом классе. Возвращает `static identifier` класса. |
| `getInstanceId()` | Реализован в базовом классе. Возвращает `id` регистрации этого инстанса, взятый из аргумента `instanceId` конструктора, или `null` для инстанса по умолчанию. |

Вот минимальная форма провайдера со всеми членами класса из таблицы выше, кроме тех, что уже реализует базовый класс:

```ts title="providers/integration-my/services/my-integration.ts"
import { AbstractIntegrationProviderService } from "@gorgo/medusa-integration"

class MyIntegrationProvider extends AbstractIntegrationProviderService {
  static identifier = "my"

  static validateOptions(options: Record<string, unknown>) {
    // необязательная fail-fast проверка
  }

  get descriptor() {
    return descriptor
  }
}

export default MyIntegrationProvider
```

`descriptor` здесь представляет собой результат `defineIntegration`. Все поля, которые он принимает, смотрите на странице [Дескриптор провайдера интеграций](/medusa-modules/integration/descriptor). `getIdentifier()` и `getInstanceId()` в примере не показаны, потому что `AbstractIntegrationProviderService` уже реализует оба метода. `getIdentifier()` возвращает `static identifier` класса, а `getInstanceId()` возвращает `instanceId`, который модуль передаёт третьим аргументом конструктора. Поэтому подкласс добавляет только `static identifier`, `descriptor` и, опционально, `static validateOptions`.

Если у подкласса есть собственный конструктор, он должен передать в `super` все три аргумента, `container`, `options` и `instanceId`. Иначе `getInstanceId()` вернёт `null`, даже для именованного инстанса.

<Note type="default" title="">

Прежнее имя `AbstractIntegrationProviderService` было `AbstractIntegrationProvider`. Пакет по-прежнему экспортирует его как устаревший алиас, сохранит во всех версиях 2.x и удалит в версии 3.0.

</Note>

<Note type="default" title="">

Полный пошаговый пример с кодом смотрите в разделе [Как создать провайдер Модуля интеграций](/medusa-modules/integration/create-integration-module-provider).

</Note>

## Регистрация провайдеров Модуля интеграций

### Настройка провайдеров Модуля интеграций

Модуль интеграций принимает параметр `providers`, в котором вы настраиваете провайдеры, зарегистрированные в вашем приложении, а также параметр `encryptionKey`, используемый для секретных полей модуля. Точную структуру `medusa-config.ts` смотрите в [шаге 4 руководства «Как создать провайдер Модуля интеграций»](/medusa-modules/integration/create-integration-module-provider#4-подключите-провайдер).

### Регистрация при старте приложения

При старте приложения Medusa Модуль интеграций регистрирует каждый провайдер из параметра `providers`. Сначала Medusa проверяет `static identifier` и `id` каждой записи. Затем модуль вызывает `static validateOptions` провайдера с `options` записи и объединяет `static identifier` класса с `id` записи в ключ `int_<identifier>[_<id>]`. Это тот же формат, что используется для `provider_id` этого инстанса в базе данных. Модуль регистрирует провайдер в своём контейнере под этим ключом, а контейнер создаёт инстанс через `new ProviderClass(container, options, instanceId)`.

Для каждой записи шаги идут в таком порядке:

```mermaid alt="Схема показывает, как запись providers в medusa-config.ts становится зарегистрированным инстансом из списка Настройки → Интеграции"
flowchart TD
  config["Запись providers в medusa-config.ts"] --> check["Medusa проверяет static identifier и id"]
  check --> validate["static validateOptions(options)"]
  validate --> key["Ключ int_<identifier><br/>или int_<identifier>_<id>"]
  key --> instance["Инстанс в контейнере модуля"]
  instance --> admin(["Инстанс в списке Настройки → Интеграции"])
```

Если проверка или `validateOptions` не проходит, приложение останавливается при старте, и неверная запись до ключа не доходит. Запись, прошедшая проверки, становится инстансом в контейнере модуля, а Admin показывает каждый зарегистрированный инстанс, настроенный или нет, в разделе **Настройки → Интеграции**.

Зарегистрировав все провайдеры, модуль пишет в лог предупреждение о каждом параметре, название которого похоже на учётные данные, но который не помечен `secret: true`. Как модуль обращается с секретами, описано на странице [Дескриптор провайдера интеграций](/medusa-modules/integration/descriptor#секреты-и-шифрование).

### Ошибки регистрации

Medusa останавливает приложение при старте, если запись в `providers` нарушает одно из этих правил, и ошибка называет проблему:

- У двух записей одинаковые идентификатор и `id`, в том числе у двух записей без `id`. В этом случае Medusa выводит ошибку `Module provider my has already been registered. Please provide a different "id" in the provider options.`, где вместо `my` стоит идентификатор.
- У класса сервиса нет `static identifier`. В этом случае Medusa выводит ошибку `Module provider <name> does not have a static "identifier" property on its service class.`, где `<name>` берётся из `DISPLAY_NAME` сервиса или, если его нет, из пути к модулю провайдера.
- Экспорт по умолчанию модуля провайдера не содержит ни одного сервиса. В этом случае Medusa выводит ошибку `<resolve> doesn't seem to have a main service exported -- make sure your module has a default export of a service.`, где `<resolve>` это значение `resolve` записи.

Чтобы избежать первой ошибки, задайте каждому инстансу провайдера собственный `id`. Как `id` образует ключ, описано на странице [Основные концепции](/medusa-modules/integration/concepts#несколько-инстансов).

### Модель данных `Integration`

Инстанс зарегистрированного провайдера Модуля интеграций представлен в приложении Medusa моделью данных `Integration`.

<Note type="warning">

Собственный `id` модели служит лишь её внутренним идентификатором записи, таким же, как у любой другой модели данных Medusa. Это не то же самое, что `provider_id`, поле, которое хранит ключ `int_<identifier>[_<id>]` из раздела [Инстансы и их идентификаторы](/medusa-modules/integration/concepts#инстансы-и-их-идентификаторы).

</Note>

Запись хранит `provider_id` инстанса, его `category`, настройки администратора магазина в `options` с зашифрованными секретными параметрами, флаг `is_enabled` и результат последней проверки соединения. Модуль создаёт запись при первом сохранении любой секции, поэтому зарегистрированный провайдер без записи показывается в Admin как **Не настроено**. Все свойства модели перечислены в справочнике [Модели данных Модуля интеграций](/medusa-modules/integration/data-models#integration).

История изменений инстанса хранится в отдельной модели данных `IntegrationChange`, которая не связана с `Integration` и переживает её. Подробнее на странице [История изменений настроек](/medusa-modules/integration/change-history).

### Удаление провайдера Модуля интеграций

Вы можете удалить зарегистрированный провайдер Модуля интеграций, удалив его запись из параметра `providers` в `medusa-config.ts`. В отличие от отключения интеграции из Admin, это не затрагивает сохранённую запись. Провайдер перестаёт регистрироваться, поэтому модуль больше не может найти его запись `Integration` по `provider_id`. Интеграция исчезает из списка в Admin, а её сохранённые данные становятся недоступны через собственные admin-роуты Модуля интеграций. Её записи остаются в истории изменений всех интеграций.

<Note type="warning">

Удалите интеграцию из Admin, прежде чем убирать провайдер из `medusa-config.ts`, а не наоборот. Как только провайдер исчезает из конфигурации, его запись `Integration` становится недостижима, в том числе через сам роут удаления, и остаётся в базе данных без возможности удалить её из Admin. Обычный порядок удаления описан в разделе [Удаление интеграции](/medusa-modules/integration/manage-integrations#удаление-интеграции).

</Note>

То же происходит, если изменить `id` записи или `static identifier` класса, потому что меняется ключ `int_<identifier>[_<id>]`. У нового ключа нет сохранённой записи `Integration`, поэтому инстанс показывается как **Не настроено**, а настройки остаются в базе данных под старым ключом, недоступные из Admin. Есть два выхода:

- Верните старую запись, удалите интеграцию из Admin и только потом уберите запись или замените её `id` на новый.
- Запустите `deleteIntegrationWorkflow` из своего кода, передав старый ключ как `provider_id`. Ему не нужно, чтобы провайдер был зарегистрирован, поэтому он удалит настройки, хранящиеся под этим ключом, а интеграцию можно будет настроить заново под новым.

Входные данные воркфлоу и путь импорта описаны на странице [Воркфлоу Модуля интеграций](/medusa-modules/integration/workflows#deleteintegrationworkflow).

Чтобы временно прекратить использование провайдера, сохранив его настройки и возможность быстро вернуть его обратно, отключите интеграцию из Admin вместо удаления провайдера из `medusa-config.ts`. Как это сделать, описано на странице [Управление интеграциями в Medusa Admin](/medusa-modules/integration/manage-integrations#включение-и-отключение-интеграции).
