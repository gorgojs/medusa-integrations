# {frontmatter.title}

В этой главе вы узнаете о Модуле интеграций и о том, как его использовать.

## Где можно применять Модуль интеграций

Модуль интеграций можно применять в самых разных сценариях. Он не зависит от типа провайдера, и ему всё равно, для чего нужны параметры.

- **Любой тип провайдера:** Платежи, доставка, уведомления, аналитика, авторизация и другие.
- **Плагины:** Добавляйте плагину настраиваемые параметры, не разрабатывая UI и слой данных.
- **Собственные модули и расширения:** Любой модуль Medusa, которому нужны настраиваемые параметры в Admin, например API-ключи, режимы или feature-флаги.

Если администратор магазина должен уметь управлять настройкой, её можно сделать через Модуль интеграций.

---

## Провайдеры и потребители

В интеграции участвуют две роли разработчика, а между ними находится администратор магазина.

- **Провайдер интеграций:** Объявляет интеграцию. Описывает параметры, их группировку и валидацию, а также необязательную проверку соединения. Провайдером интеграций может быть любой плагин, провайдер или собственный модуль, и всё это он объявляет в одном [дескрипторе](#дескриптор).
- **Администратор магазина:** Настраивает в Admin эти параметры, например учётные данные, режимы или вебхуки.
- **Потребитель:** Читает параметры [инстанса](#инстансы-и-их-идентификаторы) интеграции во время выполнения.

Провайдер и потребитель обычно живут в одном пакете. Платёжный плагин объявляет свои учётные данные, затем считывает их обратно в своей платёжной логике. Потребителем может быть и посторонний код, например API-роут, подписчик или запланированная задача, которым нужны параметры настроенной интеграции.

## Дескриптор

Дескриптор представляет собой единое объявление метаданных интеграции, её параметров, секций настроек, валидации и необязательной проверки соединения. Создаётся он через `defineIntegration`.

Вот дескриптор платёжного провайдера с двумя параметрами и одной секцией:

```ts title="providers/integration-my/services/my-integration.ts"
import { defineIntegration, AbstractIntegrationProviderService } from "@gorgo/medusa-integration"

const descriptor = defineIntegration({
  category: "payment",
  displayName: "my.name",
  options: {
    apiKey:  {
      type: "string",
      control: "secret",
      secret: true,
      required: true,
      label: "my.apiKey"
    },
    sandbox: {
      type: "boolean",
      control: "switch",
      default: false,
      label: "my.sandbox"
    },
  },
  sections: [
    {
      id: "credentials",
      title: "my.credentials",
      options: ["apiKey", "sandbox"]
    },
  ],
})

export class MyIntegration extends AbstractIntegrationProviderService {
  static identifier = "my"

  get descriptor() {
    return descriptor
  }
}
```

Дескриптор служит единым источником истины для интеграции: в этом примере он объявляет `apiKey` и `sandbox`, сгруппированные в одну секцию `credentials`. По нему модуль генерирует CRUD API, валидирует запись, отрисовывает UI настроек и определяет, что потребители получают во время выполнения. Вам не нужно писать ни модели данных, ни API-роуты, ни UI-формы.

Полный справочник по каждому полю параметра, по типу, а также по валидации, секретам и проверке соединения смотрите в разделе [Дескриптор провайдера интеграций](/medusa-modules/integration/descriptor).

## Инстансы и их идентификаторы

Инстанс представляет собой отдельную регистрацию провайдера интеграций с собственной конфигурацией. Один и тот же провайдер можно зарегистрировать несколько раз, и каждая регистрация даёт самостоятельный инстанс со своими настройками в Admin.

Каждый инстанс интеграции адресуется по `provider_id` вида:

```
int_<identifier>[_<instanceId>]
```

В `<identifier>` подставляется `static identifier` провайдера, общий для всех его инстансов. `<instanceId>` берётся из `id` конкретной регистрации и присутствует только у именованных инстансов.

У каждой интеграции есть стабильный идентификатор, например `my`, заданный как `static identifier` в провайдере:

```ts title="providers/integration-my/services/my-integration.ts"
import { defineIntegration, AbstractIntegrationProviderService } from "@gorgo/medusa-integration"

// ...

export class MyIntegration extends AbstractIntegrationProviderService {
  static identifier = "my"

  // ...
}
```

Все инстансы провайдера используют общий `static identifier`. Он всегда `my`. Различает инстансы только `instanceId` в `provider_id`.

### Один инстанс

Это вариант по умолчанию. У него нет ID инстанса (`instanceId`), поэтому его `provider_id` выглядит, например, как `int_my`.

Зарегистрируйте его без `id`:

```ts title="medusa-config.ts"
module.exports = defineConfig({
  // ...
  plugins: [
    {
      resolve: "@gorgo/medusa-integration",
      options: {
        // ...
        providers: [
          {
            resolve: "@gorgo/medusa-payment-my/providers/integration-my",
            options: {},
          },
        ],
      },
    },
  ],
})
```

Без `id` в записи регистрации провайдер получает единственный, безымянный инстанс с ключом `int_my`.

### Несколько инстансов

Зарегистрируйте один и тот же провайдер несколько раз, каждый со своим `id`. Каждый инстанс настраивается независимо, например для поддержки нескольких аккаунтов интегрируемого сервиса.

Например, две независимые регистрации одного и того же провайдера:

```ts title="medusa-config.ts"
module.exports = defineConfig({
  // ...
  plugins: [
    {
      resolve: "@gorgo/medusa-integration",
      options: {
        // ...
        providers: [
          {
            resolve: "@gorgo/medusa-payment-my/providers/integration-my",
            id: "eu",
            options: {},
          },
          {
            resolve: "@gorgo/medusa-payment-my/providers/integration-my",
            id: "us",
            options: {},
          },
        ],
      },
    },
  ],
})
```

Это даст `int_my_eu` и `int_my_us` соответственно. `id` задаётся на верхнем уровне записи. Если случайно поместить его внутрь `options`, провайдер зарегистрируется под инстансом по умолчанию (безымянным) без предупреждения.

Потребитель получает параметры по идентификатору и инстансу, поэтому один и тот же код может обращаться к нужному.

## Параметры интеграции

Параметры интеграции движутся по предсказуемому пути. Автор объявляет их в дескрипторе, администратор настраивает, модуль валидирует, они становятся активными, как только интеграция включена и заполнена, а потребитель получает их во время выполнения. По пути проверка соединения может сверить их со сторонним сервисом.

Полный справочник по каждому полю параметра, по типу, а также по секретам и проверке соединения смотрите в разделе [Дескриптор провайдера интеграций](/medusa-modules/integration/descriptor). Какие правила срабатывают при сохранении секции, а какие перед тем, как параметры станут активными, объясняет руководство [Валидация параметров интеграции](/medusa-modules/integration/validation), а сторону потребителя описывает [Чтение параметров](/medusa-modules/integration/reading-options).

## Генерация UI

Модуль генерирует UI интеграции из её дескриптора, поэтому строить страницы не нужно.

### Секции

Параметры группируются в секции настроек и отрисовываются через [LayoutComposer](https://docs.medusajs.com/resources/admin-components/components/layout-composer) Medusa в виде карточек с изменяемым порядком, в одну или две колонки.

### Собственные секции

Когда сгенерированного UI недостаточно, вы можете построить для своих параметров любой интерфейс на собственных admin-виджетах. Это обычные admin-виджеты Medusa на `defineWidgetConfig`. Модуль предоставляет зону внедрения для каждой колонки страницы интеграции, `gorgo.integration.<identifier>` и `gorgo.integration.<identifier>.side`. Виджет в такой зоне стоит рядом со сгенерированными секциями и получает `providerId` инстанса и его несекретные значения.

Как построить такой виджет, читайте в руководстве [Собственные секции на виджетах](/medusa-modules/integration/custom-sections), а сами зоны описаны в справочнике [Зоны виджетов в Admin](/medusa-modules/integration/admin-widget-zones).

### Локализация

Метки, подсказки и заголовки в дескрипторе задаются как i18n-ключи. Поставляйте переводы вместе со своей интеграцией, и UI настроек локализуется автоматически. Всё это построено на стандартном i18n Admin в Medusa, а собственные виджеты локализуются так же и с теми же переводами, что и сгенерированная форма.

Где находятся переводы и что показывается, если ключа нет, читайте в руководстве [Локализация интеграции](/medusa-modules/integration/localization).

## История изменений

Модуль записывает каждое изменение настроек интеграции вместе с автором, временем и изменёнными полями. Значения секретов в историю не попадают, а сама история переживает интеграцию, которую описывает. Администраторы магазина смотрят её в Medusa Admin, а ваш код может получить её через Admin API или сервис модуля.

Что именно записывается и как подписать изменения из вашего кода правильным автором, читайте на странице [История изменений настроек](/medusa-modules/integration/change-history).
