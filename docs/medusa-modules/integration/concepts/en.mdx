# {frontmatter.title}

In this document, you'll learn about the roles involved in an integration, the descriptor at its center, and how an integration's options flow from configuration to runtime and into the UI. Later pages turn each idea into a step-by-step guide.

## Where It Can Be Used

The Integration Module is provider-agnostic. It does not care what the options are for.

- **Any provider type:** payment, fulfillment, ERP, notification, content, and more.
- **Plugins:** add configurable settings to a plugin without building a settings page and a data layer.
- **Custom modules and admin customizations:** any Medusa module that needs admin-configurable options, such as API keys, modes, or feature flags.

If a store admin should be able to manage a setting, it can be an integration.

---

## Providers and Consumers

An integration involves two developer roles, with the store admin between them.

- **Integration provider:** Declares an integration. It defines the options, how they are grouped and validated, and an optional connection test. Any plugin, provider, or custom module can be an integration provider, and it declares all of this in a single [descriptor](#descriptor).
- **Store admin:** Configures those options in the Admin, such as credentials, modes, or webhooks. There are no `medusa-config` edits and no redeploys.
- **Consumer:** Reads the resolved options at runtime.

All three roles meet in the Integration Module:

```mermaid alt="Diagram showcasing how the integration provider declares the descriptor, the store admin configures the options, and the consumer reads the resolved options from the Integration Module"
flowchart TD
  provider["Integration provider"] -->|"declares the descriptor"| module["Integration Module"]
  admin(["Store admin"]) -->|"configures the options"| module
  module -->|"resolved options"| consumer["Consumer"]
```

The provider declares the options once, the store admin sets their values whenever needed, and the consumer reads the resolved options, which are the saved values decrypted and with defaults applied.

The provider and the consumer are usually the same package. A payment plugin declares its credentials as an integration, then reads them back in its payment logic. A consumer can also be unrelated code, such as an API route, a subscriber, or a scheduled job, that needs a configured integration's options.

## Descriptor

A descriptor is a single declaration of an integration's metadata, options, settings sections, validation, and an optional connection test. You create it with `defineIntegration`.

Here's a payment provider's descriptor, declaring two options and one section:

```ts title="providers/integration-my/services/my-integration.ts"
import { defineIntegration, AbstractIntegrationProviderService } from "@gorgo/medusa-integration"

const descriptor = defineIntegration({
  category: "payment",
  displayName: "my.name",
  options: {
    apiKey:  {
      type: "string",
      control: "secret",
      secret: true,
      required: true,
      label: "my.apiKey"
    },
    sandbox: {
      type: "boolean",
      control: "switch",
      default: false,
      label: "my.sandbox"
    },
  },
  sections: [
    {
      id: "credentials",
      title: "my.credentials",
      options: ["apiKey", "sandbox"]
    },
  ],
})

class MyIntegrationProvider extends AbstractIntegrationProviderService {
  static identifier = "my"

  get descriptor() {
    return descriptor
  }
}

export default MyIntegrationProvider
```

The descriptor is the source of truth for the integration: this one declares `apiKey` and `sandbox`, grouped into a single `credentials` section. The module uses it to generate the CRUD API, validate writes, render the settings UI, and define what consumers resolve at runtime. You never write data models, routes, or forms.

Refer to [Integration Provider Descriptor](/medusa-modules/integration/descriptor) for the full reference of every option field, by type, along with validation, secrets, and the connection test.

## Identifiers and Instances

An instance is one registration of an integration provider, with its own configuration. You can register the same provider more than once; each registration becomes an independent instance with its own settings in the Admin.

Every integration instance is addressed by a `provider_id` of the form:

```
int_<identifier>[_<instanceId>]
```

`<identifier>` is the provider's `static identifier`, shared by every one of its instances. `<instanceId>` is that particular registration's `id`, present only for named instances.

Every integration has a stable identifier, such as `my`, set as the provider's `static identifier`:

```ts title="providers/integration-my/services/my-integration.ts"
import { defineIntegration, AbstractIntegrationProviderService } from "@gorgo/medusa-integration"

// ...

class MyIntegrationProvider extends AbstractIntegrationProviderService {
  static identifier = "my"

  // ...
}

export default MyIntegrationProvider
```

Every instance of the provider shares this `static identifier`. It's always `my`. Only the `instanceId` in the `provider_id` tells the instances apart.

Next to an integration's name, Medusa Admin shows the ID Medusa knows the provider by. For the payment category it swaps `int_` for `pp_`, for fulfillment it swaps it for `fp_`, and for every other category it shows the `int_…` key as it is.

### Single Instance

This is the default. It has no instance id (`instanceId`), so its `provider_id` looks like `int_my`.

Register it without an `id`:

```ts title="medusa-config.ts"
module.exports = defineConfig({
  // ...
  plugins: [
    {
      resolve: "@gorgo/medusa-integration",
      options: {
        // ...
        providers: [
          {
            resolve: "@gorgo/medusa-payment-my/providers/integration-my",
            options: {},
          },
        ],
      },
    },
  ],
})
```

Without an `id` in the registration entry, the provider gets the single, unnamed instance keyed `int_my`.

### Multiple Instances

Register the same provider more than once, each with its own `id`. Each instance is configured independently, which is how you support several accounts on the integrated service.

For example, two independent registrations of the same provider:

```ts title="medusa-config.ts"
module.exports = defineConfig({
  // ...
  plugins: [
    {
      resolve: "@gorgo/medusa-integration",
      options: {
        // ...
        providers: [
          {
            resolve: "@gorgo/medusa-payment-my/providers/integration-my",
            id: "eu",
            options: {},
          },
          {
            resolve: "@gorgo/medusa-payment-my/providers/integration-my",
            id: "us",
            options: {},
          },
        ],
      },
    },
  ],
})
```

That gives `int_my_eu` and `int_my_us` respectively. `id` goes at the top level of the entry, not inside `options`. Putting it inside `options` instead makes the provider silently register under the default (unnamed) instance.

A consumer resolves options by identifier and instance, so the same code can target the right one.

<Note type="warning">

The identifier and the `id` can both contain `_`, so two registrations can end up with the same key. The identifier `my` with the `id` `eu`, and the identifier `my_eu` without an `id`, both give `int_my_eu`. Registering both stops the application at startup, and [Integration Module Provider](/medusa-modules/integration/integration-module-provider#registration-errors) lists the error. Pick identifiers that can't collide.

</Note>

### Building and Parsing a `provider_id`

When your own code receives a `provider_id`, for example on a route of your plugin, use the two helpers the package exports instead of splitting the string yourself:

```ts
import {
  integrationProviderKey,
  parseIntegrationProviderKey,
} from "@gorgo/medusa-integration"

integrationProviderKey("my") // "int_my"
integrationProviderKey("my", "eu") // "int_my_eu"

parseIntegrationProviderKey("int_my_eu", "my") // { identifier: "my", instanceId: "eu" }
parseIntegrationProviderKey("int_my", "my") // { identifier: "my", instanceId: null }
parseIntegrationProviderKey("int_other", "my") // null
```

`integrationProviderKey(identifier, instanceId?)` builds the key, and `parseIntegrationProviderKey(providerId, identifier)` reverses it. The parser takes the identifier you expect because `_` can appear in both parts, so the key alone doesn't say where one ends. It returns `{ identifier, instanceId }`, with `instanceId` set to `null` for the single instance, and returns `null` when the key doesn't belong to that identifier.

## Integration Options

An integration's options move through a predictable path. An author declares them in the descriptor, an admin configures them, the module validates them, they become live once the integration is enabled and complete, and a consumer resolves them at runtime. A connection test can check them against the third-party service along the way.

When a store admin saves a section in Medusa Admin, the request reaches `upsertIntegrationWorkflow` through the API route, and the workflow validates the values, encrypts the secrets, stores them, and records the change:

```mermaid alt="Diagram showcasing how a section saved in Medusa Admin passes through the API route and upsertIntegrationWorkflow to the database and back"
sequenceDiagram
  participant admin as Admin
  participant route as API route
  participant wf as upsertIntegrationWorkflow
  participant svc as Module service
  participant db as Database
  admin->>route: { section_id, values }
  route->>wf: values, actor
  wf->>svc: get descriptor, stored values
  wf->>wf: validate values
  wf->>svc: encrypt secrets
  wf->>svc: upsert integration
  svc->>db: write row
  wf->>svc: record change
  svc->>db: write history
  wf-->>svc: integration.updated clears cache
  wf-->>route: saved record
  route-->>admin: no secrets
```

The workflow validates only the submitted values against the descriptor, so a failed check stops it before anything is written. It then writes the settings and the history record through the module's service, and the `integration.updated` event clears the cached options of that instance. The response is the stored record without its secrets, so the Admin learns only which secret options have a value. Refer to [Reading Options](/medusa-modules/integration/reading-options#caching-and-freshness) to learn when a consumer picks up the change.

Refer to [Integration Provider Descriptor](/medusa-modules/integration/descriptor) for the full reference of every option field, by type, along with secrets and the connection test. [Validate Integration Options](/medusa-modules/integration/validation) explains which rules run when a section is saved and which run before the options go live, and [Reading Options](/medusa-modules/integration/reading-options) covers the consumer's side.

## UI Generation

The module generates the UI for an integration from its descriptor, so there are no pages to build.

### Sections

Options are grouped into settings sections and rendered with Medusa's [LayoutComposer](https://docs.medusajs.com/resources/admin-components/components/layout-composer) as reorderable cards, in a single- or two-column layout. Refer to [Integration Provider Descriptor](/medusa-modules/integration/descriptor#sections) for the fields of a section.

### Custom Sections

When the generated UI is not enough, you can build any UI for your options with custom admin widgets. These are standard Medusa admin widgets built with `defineWidgetConfig`. The module exposes an injection zone for each column of an integration's page, `gorgo.integration.<identifier>` and `gorgo.integration.<identifier>.side`. A widget in one of them sits next to the generated sections and receives the instance's `providerId` and its non-secret values.

Refer to [Custom Sections with Widgets](/medusa-modules/integration/custom-sections) to learn how to build one, and [Admin Widget Injection Zones](/medusa-modules/integration/admin-widget-zones) for the zones themselves.

### Localization

Descriptor labels, hints, and titles are i18n keys. Ship translations with your integration and the settings UI is localized automatically. This builds on Medusa's standard admin i18n, and custom widgets localize the same way, with the same translations as the generated form.

Refer to [Localize an Integration](/medusa-modules/integration/localization) for where translations go and how a missing key falls back.

---

## Change History

The module records every change to an integration's settings, with its author, time, and the fields it changed. Secret values never reach the history, and the history outlives the integration it describes. Store admins browse it in Medusa Admin, and your code can read it through the Admin API or the module's service.

Refer to [Settings Change History](/medusa-modules/integration/change-history) for what gets recorded and how to attribute your own code's changes to the right author.
