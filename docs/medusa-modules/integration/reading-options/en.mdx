# {frontmatter.title}

In this guide, you'll learn how to read an integration's options at runtime, after a store admin configures it. The code that reads them is the consumer. It's often the same package that declared the integration, such as a payment provider reading its own credentials, but it can be any other code, like an API route, a subscriber, or a scheduled job.

<Note type="default" title="">

What you get back is resolved, which means the module has decrypted and validated the options and applied their defaults. Refer to [What Resolved Means](#what-resolved-means) for the details.

</Note>

## Two Ways to Read

The API you use depends on where your code runs.

| Where your code runs | How to read |
| --- | --- |
| A provider in an isolated module container, or a module service | [`resolveIntegrationOptions`](#the-resolveintegrationoptions-helper) |
| Code with the app or request container (API routes, subscribers, scheduled jobs, workflow steps) | [`getResolvedOptions`](#the-getresolvedoptions-service-method) |
| A step inside a workflow you compose | [`getResolvedIntegrationOptionsStep`](#resolving-inside-a-workflow) |

A payment or fulfillment provider runs inside its own module's isolated container, so it cannot resolve the Integration Module directly. It uses `resolveIntegrationOptions`, which runs a workflow to reach the Integration Module. Code that already holds the container resolves the module and calls `getResolvedOptions` directly, without a workflow.

---

## The `resolveIntegrationOptions` Helper

Use the helper from a provider that cannot reach the Integration Module directly.

### Basic Usage

Pass the identifier your integration declares, and a type parameter for typed options. For example:

```ts title="providers/payment-my/services/my-payment.ts"
import { resolveIntegrationOptions } from "@gorgo/medusa-integration"
import type { MyOptions } from "../../integration-my/services/my-integration"

// inside any provider method
const options = await resolveIntegrationOptions<MyOptions>({
  identifier: "my"
})
```

The returned `options` is typed as `MyOptions`, already decrypted and validated.

<Note type="default" title="">

The helper runs a workflow, and a workflow run without a container of its own gets the modules loaded at that moment. Medusa builds that list once and reuses it for every later run in the process, and not every module has loaded while the application starts. Don't call `resolveIntegrationOptions` in a provider's constructor or in `static validateOptions`. Call it from the methods that run later.

</Note>

### Targeting a Specific Instance

For a provider that supports [multiple instances](/medusa-modules/integration/concepts#identifiers-and-instances), pass `instance_id`. Omit it, or pass `null`, for the default instance.

Medusa constructs a payment or fulfillment provider with the module's container and its own `options` only, so the provider doesn't receive the Integration Module's instance id from Medusa. You pair the two registrations yourself. Give the integration provider an `id`, and pass the same value in the `options` of the consumer provider in `medusa-config.ts`:

```ts title="medusa-config.ts"
const MY_INTEGRATION_ID = "my-1"

module.exports = defineConfig({
  // ...
  plugins: [
    {
      resolve: "@gorgo/medusa-integration",
      options: {
        providers: [
          {
            resolve: "@gorgo/medusa-payment-my/providers/integration-my",
            id: MY_INTEGRATION_ID,
            options: {},
          },
        ],
      },
    },
  ],
  modules: [
    {
      resolve: "@medusajs/medusa/payment",
      options: {
        providers: [
          {
            resolve: "@gorgo/medusa-payment-my/providers/payment-my",
            id: "my",
            options: {
              // must match the id of the integration provider above
              id: MY_INTEGRATION_ID,
            },
          },
        ],
      },
    },
  ],
})
```

The `id` inside the consumer provider's `options` is the Integration Module instance id. It is separate from the `id` on the payment provider's own entry, which Medusa uses for the payment provider's key.

Store the instance id in the constructor of a base class for the consumer provider, and pass it as `instance_id` on every call:

```ts title="providers/payment-my/core/my-base.ts"
import { AbstractPaymentProvider } from "@medusajs/framework/utils"
import { resolveIntegrationOptions } from "@gorgo/medusa-integration"
import type { MyOptions } from "../../integration-my/services/my-integration"

type MyPaymentOptions = {
  id?: string
}

export abstract class MyPaymentBase extends AbstractPaymentProvider<MyPaymentOptions> {
  protected instanceId_: string | null

  constructor(container: Record<string, unknown>, options: MyPaymentOptions) {
    super(container, options)
    this.instanceId_ = options.id ?? null
  }

  protected async resolveOptions(): Promise<MyOptions> {
    return resolveIntegrationOptions<MyOptions>({
      identifier: "my",
      instance_id: this.instanceId_,
    })
  }
}
```

`instanceId_` is a property of this base class that the constructor sets from `options.id`, not something Medusa's `AbstractPaymentProvider` provides. It stays `null` when `options.id` is not set, which resolves the default instance. Your payment provider extends this class, as the YooKassa provider extends its own base class, and calls `this.resolveOptions()` from its methods. Refer to [Migrate an Existing Medusa Provider to the Integration Module](/medusa-modules/integration/migrate-provider-to-integration-module) to learn how the same pattern works in a fulfillment provider.

### When It Isn't Configured

By default, the helper throws a `MedusaError` when the integration is not configured, disabled, or incomplete:

```ts
// throws if the integration isn't usable yet
const options = await resolveIntegrationOptions<MyOptions>({
  identifier: "my"
})
```

Pass `{ optional: true }` to receive `null` instead, so you can handle the missing case yourself:

```ts
const options = await resolveIntegrationOptions<MyOptions>(
  { identifier: "my" },
  { optional: true }
)

if (!options) {
  // not configured yet: skip, fall back, or return a friendly error
}
```

With `{ optional: true }`, a missing, disabled, or incomplete integration resolves to `null` here instead of throwing, which is what the `if (!options)` check above is guarding against.

<Note type="default" title="">

`{ optional: true }` covers an integration that isn't set up yet, not one that isn't registered. When no provider is registered under the identifier and instance you pass, the helper throws in either case, since that points to a mistake in `medusa-config.ts`, such as a wrong `id`.

</Note>

## The `getResolvedOptions` Service Method

When your code already has the container, resolve the module and call `getResolvedOptions` directly. This suits API routes, subscribers, scheduled jobs, and workflow steps, and no workflow is involved. For example, in an API route:

```ts title="api/admin/my-payment/route.ts"
import { INTEGRATION_MODULE, IntegrationModuleService } from "@gorgo/medusa-integration"
import type { MedusaRequest, MedusaResponse } from "@medusajs/framework/http"
import type { MyOptions } from "../../../providers/integration-my/services/my-integration"

export async function GET(req: MedusaRequest, res: MedusaResponse) {
  const integration: IntegrationModuleService = req.scope.resolve(INTEGRATION_MODULE)

  const resolved = await integration.getResolvedOptions("my")
  if (!resolved) {
    return res.status(503).send("My is not configured")
  }

  const options = resolved.options as MyOptions
  const { provider_id, category, is_enabled } = resolved.meta
}
```

`getResolvedOptions(identifier, instanceId?)` returns `ResolvedOptions | null`. A value is `{ options, meta }`, where `meta` holds `provider_id`, `category`, and `is_enabled`. A `null` result means the integration is not configured, disabled, or incomplete. When no provider is registered under that identifier and instance, the method throws instead. Refer to [Integration Module Service](/medusa-modules/integration/service) for the module's other methods.

## Resolving Inside a Workflow

When you compose your own workflow, use the exported step instead of the helper:

```ts title="workflows/create-my.ts"
import { createWorkflow, WorkflowResponse } from "@medusajs/framework/workflows-sdk"
import { getResolvedIntegrationOptionsStep } from "@gorgo/medusa-integration"

export const createMyWorkflow = createWorkflow("create-my", () => {
  const resolved = getResolvedIntegrationOptionsStep({
    identifier: "my"
  })
  return new WorkflowResponse(resolved)
})
```

The step takes `{ identifier, instance_id? }` and returns `{ options, meta } | null`. Unlike the `resolveIntegrationOptions` helper, it returns `null` for an integration that is not configured, disabled, or incomplete instead of throwing, so check for `null` in the steps that use the result. When no provider is registered under that identifier and instance, the step throws, as `getResolvedOptions` does.

The standalone `getResolvedIntegrationOptionsWorkflow` is also exported. It is what the helper runs internally.

## What Resolved Means

Resolved options are not the raw stored values. When the module builds them, it does three things:

- decrypts secret fields,
- confirms the integration is enabled and complete, meaning it passes full validation,
- applies descriptor defaults for options the admin never set.

If the integration is not configured, disabled, or incomplete, it resolves to `null`. The helper throws in that case, or returns `null` with `{ optional: true }`. Partial drafts never reach runtime.

The diagram follows one call of `resolveIntegrationOptions` from your provider to the database and back:

```mermaid alt="Diagram showcasing how one resolveIntegrationOptions call reaches the cache and the database, and what comes back"
sequenceDiagram
  participant provider as Provider
  participant helper as resolveIntegrationOptions
  participant service as Service
  participant cache as Cache
  participant db as Database
  provider->>helper: identifier, instance_id
  helper->>service: getResolvedOptions
  service->>cache: look up the key
  alt cache hit
    cache-->>service: value, or null
  else cache miss
    service->>db: read the record
    db-->>service: record
    opt record is enabled
      service->>service: decrypt, validate, add defaults
    end
    service->>cache: store for 60 s, null too
  end
  service-->>helper: options and meta, or null
  helper-->>provider: options, or an error for null
```

The service looks the integration up by the key `int_<identifier>[_<instanceId>]`. A cache hit returns at once, and the cached value may be `null`. On a miss the service reads the record. Only a record that is enabled is decrypted, validated in full, and given its defaults, and a record that is missing, disabled, or incomplete gives `null`. The service caches the result for 60 seconds, `null` included, and the helper turns `null` into an error unless you pass `{ optional: true }`. The diagram leaves out one check, which throws before the service reads the record when no provider is registered under the key.

## Caching and Freshness

Resolved options are cached in the memory of each Medusa process for up to 60 seconds, so hot paths do not re-read and decrypt on every call. An integration that is not configured, disabled, or incomplete is cached too, as `null`.

Whenever the integration changes, whether it is saved, enabled, disabled, or deleted, the module emits the [`integration.updated` event](/medusa-modules/integration/events), and its subscriber clears the cached entry. Consumers pick up new configuration without a redeploy.

<Note type="default" title="">

The cache is a map in each process's memory, and one process handles the event, so the event clears the cache in that process only. Medusa runs subscribers only in the `shared` and `worker` [worker modes](https://docs.medusajs.com/learn/production/worker-mode). In any deployment with more than one process, such as a separate worker or several server instances, the other processes keep serving the old options until their cached entry expires, within 60 seconds.

The connection test reads the same cache, so a test started right after a save can run against the old options in a process that has not cleared its entry.

</Note>
