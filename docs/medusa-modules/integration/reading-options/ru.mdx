# {frontmatter.title}

В этом руководстве вы узнаете, как читать параметры интеграции во время выполнения, после того как администратор магазина её настроил. Код, который их читает, называется потребителем. Часто это тот же пакет, что объявил интеграцию (например, платёжный провайдер, читающий собственные учётные данные), но им может быть и любой другой код, например API-роут, подписчик или запланированная задача.

<Note type="default" title="">

Вы получаете итоговые параметры, то есть модуль их расшифровал, проверил и применил к ним значения по умолчанию. Подробнее в разделе [Что значат «итоговые параметры»](#что-значат-итоговые-параметры).

</Note>

## Два способа чтения

Какой API использовать, зависит от того, где выполняется ваш код.

| Где выполняется код | Как читать |
| --- | --- |
| Провайдер в изолированном контейнере модуля или сервис модуля | [`resolveIntegrationOptions`](#хелпер-resolveintegrationoptions) |
| Код с контейнером приложения или запроса (API-роуты, подписчики, запланированные задачи, шаги воркфлоу) | [`getResolvedOptions`](#метод-сервиса-getresolvedoptions) |
| Шаг внутри вашего воркфлоу | [`getResolvedIntegrationOptionsStep`](#получение-параметров-внутри-воркфлоу) |

Платёжный или логистический провайдер выполняется внутри изолированного контейнера своего модуля, поэтому не может получить Модуль интеграций напрямую. Он использует `resolveIntegrationOptions`, который запускает воркфлоу, чтобы обратиться к Модулю интеграций. Код, у которого контейнер уже есть, получает модуль из контейнера и вызывает `getResolvedOptions` напрямую, без воркфлоу.

---

## Хелпер `resolveIntegrationOptions`

Используйте хелпер из провайдера, который не может обратиться к модулю интеграций напрямую.

### Базовое использование

Передайте идентификатор, который объявляет ваша интеграция, и тип-параметр для типизированных настроек. Например:

```ts title="providers/payment-my/services/my-payment.ts"
import { resolveIntegrationOptions } from "@gorgo/medusa-integration"
import type { MyOptions } from "../../integration-my/services/my-integration"

// внутри любого метода провайдера
const options = await resolveIntegrationOptions<MyOptions>({
  identifier: "my"
})
```

Возвращённый `options` типизирован как `MyOptions`, уже расшифрован и проверен.

<Note type="default" title="">

Хелпер запускает воркфлоу, а воркфлоу, запущенный без собственного контейнера, получает модули, загруженные на этот момент. Medusa собирает этот список один раз и использует его при каждом следующем запуске в процессе, а пока приложение стартует, загружены не все модули. Не вызывайте `resolveIntegrationOptions` в конструкторе провайдера или в `static validateOptions`. Вызывайте его из методов, которые выполняются позже.

</Note>

### Обращение к конкретному инстансу

Для провайдера, который поддерживает [несколько инстансов](/medusa-modules/integration/concepts#инстансы-и-их-идентификаторы), передайте `instance_id`. Опустите его или передайте `null` для инстанса по умолчанию.

Medusa создаёт платёжный или логистический провайдер, передавая ему только контейнер модуля и его собственные `options`, поэтому id инстанса Модуля интеграций провайдер от Medusa не получает. Две регистрации вы связываете сами. Задайте провайдеру интеграции `id` и передайте то же значение в `options` провайдера-потребителя в `medusa-config.ts`:

```ts title="medusa-config.ts"
const MY_INTEGRATION_ID = "my-1"

module.exports = defineConfig({
  // ...
  plugins: [
    {
      resolve: "@gorgo/medusa-integration",
      options: {
        providers: [
          {
            resolve: "@gorgo/medusa-payment-my/providers/integration-my",
            id: MY_INTEGRATION_ID,
            options: {},
          },
        ],
      },
    },
  ],
  modules: [
    {
      resolve: "@medusajs/medusa/payment",
      options: {
        providers: [
          {
            resolve: "@gorgo/medusa-payment-my/providers/payment-my",
            id: "my",
            options: {
              // должен совпадать с id провайдера интеграции выше
              id: MY_INTEGRATION_ID,
            },
          },
        ],
      },
    },
  ],
})
```

`id` внутри `options` провайдера-потребителя указывает инстанс Модуля интеграций. Он не связан с `id` в собственной записи платёжного провайдера, из которого Medusa собирает ключ платёжного провайдера.

Сохраните id инстанса в конструкторе базового класса провайдера-потребителя и передавайте его как `instance_id` при каждом вызове:

```ts title="providers/payment-my/core/my-base.ts"
import { AbstractPaymentProvider } from "@medusajs/framework/utils"
import { resolveIntegrationOptions } from "@gorgo/medusa-integration"
import type { MyOptions } from "../../integration-my/services/my-integration"

type MyPaymentOptions = {
  id?: string
}

export abstract class MyPaymentBase extends AbstractPaymentProvider<MyPaymentOptions> {
  protected instanceId_: string | null

  constructor(container: Record<string, unknown>, options: MyPaymentOptions) {
    super(container, options)
    this.instanceId_ = options.id ?? null
  }

  protected async resolveOptions(): Promise<MyOptions> {
    return resolveIntegrationOptions<MyOptions>({
      identifier: "my",
      instance_id: this.instanceId_,
    })
  }
}
```

`instanceId_` является свойством этого базового класса, которое конструктор заполняет из `options.id`. Базовый класс `AbstractPaymentProvider` из Medusa его не предоставляет. Если `options.id` не задан, свойство остаётся `null`, и провайдер получает параметры инстанса по умолчанию. Ваш платёжный провайдер наследует этот класс, как провайдер YooKassa наследует собственный базовый класс, и вызывает `this.resolveOptions()` из своих методов. Как тот же приём работает в логистическом провайдере, описано в руководстве [Миграция существующего провайдера Medusa на Модуль интеграций](/medusa-modules/integration/migrate-provider-to-integration-module).

### Когда интеграция не настроена

По умолчанию хелпер бросает `MedusaError`, если интеграция не настроена, выключена или не заполнена:

```ts
// бросит исключение, если интеграцией ещё нельзя пользоваться
const options = await resolveIntegrationOptions<MyOptions>({
  identifier: "my"
})
```

Передайте `{ optional: true }`, чтобы вместо этого получить `null` и обработать отсутствие настройки самостоятельно:

```ts
const options = await resolveIntegrationOptions<MyOptions>(
  { identifier: "my" },
  { optional: true }
)

if (!options) {
  // ещё не настроена: пропустите, используйте запасной вариант или верните понятную ошибку
}
```

С `{ optional: true }` не настроенная, выключенная или незаполненная интеграция даёт здесь `null` вместо исключения. Именно от этого случая защищает проверка `if (!options)` выше.

<Note type="default" title="">

`{ optional: true }` относится к интеграции, которая ещё не настроена, а не к той, что не зарегистрирована. Если под переданными идентификатором и инстансом не зарегистрирован ни один провайдер, хелпер бросает исключение в любом случае, потому что это указывает на ошибку в `medusa-config.ts`, например неверный `id`.

</Note>

## Метод сервиса `getResolvedOptions`

Когда у вашего кода уже есть контейнер, получите модуль из контейнера и вызовите `getResolvedOptions` напрямую. Это подходит для API-роутов, подписчиков, запланированных задач и шагов воркфлоу, и никакой воркфлоу не задействуется. Например, в API-роуте:

```ts title="api/admin/my-payment/route.ts"
import { INTEGRATION_MODULE, IntegrationModuleService } from "@gorgo/medusa-integration"
import type { MedusaRequest, MedusaResponse } from "@medusajs/framework/http"
import type { MyOptions } from "../../../providers/integration-my/services/my-integration"

export async function GET(req: MedusaRequest, res: MedusaResponse) {
  const integration: IntegrationModuleService = req.scope.resolve(INTEGRATION_MODULE)

  const resolved = await integration.getResolvedOptions("my")
  if (!resolved) {
    return res.status(503).send("My is not configured")
  }

  const options = resolved.options as MyOptions
  const { provider_id, category, is_enabled } = resolved.meta
}
```

`getResolvedOptions(identifier, instanceId?)` возвращает `ResolvedOptions | null`. Значение представляет собой `{ options, meta }`, где `meta` содержит `provider_id`, `category` и `is_enabled`. Результат `null` означает, что интеграция не настроена, выключена или не заполнена. Если под этими идентификатором и инстансом не зарегистрирован ни один провайдер, метод вместо этого бросает исключение. Остальные методы модуля описаны в справочнике [Сервис Модуля интеграций](/medusa-modules/integration/service).

## Получение параметров внутри воркфлоу

Когда вы собираете собственный воркфлоу, используйте экспортируемый шаг вместо хелпера:

```ts title="workflows/create-my.ts"
import { createWorkflow, WorkflowResponse } from "@medusajs/framework/workflows-sdk"
import { getResolvedIntegrationOptionsStep } from "@gorgo/medusa-integration"

export const createMyWorkflow = createWorkflow("create-my", () => {
  const resolved = getResolvedIntegrationOptionsStep({
    identifier: "my"
  })
  return new WorkflowResponse(resolved)
})
```

Шаг принимает `{ identifier, instance_id? }` и возвращает `{ options, meta } | null`. В отличие от хелпера `resolveIntegrationOptions`, для интеграции, которая не настроена, выключена или не заполнена, он возвращает `null` вместо исключения, поэтому проверяйте `null` в шагах, которые используют результат. Если под этими идентификатором и инстансом не зарегистрирован ни один провайдер, шаг бросает исключение, как и `getResolvedOptions`.

Также экспортируется `getResolvedIntegrationOptionsWorkflow`. Именно его хелпер запускает внутри себя.

## Что значат «итоговые параметры»

Итоговые параметры не совпадают с сырыми хранимыми значениями. Когда модуль их собирает, он делает три вещи:

- расшифровывает секретные поля,
- подтверждает, что интеграция включена и заполнена, то есть проходит полную валидацию,
- применяет значения по умолчанию из дескриптора для параметров, которые администратор так и не задал.

Если интеграция не настроена, выключена или не заполнена, она даёт `null`. В этом случае хелпер бросает исключение или возвращает `null` при `{ optional: true }`. Частичные черновики никогда не доходят до работающего приложения.

Схема ниже проводит один вызов `resolveIntegrationOptions` от вашего провайдера до базы данных и обратно:

```mermaid alt="Схема показывает, как один вызов resolveIntegrationOptions доходит до кэша и базы данных и что возвращается обратно"
sequenceDiagram
  participant provider as Провайдер
  participant helper as resolveIntegrationOptions
  participant service as Сервис
  participant cache as Кэш
  participant db as База данных
  provider->>helper: identifier, instance_id
  helper->>service: getResolvedOptions
  service->>cache: поиск по ключу
  alt кэш найден
    cache-->>service: значение или null
  else кэша нет
    service->>db: чтение записи
    db-->>service: запись
    opt запись включена
      service->>service: расшифровка, проверка, значения по умолчанию
    end
    service->>cache: сохранение на 60 с, null тоже
  end
  service-->>helper: параметры и meta или null
  helper-->>provider: параметры или ошибка при null
```

Сервис ищет интеграцию по ключу `int_<identifier>[_<instanceId>]`. Если запись есть в кэше, сервис сразу возвращает её, и значение в кэше может быть `null`. Если записи нет, сервис читает её из базы. Расшифровку, полную проверку и применение значений по умолчанию проходит только включённая запись, а отсутствующая, выключенная или не заполненная запись даёт `null`. Сервис кэширует результат на 60 секунд, включая `null`, а хелпер превращает `null` в ошибку, если вы не передали `{ optional: true }`. На схеме нет одной проверки: если под ключом не зарегистрирован ни один провайдер, сервис бросает исключение ещё до чтения записи.

## Кэширование и актуальность

Итоговые параметры кэшируются в памяти каждого процесса Medusa на срок до 60 секунд, чтобы на горячих путях не перечитывать и не расшифровывать их при каждом вызове. Ненастроенная, выключенная или незаполненная интеграция тоже попадает в кэш, как `null`.

При любом изменении интеграции (сохранении, включении, выключении или удалении) модуль отправляет [событие `integration.updated`](/medusa-modules/integration/events), и его подписчик сбрасывает запись в кэше. Потребители подхватывают новую конфигурацию без повторного развёртывания.

<Note type="default" title="">

Кэш хранится в памяти каждого процесса, а событие обрабатывает один процесс, поэтому оно сбрасывает кэш только в нём. Medusa запускает подписчиков только в [режимах](https://docs.medusajs.com/learn/production/worker-mode) `shared` и `worker`. При любом развёртывании больше чем с одним процессом, например с отдельным воркером или несколькими серверными инстансами, остальные процессы продолжают отдавать старые параметры, пока не истечёт срок их записи в кэше, то есть не дольше 60 секунд.

Проверка соединения читает тот же кэш, поэтому проверка, запущенная сразу после сохранения, может выполниться со старыми параметрами в процессе, который ещё не сбросил свою запись.

</Note>
