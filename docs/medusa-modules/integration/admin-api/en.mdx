# {frontmatter.title}

This reference lists the API routes the Integration Module adds under `/admin/integrations`. Medusa Admin uses them for every integration page, and your scripts and [custom widgets](/medusa-modules/integration/custom-sections) can use them too.

Like every Medusa `/admin` route, they require an authenticated admin user or a secret API key. Routes that take `:provider_id` respond with `404` when no provider is registered under that key.

## Integrations

| Method | Path | What it does |
| --- | --- | --- |
| `GET` | `/admin/integrations` | Lists every registered instance with its state. |
| `GET` | `/admin/integrations/:provider_id` | Returns one instance's descriptor, stored settings, and package details. |
| `POST` | `/admin/integrations/:provider_id` | Saves option values, through [`upsertIntegrationWorkflow`](/medusa-modules/integration/workflows#upsertintegrationworkflow). |
| `DELETE` | `/admin/integrations/:provider_id` | Deletes the stored settings, through [`deleteIntegrationWorkflow`](/medusa-modules/integration/workflows#deleteintegrationworkflow). |
| `POST` | `/admin/integrations/:provider_id/enable` | Enables or disables the integration, through [`setIntegrationEnabledWorkflow`](/medusa-modules/integration/workflows#setintegrationenabledworkflow). |
| `POST` | `/admin/integrations/:provider_id/test-connection` | Runs the connection test, through [`testIntegrationConnectionWorkflow`](/medusa-modules/integration/workflows#testintegrationconnectionworkflow). |

The routes that change settings pass the authenticated actor and the request's IP address, client, and ID to the workflow, so the [change history](/medusa-modules/integration/change-history) names the author.

### List Integrations

`GET /admin/integrations` accepts these query parameters:

- `q` – matches the provider's identifier or the instance id. The Admin searches translated names on its side.
- `category` – one category, such as `payment`.
- `limit` – from 1 to 1000, `20` by default.
- `offset` – `0` by default.

It returns `{ integrations, count, limit, offset, categories }`. Each item of `integrations` holds the instance's `provider_id`, `identifier`, `instance_id`, `category`, the i18n keys `display_name` and `description`, `icon`, the package's `version`, `author`, and `author_url`, the flags `supports_multiple_instances`, `has_test_connection`, `is_configured`, `is_enabled`, and `is_complete`, and `last_test_status`. `categories` lists the categories of every registered instance, whatever the filters.

### Save Option Values

`POST /admin/integrations/:provider_id` takes a body with these fields:

- `values` – the option values to save, keyed by option id.
- `section_id` – optional. With it, only that section's options are written. Without it, every submitted key the descriptor declares is written.
- `title` – optional. A title for the stored record, or `null` to clear it.

For example, to save the credentials section of the integration `int_my`:

```bash
curl -X POST "http://localhost:9000/admin/integrations/int_my" \
  -H "Authorization: Bearer {token}" \
  -H "Content-Type: application/json" \
  --data '{ "section_id": "credentials", "values": { "apiKey": "sk_test_123", "sandbox": true } }'
```

The response is `{ integration }`, the stored record without its secrets. `apiKey` from the request appears only by name, in `configured_secrets`. A value that fails validation gets a `400` response whose message lists every problem as `<option id>: <message>`.

## Change History

| Method | Path | What it does |
| --- | --- | --- |
| `GET` | `/admin/integrations/changes` | Lists the changes of every integration. |
| `GET` | `/admin/integrations/:provider_id/changes` | Lists the changes of one integration. |
| `GET` | `/admin/integrations/changes/:id` | Returns one change. |
| `GET` | `/admin/integrations/changes/actors` | Lists the authors of the history, for the author filter. |
| `GET` | `/admin/integrations/changes/fields` | Lists the options the history names, for the search. |

The history is read-only, and these routes accept nothing but `GET`.

### List Changes

Both list routes accept these query parameters:

- `limit` – from 1 to 100, `20` by default.
- `offset` – `0` by default.
- `order` – a field to sort by, with `-` in front for descending order. `-created_at` by default.
- `provider_id` – one or more instance keys. The route for one integration ignores it.
- `change_type` – one or more of `created`, `updated`, `enabled`, `disabled`, and `deleted`.
- `actor_id` – one or more user ids. `system` stands for every change made by anything but an admin user.
- `created_at` – a date range, with operators such as `$gte` and `$lte`.
- `q` – matches the author's email or API key title and the `provider_id`.
- `q_fields`, `q_providers` – with `q`, also match the changes that touched one of these option ids or label keys, or that belong to one of these instances. The Admin fills them in with what matches `q` in translated names.

They return `{ integration_changes, count, offset, limit }`, newest first by default.

## Catalog and Licenses

| Method | Path | What it does |
| --- | --- | --- |
| `GET` | `/admin/integrations/catalog` | Returns the [integration catalog](/medusa-modules/integration/browse-integrations), with `installed` and `provider_id` for every entry registered in the project. |
| `GET` | `/admin/integrations/license-status` | Returns the latest license check result of every paid Gorgo integration, as `{ packages }`. |
| `POST` | `/admin/integrations/license-status/recheck` | Checks the licenses right away and returns the fresh results in the same shape. |
