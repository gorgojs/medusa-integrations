# {frontmatter.title}

This reference lists the API routes the Integration Module adds under `/admin/integrations`. Medusa Admin uses them for every integration page, and your scripts and [custom widgets](/medusa-modules/integration/custom-sections) can use them too.

Like every Medusa `/admin` route, they require an authenticated admin user or a secret API key. A route that takes `:provider_id` responds with `404`, type `not_found`, and the message `Unknown integration "<id>"` when no provider is registered under that key.

The routes that take a body or query parameters validate them strictly, so an unknown key or an out-of-range value gets `400` with a message that starts with `Invalid request`. Body validation runs before the provider check, so an invalid body sent for an unknown provider gets `400`.

## Integrations

| Method | Path | What it does |
| --- | --- | --- |
| `GET` | `/admin/integrations` | Lists every registered instance with its state. |
| `GET` | `/admin/integrations/:provider_id` | Returns one instance's descriptor, stored settings, and package details. |
| `POST` | `/admin/integrations/:provider_id` | Saves option values, through [`upsertIntegrationWorkflow`](/medusa-modules/integration/workflows#upsertintegrationworkflow). |
| `DELETE` | `/admin/integrations/:provider_id` | Deletes the stored settings, through [`deleteIntegrationWorkflow`](/medusa-modules/integration/workflows#deleteintegrationworkflow). |
| `POST` | `/admin/integrations/:provider_id/enable` | Enables or disables the integration, through [`setIntegrationEnabledWorkflow`](/medusa-modules/integration/workflows#setintegrationenabledworkflow). |
| `POST` | `/admin/integrations/:provider_id/test-connection` | Runs the connection test, through [`testIntegrationConnectionWorkflow`](/medusa-modules/integration/workflows#testintegrationconnectionworkflow). |

The routes that change settings pass the authenticated actor and the request's IP address, client, and ID to the workflow, so the [change history](/medusa-modules/integration/change-history) names the author.

### List Integrations

`GET /admin/integrations` accepts these query parameters:

- `q` – matches the provider's identifier or the instance id. The Admin searches translated names on its side.
- `category` – one category, such as `payment`.
- `limit` – from 1 to 1000, `20` by default.
- `offset` – `0` by default.

It returns `{ integrations, count, limit, offset, categories }`. Each item of `integrations` holds the instance's `provider_id`, `identifier`, `instance_id`, `category`, the i18n keys `display_name` and `description`, `icon`, the package's `version`, `author`, and `author_url`, the flags `has_test_connection`, `is_configured`, `is_enabled`, and `is_complete`, and `last_test_status`. `categories` lists the categories of every registered instance, whatever the filters.

### Save Option Values

`POST /admin/integrations/:provider_id` takes a body with these fields:

- `values` – optional. The option values to save, keyed by option id. Without it, no option is written, for example when you change only `metadata`.
- `section_id` – optional. With it, only that section's options are written. Without it, every submitted key the descriptor declares is written.
- `title` – optional. A title for the stored record, or `null` to clear it.
- `metadata` – optional. Merged into the stored metadata key by key, as on any Medusa entity. A key set to an empty string is removed, and `null` clears the metadata. Metadata isn't part of the settings, so the change history doesn't list it.

For example, to save the credentials section of the integration `int_my`:

```bash
curl -X POST "http://localhost:9000/admin/integrations/int_my" \
  -H "Authorization: Bearer {token}" \
  -H "Content-Type: application/json" \
  --data '{ "section_id": "credentials", "values": { "apiKey": "sk_test_123", "sandbox": true } }'
```

The response is `{ integration }`, the stored record without its secrets. `apiKey` from the request appears only by name, in `configured_secrets`. A value that fails validation gets a `400` response whose message lists every problem as `<option id>: <message>`. An unknown `section_id` also gets `400`, with the type `invalid_data` and the message `Unknown section "<id>"`.

### Enable or Disable

`POST /admin/integrations/:provider_id/enable` takes the body `{ is_enabled }`, where `is_enabled` is a required boolean, and returns `{ integration }`. A registered provider with nothing saved yet gets `404`, type `not_found`, and the message `Integration "<id>" is not configured`. Setting the state the integration is already in returns `200` and records nothing in the change history.

### Delete the Settings

`DELETE /admin/integrations/:provider_id` takes no body and returns `{ id, object: "integration", deleted: true }`, where `id` is the instance key. The answer is `200` even when nothing was stored.

### Test the Connection

`POST /admin/integrations/:provider_id/test-connection` takes no body and always answers `200` for a registered provider, with `{ status, message? }`, where `status` is `passed`, `failed`, or `skipped`. An integration that is not configured, is disabled, or is incomplete gets `failed` with the message `Not configured`, and a test that throws gets `failed` with the error's message. A descriptor without a connection test gets `skipped` with the message `No test configured`.

## Change History

| Method | Path | What it does |
| --- | --- | --- |
| `GET` | `/admin/integrations/changes` | Lists the changes of every integration. |
| `GET` | `/admin/integrations/:provider_id/changes` | Lists the changes of one integration. |
| `GET` | `/admin/integrations/changes/:id` | Returns one change. |
| `GET` | `/admin/integrations/changes/actors` | Lists the authors of the history, for the author filter. |
| `GET` | `/admin/integrations/changes/fields` | Lists the options the history names, for the search. |

The history is read-only, and these routes accept nothing but `GET`. A `POST` or `DELETE` sent to `/admin/integrations/changes` reaches the `:provider_id` routes instead, which read `changes` as an instance key and answer `404` (`400` for a `POST` with an invalid body).

### List Changes

Both list routes accept these query parameters:

- `fields` – a comma-separated list of the fields to return. The list routes leave out `ip`, `user_agent`, and `request_id` unless you ask for them.
- `limit` – from 1 to 100, `20` by default.
- `offset` – `0` by default.
- `order` – a field to sort by, with `-` in front for descending order. `-created_at` by default.
- `provider_id` – one or more instance keys. The route for one integration ignores it.
- `change_type` – one or more of `created`, `updated`, `enabled`, `disabled`, and `deleted`.
- `actor_id` – one or more user ids. `system` stands for every change made by anything but an admin user.
- `created_at` – a date range, with operators such as `$gte` and `$lte`.
- `q` – matches the author's email or API key title and the `provider_id`.
- `q_fields`, `q_providers` – with `q`, also match the changes that touched one of these option ids or label keys, or that belong to one of these instances. The Admin fills them in with what matches `q` in translated names.

They return `{ integration_changes, count, offset, limit }`, newest first by default.

### Get a Change

`GET /admin/integrations/changes/:id` returns `{ integration_change }`, one change with every field, including `ip`, `user_agent`, and `request_id`. It accepts `fields` and answers `404` for an unknown id.

### Authors and Fields

`GET /admin/integrations/changes/actors` returns `{ users, system }`. Each item of `users` is `{ id, label }`, sorted by `label`, where `label` is the user's current name, else the current email, else the email stored with the user's changes, else `null`. `system` is `true` when anything but an admin user made a change, such as an API key or code run without a request.

`GET /admin/integrations/changes/fields` returns `{ fields }`, one `{ field, label }` for every option id and label key the history names, including those of options and integrations that no longer exist. `field` is the option id, or `@title` for the record's title, and `label` is the label key stored with the change, or `null`.

## Catalog and Licenses

| Method | Path | What it does |
| --- | --- | --- |
| `GET` | `/admin/integrations/catalog` | Returns the [integration catalog](/medusa-modules/integration/browse-integrations) merged with the install state of the project, as `{ integrations }`. |
| `GET` | `/admin/integrations/license-status` | Returns the latest license check result of every licensed package, as `{ packages }`. |
| `POST` | `/admin/integrations/license-status/recheck` | Checks the licenses right away and returns the fresh results in the same shape. |

### The Catalog Entry

`GET /admin/integrations/catalog` returns `{ integrations }`. Every item is an entry of the Gorgo catalog with `installed` and `provider_id`, which are `false` and `null` when the integration is not registered in the project.
