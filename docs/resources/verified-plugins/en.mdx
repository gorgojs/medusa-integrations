# {frontmatter.title}

The [Medusa plugin catalog](https://gorgojs.com/medusa/plugins) rates plugins with a **Quality Score**. It shows how many of the four groups of checks on this page a plugin passes, covering security, compatibility with the latest Medusa release, maintenance and documentation. A group counts as passed when the plugin passes every check in it.

The plugin page shows the score as a badge such as `3/4`. The badge is green at 4/4, orange at 2/4 and 3/4, and red below that. Hover over it or tap it to see the result of each group, the checks the plugin failed and why, the plugin version, the Medusa release and the check date.

In the catalog list, only plugins with a score of 4/4 carry the badge, and hovering over it shows the plugin version, the Medusa release and the check date. To see only these plugins, turn on the **Quality Score** filter in the catalog.

## What We Check

### Security

- **No install scripts** – the published package has no `preinstall`, `install` or `postinstall` script of its own.
- **No known vulnerabilities** – the plugin's own dependencies, apart from Medusa packages, have no known vulnerabilities rated high or critical.
- **No malware reports** – the OSV database has no malicious-package report for the plugin or its dependencies.
- **No secrets in the package** – the published archive has no `.env` files, key files or bundled `node_modules`, and none of its files contains a private key or a common API token.
- **No obfuscation** – the published JavaScript shows no signs of obfuscation.

### Compatibility

- **Medusa version ranges** – the version ranges the plugin declares for Medusa core packages admit the latest Medusa release.
- **Clean install** – the plugin installs into a new Medusa project on the latest release without `--force` or `--legacy-peer-deps`.
- **Build** – `medusa build` succeeds, including Medusa Admin with the plugin's admin extensions.
- **Migrations** – `medusa db:migrate` succeeds and, when the plugin ships migrations, creates its tables.
- **Startup** – the server starts, `/health` responds with `200`, and the startup log has no errors.

### Maintenance

- **Public repository** – the source code is in a public GitHub repository that is not archived, and the npm package is not deprecated.
- **Recent release** – the latest version was published no more than 180 days ago.
- **Up to date with Medusa** – the plugin was built against a Medusa release no more than four months older than the latest one, or its version ranges admit the latest release and it installs on that release without errors.
- **Tests in CI** – the repository has test files and a CI workflow that runs them.
- **Open-source license** – `package.json` declares an OSI-approved license.

### Documentation

- **Setup instructions** – the README shows how to install the plugin and register it in `medusa-config.ts`.
- **English** – the README is written mostly in English.
- **Environment variables** – the README lists every environment variable the plugin reads.

## How We Check Plugins

We read the package as npm publishes it, along with its public repository. To check compatibility, we install the plugin into a new Medusa project on the latest release with a PostgreSQL database, then build the project, run the migrations and start the server.

We use placeholder values instead of real API keys. That is enough to confirm that the plugin loads and starts, but not to test whether a payment goes through or a provider receives an order.

When a check can't run, for example because the GitHub API didn't respond, its group shows **Not checked** and doesn't count toward the score.

Our own plugins go through the same checks as every other plugin in the catalog. The [Maintenance](/resources/maintenance) page describes how we test and update them.

## What the Score Means

A score of 4/4 confirms that a specific plugin version passed these checks on a specific Medusa release. It is not an endorsement or a guarantee from us, so make sure a plugin fits your store before you use it in production.

The security checks look for known risks in the published package. They are not an audit of the plugin's code.

A lower score is not a warning. A plugin may work well and still fail one of the checks on this page, and the plugin page shows which one.

## For Plugin Authors

You don't need to apply. A plugin listed in the catalog scores 4/4 if it passes every check on this page. These steps help a plugin pass:

- Keep the `@medusajs/*` peer dependency ranges open to new minor releases instead of pinning an exact version.
- Host the public repository on GitHub, where we read the repository status.
- Describe the install command, the `medusa-config.ts` registration and every environment variable in the README.

If your plugin meets the criteria but scores lower, or you disagree with a result, write to the [Telegram support chat](https://t.me/gorgojs_chat) or open an issue in the [medusa-integrations](https://github.com/gorgojs/medusa-integrations/issues) repository on GitHub.
